# テスト要求設計 詳細判断基準

## 目的

仕様分析とテスト分析から、**何を検証・保証する必要があるか**をテスト要求として定義します。

Test Requirementはこのワークフロー固有の中間成果物であり、仕様とTest Conditionの間で検証責務を安定させ、AIが条件やケースへ早すぎる具体化をするのを防ぎます。

## 入力

必須:

- 対象仕様 / 決定を理解できる上流成果物
- テスト対象範囲

利用可能なら次も使います。

- `test-analysis`（テスト分析）のProduct Risk / テスト重点
- 案件コンテキスト
- 不明点・矛盾分析
- 承認済み`ASM`
- テストレベル / 観測方法

## Oracle Authority

テスト要求が製品の期待挙動を含む場合、根拠は原則として次に限定します。

1. `SPEC`
2. `DECISION`
3. `承認済み ASM`

Product Risk、実装、既存テスト、一般的慣習、未承認`INFERENCE`は単独で期待挙動を確定するAuthorityにはできません。

Product Riskは、要求を作る理由、優先度、深度には使えます。

## 抽象度

テスト要求は「何を検証するか」を表します。

含める:

- 検証対象の挙動 / ルール / 品質責務
- 期待される成立条件の意味
- 上流根拠
- Product Risk / 優先度
- テストレベル / 観測方法

含めない:

- 具体的入力値の列挙
- 境界値の具体展開
- 組合せ表
- 実行手順
- テストケースの前提 / データ / Step

それらは`test-condition-design`または`test-case-design`が担当します。

## 分割・統合の判断

1つのTest Requirementにまとめてよいのは、次が同じ検証責務として扱える場合です。

- 守るべき製品挙動
- 上流根拠
- 失敗時の意味
- テストレベル

次の場合は分割します。

- 異なる業務ルール
- 異なる権限責務
- 異なる状態 / ライフサイクル責務
- 成功 / エラーなど期待挙動の意味が別
- 追跡時にどの仕様を保証する要求か曖昧になる

ケース数削減のために無関係な責務を統合しません。

## 手順

### 1. 対象上流項目を整理する

対象Specification、Decision、承認済みAssumption、Product Risk、テストレベルを確認します。

### 2. 検証責務を抽出する

「この仕様が正しく実装されていると判断するために、何を保証する必要があるか」を記述します。

例:

- 権限ルールが適用されること
- 上限値ルールが適用されること
- 状態変更後に定義された表示・操作可否になること
- 指定されたエラー時に定義済み結果になること

### 3. Product Riskを接続する

関連Product Riskがある場合、要求の優先度・深度根拠として関連付けます。Product Riskだけから新しい期待挙動を作りません。

### 4. テストレベル / 観測方法を割り当てる

現在レベルで検証できない重要要求は消さず、次のいずれかへ位置づけます。

- 別テストレベル
- 残存リスク
- 対象外
- Blocked

### 5. 追跡性を確認する

各重要要求は、少なくとも1つの上流根拠へ戻れるようにします。

## 意味上の出力契約

各Test Requirementに必要な情報:

- 安定したID（例: `TR-001`）
- 検証責務
- 上流Specification / Decision / 承認済みAssumption
- 関連Product Risk
- 優先度
- テストレベル / 観測方法
- 対象外 / 残存 / Blockedならその理由

## 停止条件

次の場合、影響要求をBlockedとします。

- 何を保証すべきかを上流情報から決められない
- 期待挙動を未承認推論で埋めないと要求を書けない
- 相反する上流根拠が未解決
- テスト要求の対象範囲そのものが特定できない

Product Riskが未評価でも、仕様上の検証責務自体が明確なら要求作成は可能です。その場合は優先度根拠の制約を明示します。

## 品質ゲート

- 各重要要求が上流根拠へ追跡できる
- Product Riskを期待挙動のAuthorityにしていない
- 未承認`INFERENCE`を完成済み要求のOracleにしていない
- 「何を検証するか」に留まり、具体条件 / 手順を先回りしていない
- 要求同士の重複・過剰統合がない
- 現在レベル外の重要要求を消していない
- 優先度にProduct Riskまたは明示的案件重点の理由がある

## 次の担当Skill

- 不明点・期待挙動不明 → `question-analysis`
- Test Condition / Coverage Item設計 → `test-condition-design`
