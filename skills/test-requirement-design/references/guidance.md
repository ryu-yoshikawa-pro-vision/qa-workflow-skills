# テスト要求設計 詳細判断基準

## 目的

仕様分析とテスト分析から、**何を検証・保証する必要があるか**をTest Requirementとして定義します。

Test Requirementはこのワークフロー固有の中間成果物であり、仕様とTest Conditionの間で検証責務を安定させ、AIが条件やケースへ早すぎる具体化をするのを防ぎます。

## 入力

必須:

- 対象仕様 / 決定を理解できる上流成果物
- テスト対象範囲

利用可能なら`test-analysis`のProduct Risk / テスト重点、案件コンテキスト、不明点・矛盾分析、承認済み`ASM`、テストレベル / 観測方法も使います。

## Oracle Authority

Test Requirementが製品の期待挙動を含む場合、根拠は原則として次に限定します。

1. `SPEC`
2. `DECISION`
3. `承認済み ASM`

Product Risk、実装、既存テスト、一般的慣習、未承認`INFERENCE`は単独で期待挙動を確定するAuthorityにはできません。Product Riskは要求を作る理由、優先度、深度に使えます。

## 抽象度

Test Requirementは「何を検証するか」を表します。

含める:

- 検証対象の挙動 / ルール / 品質責務
- 期待される成立条件の意味
- 上流根拠
- Product Risk / 優先度
- テストレベル / 観測方法

含めない:

- 具体的入力値の列挙
- 境界値の具体展開
- 組合せ表
- 実行手順
- テストケースの前提 / データ / Step

Test RequirementはSpecificationの文を言い換えただけでは不十分です。「何を保証すればその仕様責務が検証されたと言えるか」が独立して分かる検証責務へ変換します。

## 分割・統合の判断

1つにまとめてよいのは、守るべき製品挙動、上流根拠、失敗時の意味、テストレベルが同じ検証責務として扱える場合です。

異なる業務ルール、権限責務、状態 / ライフサイクル責務、期待挙動の意味、または追跡責務を持つ場合は分割します。ケース数削減のために無関係な責務を統合しません。

## 優先度

関連Product Riskがある場合は、その最も高いリスクレベルを既定優先度として引き継ぎます。案件固有の明示的重点がある場合はそれも考慮できます。

上流より優先度を下げる場合は、対象外、別テストレベル、重複Coverage等の理由を明示します。理由なく高い上流優先度を下げません。

## 手順

1. 対象Specification、Decision、承認済みAssumption、Product Risk、テストレベルを確認する
2. 「この仕様が正しく実装されていると判断するために、何を保証する必要があるか」を検証責務として抽出する
3. 関連Product Riskを優先度・深度根拠として接続する
4. 現在レベルで検証できない重要要求を別テストレベル / 残存リスク / 対象外 / Blockedへ位置づける
5. 各重要要求が少なくとも1つの上流根拠へ戻れることを確認する

## 意味上の出力契約

各Test Requirementに必要な情報:

- 安定ID（例: `TR-001`）
- 検証責務
- 上流Specification / Decision / 承認済みAssumption
- 関連Product Risk
- 優先度
- テストレベル / 観測方法
- 対象外 / 残存 / Blockedならその理由

## 停止条件

次の場合、影響要求をBlockedとします。

- 何を保証すべきかを上流情報から決められない
- 期待挙動を未承認推論で埋めないと要求を書けない
- 相反する上流根拠が未解決
- 対象範囲そのものが特定できない

Product Riskが未評価でも仕様上の検証責務自体が明確なら要求作成は可能です。その場合は優先度根拠の制約を明示します。

## 品質ゲート

- 各重要要求が上流根拠へ追跡できる
- Specificationの単なる言い換えではなく検証責務になっている
- Product Riskを期待挙動のAuthorityにしていない
- 未承認`INFERENCE`を完成済み要求のOracleにしていない
- 「何を検証するか」に留まり、具体条件 / 手順を先回りしていない
- 要求同士の重複・過剰統合がない
- 現在レベル外の重要要求を消していない
- 優先度にProduct Riskまたは明示的案件重点の理由があり、上流より下げる場合は理由がある
