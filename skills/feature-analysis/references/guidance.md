# 情報源・機能階層・変更の判断

許可された案件root・source境界だけを調べます。Issue・仕様・設計・製品実装・既存テスト・PR差分のrevision、対象範囲、pagination、権限拒否、解析不能な場所をsource別に保持します。情報源取得完全性と製品全機能の発見完全性を混同しません。

初回には全対象候補を根拠付きで列挙し、PR更新・rebase・merge・release・資料改版の際には前回正本と現時点のsource revisionを比較します。変更ファイル件数は機能件数ではありません。

製品→領域→機能→サブ機能の必要な階層を持ち、UI・API・バッチ・認可・データ処理・外部連携を含めます。複数の実装要素が一機能を構成できます。semantic identityを変更しないpath移動では同じ機能IDを使用します。分割・統合・廃止では元IDを残し、履歴のfrom_ids/to_idsで旧機能との対応を保持します。

差分は根拠に基づいてimpact / no_impact / out_of_scope / unclassified / unresolvedを判定します。対象外とするなら承認refを持たせますが、その文字列の実認証は承認ownerの責務です。specificationの期待動作は実装の観測事実から推測して確定しません。

実providerのnative create-if-absent／CAS・過去revision・readbackが未確認なら、更新案と分析結果だけを残します。同じoperation_idの再受付、旧HEAD、競合、停止再開は上流正本を再読込し、無条件再書込みを避けます。

## Git情報源の取得

`scripts/git_source_inventory.py`に許可されたcheckout rootをrepository_root・authorized_rootとして同一の正本pathで渡し、base_sha／head_shaは完全なcommit SHAで指定します。初回はbase_sha=nullです。Gitファイル一覧とrename/moveのbefore/after pathを証拠として受取り、各ファイルを自動的に別機能と数えません。Gitの出力が大きすぎる・権限不足・HEAD不一致ならcompleteとせず再取得します。Git以外のIssue／仕様・設計情報源は権限のある提供経路で列挙し、未接続ならpartial／unavailableを保持します。

Git code sourceを取得した場合は、`git_source_inventory.py`のbase→head一覧と`reconcile_git_coverage.py`による変更path照合を記録します。機能対応率だけでGit差分の全件登録を推定しません。変更ファイル内の複数振る舞いや外部資料差分の分類は別途確認します。

イベント別の現在性は`event_basis`で検証します。rebaseは前回と今回のbaseを区別し、mergeはPR headではなくmerge commitをsource revisionとします。releaseはbuild refと対象commitを固定します。外部資料改版では同じ文書refの旧版と新版が前後snapshotに存在することを確認します。通知や取得の実行方式はSkill外で、入力のrevision文字列を権限確認済みsourceの代わりに扱いません。

Gitのgitlink／submoduleは親repositoryのtreeに現れていても、その内部内容は未確認として`unretrieved`へ記録し、別情報源として取得・確認するまでcompleteにしません。新しいDIFは根拠sourceの現revisionとafter_revisionを一致させます。過去のDIFは元revisionの履歴を維持します。

code sourceを含む機能台帳を正式保存するときは、信頼済み呼出し元が各source IDのGit rootとbase/head SHAを`git_inventory_requests`に指定し、`persist_snapshot`が実Gitの全tree／変更一覧を再取得・照合した後にCAS保存します。PR更新・rebase時は前回headを別の差分基準として明示します。保存前にcheckoutの`HEAD`が指定したhead SHAから進んだ場合は`git_head_changed`として拒否し、最新revisionで再分析します。前回取得したJSONだけを再使用した場合や、未確認のGit pathが残る場合には保存をblockします。provider／権限の選定は呼出し元の責務です。

継続PRで機能DIFを追記するときは前回のDIF行を残し、新しいbase→headと前回head→headの差分に対応するDIF IDを追加します。過去のDIFのrevision・分類・根拠を直接書き換えません。分類見直し時は新しいID、`supersedes_id`、別の根拠、承認ref／revisionで履歴をつなぎ、保存前に認可callbackで検証します。

複数Git repositoryはsource ID別に各HEAD・前回HEAD・baseを確認します。主イベントの`snapshot.source_revision`が全code sourceのHEADであるという前提は使用しません。保存前のGit列挙・差分照合を省略した旧入力だけではcurrentを確定しません。

継続PRの影響抽出では、DIFの履歴保存と今回の変更影響を分けます。CIと下流へ渡す変更分類率・影響機能・承認対象は**今回の差分**だけを対象とし、前回PRのDIFを再計上しません。同一のsource／旧revision／新revision／locatorに矛盾する有効なDIFがあればblockedとします。

再分類時は`supersedes_id`で保存済みDIFを指定し、承認側に旧・新の機能ID、sourceの参照とscope、旧・新revision、locator、証拠と承認revisionを提示します。承認済みの対象範囲と異なる新しい機能IDへの切替は保存不可とします。

複数repositoryが同一HEADを共有するPRイベントでは`event_basis.primary_source_id`で主sourceを指定します。主sourceの選択はSHAだけに頼らずsource IDで照合します。
