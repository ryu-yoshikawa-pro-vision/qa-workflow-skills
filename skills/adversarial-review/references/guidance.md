# 反証レビュー 詳細判断基準

## 目的

QA成果物を肯定するためではなく、**誤り・抜け・過剰・根拠不足・追跡性欠陥**を見つけるためにレビューします。

対象:

- 仕様分析
- テスト分析
- Test Requirement
- Test Condition / Coverage Item
- ローレベルTest Case
- Coverage Analysis

## レビュー姿勢

- 生成時の意図・説明を正当化根拠にしない
- 権威ある情報源と成果物から判断を再構成する
- 「一般的には必要」を理由に欠陥を作らない
- 実在するProduct Risk、仕様、Coverage Criteria、ケース実行性へ結び付けて指摘する
- 好みと欠陥を分ける

同一AIが自己レビューする場合も、生成時の推論を引き継いで正当化せず、Cold Reviewとして上流根拠から再判定します。

## 重大度

### `Critical`

成果物が重大に誤ったQA判断 / 実行を導き、修正なしで安全に利用できない。

例:

- 期待結果が権威ある仕様と逆
- 主要業務責務が大規模に欠落
- Oracleを創作して重大な誤判定を導く
- 追跡関係が破綻し、何を検証しているか判断不能

### `Major`

Coverage、追跡性、実行可能性、Oracle信頼性を実質的に弱める。通常は利用前に修正すべき。

### `Minor`

実在する品質問題だが、全体妥当性への影響は限定的。

### `Suggestion`

現在の欠陥ではない任意改善。

重大度は好みや修正工数ではなく、成果物利用時の影響で決めます。

## 成果物別プローブ

### 仕様分析

- `SPEC` / `DECISION` / `INFERENCE` / `UNKNOWN`を混同していないか
- 情報源優先順位を正しく適用しているか
- 実装・既存テストを仕様Authorityへ昇格していないか
- 重要ルール、状態、フロー、制約が欠落していないか
- 正式用語を独自名称へ置換していないか

### テスト分析

- Product Riskだけをリスクスコアへ使っているか
- 高 / 中 / 低の評価理由があるか
- リスクレベルが設計深度へ接続されているか
- 一般的QAチェックリストを根拠なくスコープ化していないか
- テストレベル / 観測方法が要求に合っているか
- 操作 / 観測 / PASS判定の最低限を確認しているか

### Test Requirement

- 上流Specificationへ追跡できるか
- 「何を検証するか」の抽象度を維持しているか
- Product Riskや実装から期待挙動を創作していないか
- 無関係な責務を過剰統合していないか
- 重要な現在レベル外責務を消していないか

### Test Condition / Coverage Item

- 適用技法にCoverage Criteriaがあるか
- 技法名だけでCoverage済みとしていないか
- Coverage Itemの明示 / 内包判断が一意か
- 境界値2値 / 3値の選択が根拠付きか
- Pairwiseを名乗る条件を満たすか
- Error Guessingを完全網羅と表現していないか
- 不要な条件軸 / 全組合せを追加していないか

### ローレベルTest Case

各重要ケースについて次を確認します。

- 誰が / どの状態で開始するか
- 何を準備するか
- 何を操作するか
- 何を入力 / 選択するか
- 何が起きればPASSか

さらに確認します。

- 別ケースの暗黙状態へ依存していないか
- 正式用語を使っているか
- 期待結果が観測可能か
- 重要期待結果が`SPEC` / `DECISION` / `承認済み ASM`へ追跡できるか
- Product Risk / 実装 / 既存テストを未定義Oracleにしていないか
- 許可されていないDB / API / ログ観測を要求していないか
- 必要Coverage Itemがケースへ落ちているか
- 統合可能な重複ケースがないか
- 無関係な目的を過剰統合していないか

### Coverage Analysis

- 件数比較を意味上のCoverageとして扱っていないか
- Coverage Criteria充足を確認しているか
- 重要Coverage ItemがDispositionされているか
- 高Product Risk Gapを見落としていないか
- 不十分なTest CaseをCoverage済みと誤認していないか
- フルワークフローで必要隣接リンクを省略していないか

## 機能固有の欠陥プローブ

仕様・Product Riskに関連する場合だけ、例えば次を検討します。

- リロード / 画面遷移
- 二重操作
- セッション切れ
- 複数タブ
- 空 / null相当
- 上限+1 / 下限-1
- 特殊文字 / IME / オートフィル
- 権限変更
- 状態復旧
- 日時境界
- 互換性 / 画面幅

一覧に存在するという理由だけで「抜け」と判定しません。

## 過剰テストの確認

- 重複ケース
- 機械的な全組合せ
- Product Risk根拠のない非機能チェック
- 同じ前提 + 操作 + データ意味 + Oracleの複数ケース
- 低リスク詳細への過剰展開

## 不足テストの確認

- 高Product Risk業務ルールが未テスト
- 重要な権限差が未テスト
- 必要な状態遷移が未テスト
- 明示境界が未テスト
- Coverage Criteriaに必要な項目が未テスト
- 指定エラー / 復旧挙動が未テスト
- 上流要求に対する下流検証が弱い

## 修正責務

指摘は最も早い責任層へ戻します。

- 仕様モデル → `spec-analysis`
- 不明点 / Oracle不明 → `question-analysis`
- Product Risk / テスト重点 → `test-analysis`
- Test Requirement → `test-requirement-design`
- Test Condition / Coverage Criteria / Coverage Item → `test-condition-design`
- Test Case → `test-case-design`
- Coverage判定 → `coverage-analysis`
- 案件固有設定 → Project Context / 仕様決定

本Skill自身が他層成果物を再設計しません。

## 再レビュー

`Critical` / `Major`修正後は影響範囲を再レビューします。

修正が下流の意味・追跡関係を変える場合だけ、再レビュー範囲を下流へ広げます。

## 意味上の出力契約

各指摘に必要な情報:

- 指摘ID
- 重大度
- 対象成果物 / ID
- 問題
- 根拠
- 影響
- 推奨修正先Skill
- 処置状態: 未対応 / 修正済み / 残存リスクとして受容 / Blocked

## 品質ゲート

- 指摘が権威ある情報源・Product Risk・Coverage Criteria等の根拠を持つ
- 好みを欠陥として報告していない
- 一般的チェックリストを機械適用していない
- `Critical` / `Major`の影響説明が具体的
- 修正先が最も早い責任Skillになっている
- 本Skill自身が他層成果物を書き換えていない
- `Critical` / `Major`修正後の再レビュー範囲が妥当

本Skillは正式なISTQB / ISOのインスペクション手順そのものではなく、このワークフロー向けの反証レビューです。
