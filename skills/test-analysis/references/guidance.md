# テスト分析 詳細判断基準

## 目的

仕様・変更情報を、**何を、なぜ、どの深さでテストするか**というProduct Riskベースのテスト戦略へ変換します。

## 入力

必須: 対象挙動と要求範囲を理解できる仕様情報。

利用可能なら次も使います。

- 仕様分析
- 不明点・矛盾分析
- 案件コンテキスト
- 変更情報 / 実装依存
- 既存テスト / 不具合
- 障害履歴 / 利用頻度 / 業務重要度

定量根拠がない場合に数値事実を創作しません。

## テストレベル

ユーザー、案件コンテキスト、再利用する有効成果物に指定がなく、依頼が別レベルを明示していない場合は**システムテスト**を既定とします。

このSkillで決めたテストレベルは後続Skillへ引き継ぎます。

## Product Risk

本Skillでリスクスコアへ入れるのはProduct Riskだけです。

例:

- 主要機能が使えない
- 業務ルールが破綻する
- データが誤る / 欠損する
- 権限制御が破綻する
- 状態遷移が不正になる
- 必要な通知が届かない
- ユーザーが誤った結果を認識する
- 明示された非機能要件を満たさない

人員、納期、予算、組織、環境準備スケジュールなどのProject Riskはリスクスコアへ混ぜません。既知の実施不能を生む場合は案件制約として扱います。

## リスク評価

案件固有方式がない場合は次を使います。

```text
リスクスコア = 影響度 × 発生可能性
```

各値は1〜4。

### 影響度

- 4: サービス停止、重大業務失敗、重大損失、重要データ / 権限破綻
- 3: 主要機能が利用不能または重大に誤動作
- 2: 一部制限、利用者影響あり、回避策が必要
- 1: 軽微な影響

### 発生可能性

統計的確率ではなく、複雑性、新規性、変更量、不安定さ、過去不具合等を代理指標とするヒューリスティック評価です。

- 4: 失敗しやすい根拠が強い
- 3: 意味のある変更 / 複雑性 / 不安定要因がある
- 2: 比較的安定、複雑性は中程度
- 1: 単純、低変更、失敗要因が少ない

### リスクレベル

- 高: 12〜16
- 中: 6〜11
- 低: 1〜5

スコアは判断補助であり、根拠説明を置き換えません。

## Risk → 設計深度

### 高

- 選択技法のCoverage Criteriaを原則満たす
- 仕様・リスクに関連する境界、状態、権限、主要エラー / 復旧を積極的に検討する
- Coverage削減には理由を残す

### 中

- 選択技法の基本Coverageを満たす
- 組合せ、エラー推測、復旧等は仕様・失敗機構・過去不具合等の根拠がある場合に追加する

### 低

- 主挙動を代表するCoverageを確保する
- 一般的エッジケースを機械的に追加しない
- 不要な組合せを展開しない

これはケース件数ノルマではありません。仕様構造・失敗機構によって調整する場合は理由を残します。

## テスト可能性

後続のローレベルケースへ落とせる最低限として次を確認します。

- 操作可能か
- 結果を観測可能か
- PASS / FAILを判断するOracleがあるか

必要なデータ・状態・環境の準備方法が未確定という理由だけでは停止しません。設計時点ですでに準備不能と分かる条件は制約として扱います。

## 手順

### 1. 範囲を定義する

対象機能 / 変更、ロール、画面 / フロー、テストレベル、対象外、既知制約、Blockerを整理します。

### 2. 変更・影響を整理する

変更がある場合は、新規、変更、削除、直接影響、証拠に基づく回帰影響候補を区別します。理論上の依存だけで製品全体へ広げません。

### 3. Product Risk候補を出す

仕様ルール、変更複雑性、状態 / フロー、権限差、境界、依存、過去不具合、ユーザー / 業務影響、対象非機能要件等から候補を出します。

### 4. 関連性を評価する

各候補について次を確認します。

- どの仕様 / 変更 / 依存が根拠か
- どの製品失敗が起こり得るか
- 現在のテストレベルで意味があるか
- 対象範囲内か

一般的QAチェックリストにあるだけの候補は採用しません。

### 5. リスクを評価する

上記既定方式または案件固有方式で評価し、理由を残します。

### 6. テスト重点を決める

高 / 中 / 低の設計深度に基づき、どこへ厚く・薄くテスト資源を配分するか決めます。

### 7. テストレベル / 観測方法を決める

各重要要件を次へ位置づけます。

- 現在レベルで検証
- 別テストレベル
- 残存リスク
- 対象外

UI中心のシステムテストではUIから観測可能な結果を優先し、非UI要件のために架空のUI Oracleを作りません。

### 8. テスト技法を選ぶ

問題構造に合う場合だけ選びます。

候補:

- 同値分割
- 境界値分析
- デシジョンテーブル
- 状態遷移
- Pairwise / 組合せ
- エラー推測
- シナリオ / ユースケース

具体的Coverage Criteria / Coverage Itemは`test-condition-design`（テスト観点・条件設計）が定義します。

## 意味上の出力契約

- 分析範囲 / 制約
- 変更・影響領域
- Product Riskと根拠
- リスクレベル
- テスト重点
- 選択技法と適用領域
- テストレベル / 観測方法
- 最小限のテスト可能性
- 対象外 / 残存リスク
- Blocker

## 停止条件

次の場合、影響範囲をBlockedとします。

- テスト対象範囲を意味のある程度に特定できない
- 成功条件が重大に不明
- 情報源矛盾で守るべき挙動を決められない
- 変更影響分析に不可欠な証拠がない
- 重要対象のPASS / FAIL根拠がなく、後続で仕様を創作するしかない

データ / 状態 / 環境の準備方法が未決、本番定量データがない、低確度リスクを定性的に扱う、一部範囲だけのBlockerでは全体停止しません。

## 品質ゲート

- 重要なテスト重点に仕様 / 変更 / 依存 / Product Risk根拠がある
- Project Riskをリスクスコアへ混ぜていない
- 数値スコアが理由説明を代替していない
- リスクレベルが設計深度へ接続されている
- リスクから未定義の期待結果を作っていない
- 操作 / 観測 / PASS判定の最低限を確認している
- UIから見えない重要要件を消していない
- 詳細Test Requirement / Test Condition / Test Caseを先回りしていない
