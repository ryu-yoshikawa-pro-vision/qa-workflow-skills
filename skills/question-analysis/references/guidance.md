# 不明点・矛盾分析 詳細判断基準

## 目的

仕様・QA成果物に含まれる曖昧さ、矛盾、欠落、未解決事項を、**下流成果物を止める必要があるか**という観点で分類します。

## 入力

利用可能な次の情報を使います。

- 仕様分析
- 権威ある情報源
- 案件コンテキスト
- 確定事項
- 既存質問 / 回答
- 実装証拠
- 対象となるQA成果物

## 分類基準

### `Blocker`

回答・決定がないと、影響する成果物の正しさを成立させられない事項。

判定例:

- 成功条件 / 期待結果を決められない
- 相互排他的な仕様が同優先度で残る
- 主要業務ルールをどちらとして扱うべきか決められない
- 対象範囲そのものを特定できない

Blockerは質問の重要そうな度合いではなく、**現在要求されている成果物を妥当に作れるか**で決めます。

### `要確認`

回答によって設計が変わり得るが、現在の情報だけでも嘘をつかず妥当な成果物を作れる事項。

- 未確認であることを成果物へ残す
- 1つの可能性を仕様として固定しない
- 回答後に影響範囲だけ再評価する

### `仮定可能`

明示的な暫定仮定を置けば安全に作業を継続できる事項。

仮定は`SPEC`ではありません。最終Oracleへ使用する場合は、権限を持つユーザー / ステークホルダーが明示的に承認し、`ASM-xxx`として`承認済み`にします。

### `提案・任意`

製品の期待挙動を確定する質問ではなく、改善案、追加確認、設計上の任意選択など。回答がなくても要求成果物の妥当性へ影響しません。

## 判断順序

質問化する前に次を順番に確認します。

1. 案件固有の情報源優先順位で解決できないか
2. 既存の`DECISION`で解決済みではないか
3. 承認済み`ASM`で暫定解決済みではないか
4. 高優先度仕様と実装が違うだけではないか
5. 本当に下流判断に影響するか

上位情報源で期待挙動が決まっている実装差分を、製品仕様の質問へ戻しません。

## 手順

### 1. 不明点候補を抽出する

- 曖昧な表現
- 情報源間矛盾
- 必要条件の欠落
- 未定義の優先順位
- 状態 / 権限 / 境界の未確定
- Oracle不足
- 下流成果物で暗黙に置かれた仮定

### 2. 重複・解決済みを除外する

既存質問、回答、決定、情報源優先順位を確認し、同じ論点を再質問しません。

### 3. 影響成果物を特定する

例:

- Specification
- Test Requirement
- Test Condition / Coverage Item
- Test Case / Oracle
- Coverage Analysis

### 4. 分類する

「回答がない場合、その成果物を妥当に作れるか」を基準に`Blocker` / `要確認` / `仮定可能` / `提案・任意`へ分類します。

### 5. Blocker範囲を局所化する

あるロール、画面、条件だけに影響する場合は、その範囲だけをBlockedにします。無関係な範囲まで停止しません。

### 6. 仮定を管理する

仮定を使う場合は少なくとも次を明示します。

- 仮定内容
- 根拠
- 影響範囲
- 状態: 提案 / 承認済み / 撤回 / 置換済み

AI自身の推論を`承認済み`へ変更しません。

## 意味上の出力契約

各重要事項について次を伝えます。

- 安定した質問 / 論点ID
- 分類
- 内容
- 根拠 / 情報源
- 影響する成果物 / 範囲
- 回答がない場合の扱い
- 仮定可能なら仮定案
- Blocked範囲
- 回答後の再開先Skill

## 停止・継続判断

このSkill自身は質問が存在するだけで全体停止しません。

- `Blocker` → 影響範囲を停止
- `要確認` → 明示したまま継続
- `仮定可能` → 仮定を分離して継続可能
- `提案・任意` → 継続

`gated`モードでは、非Blocker質問も現在ゲートの成果物として提示しますが、分類自体は変えません。

## 品質ゲート

- 解決済み事項を再質問していない
- Blocker判定が下流成果物への実害に基づいている
- Blocker範囲を必要以上に広げていない
- `要確認`を暗黙の期待挙動へ変えていない
- `仮定可能`を仕様扱いしていない
- `承認済み ASM`は明示承認を根拠にしている
- 実装差分を不要な仕様質問へ戻していない
- 各論点の再開先がCanonical Skill名で一意に分かる

## 再開先

論点解消後は、意味が変わる最も早い担当Skillへ戻します。

例:

- 仕様モデルが変わる → `spec-analysis`
- Product Risk / テスト重点が変わる → `test-analysis`
- テスト要求が変わる → `test-requirement-design`
- 条件 / Coverage Itemが変わる → `test-condition-design`
- ケース / Oracleだけが変わる → `test-case-design`
