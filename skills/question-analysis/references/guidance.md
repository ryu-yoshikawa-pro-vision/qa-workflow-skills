# 不明点・矛盾分析 詳細判断基準

## 目的

仕様・QA成果物に含まれる曖昧さ、矛盾、欠落、未解決事項を、**下流成果物を止める必要があるか**という観点で分類します。

## 入力

必須:

- 分類対象となる不明点、矛盾、欠落、未解決事項
- その論点を判断できる仕様分析、現在有効な仕様根拠、権威ある情報源、正本一覧、対象QA成果物等の根拠

利用可能なら案件コンテキスト、既存質問 / 回答、実装証拠、前後のQA成果物も使います。

## 処理

各未解決事項を下流成果物への影響で`ブロッカー` / `要確認` / `仮定可能` / `提案・任意`へ分類し、停止・継続範囲、回答なしの場合の扱い、回答後の仕様根拠正規化先と再開先Skillを決めます。

## 分類基準

### `ブロッカー`

回答・決定がないと、影響する成果物の正しさを成立させられない事項。

例:

- 成功条件 / 期待結果を決められない
- 相互排他的な有効仕様根拠が残る
- 主要業務ルールをどちらとして扱うべきか決められない
- 対象範囲そのものを特定できない
- 完成済みテストケースのPASS / FAILが未承認仮定に依存する

ブロッカーは重要そうかではなく、**現在要求されている成果物を妥当に作れるか**で決めます。

### `要確認`

回答によって設計が変わり得るが、現在情報だけでも嘘をつかず妥当な成果物を作れる事項。

### `仮定可能`

最終判定根拠を確定しない分析・ドラフト等の範囲で、明示的な暫定仮定を置けば安全に作業を継続できる事項。

仮定は`SPEC`ではありません。完成済みテストケースのPASS / FAILへ使用するには、権限を持つユーザー / ステークホルダーの明示承認と正本の仮定一覧への記録が必要です。

### `提案・任意`

製品の期待挙動を確定する質問ではなく、改善案、追加確認、任意選択など。回答がなくても要求成果物の妥当性へ影響しません。

## 正本の仮定管理

仮定候補は本Skillで提案できますが、`承認済み ASM-xxx`の正本はProject Contextまたは案件で明示された正本の仮定一覧です。

- 提案段階では正規ASM IDを必須にしない
- AI自身の判断で`承認済み`へ変更しない
- 承認後に正本一覧へ採番・反映してから判定根拠へ利用する
- 有効な`SPEC` / `DECISION`と競合する仮定を`承認済み ASM`として上書き利用しない
- 正式挙動として確定した内容は仮定のまま残さず、仕様更新または`DECISION`へ正規化する

## 回答の正規化

質問への回答を受けた後は、その回答を下流へ直接流さず、期待挙動の仕様根拠として次のいずれかへ正規化します。

### 情報源自体が更新された

更新された権威ある情報源を`SPEC`として扱い、`spec-analysis`で再解析します。

### ステークホルダー判断として正式に確定した

正本の決定事項一覧へ`DEC-xxx`として記録し、状態・影響範囲・補足 / 上書き / 置換関係を明示します。

### 暫定的な前提としてのみ合意した

正本の仮定一覧へ`ASM-xxx`として記録し、`承認済み`にします。有効な`SPEC` / `DECISION`を上書きする用途には使いません。

回答の意味がどれに当たるか判断できない場合は、勝手に`DECISION` / `ASM`へ昇格させず再確認します。

## 判断順序

質問化する前に次を順番に確認します。

1. 現在有効な仕様根拠で解決済みではないか
2. 既存`DECISION`で解決済みではないか
3. `承認済み ASM`で暫定解決済みではないか
4. 高優先度仕様と実装が違うだけではないか
5. 本当に下流判断に影響するか
6. 最終成果物のPASS / FAILがその未確定事項へ依存するか

上位仕様根拠で期待挙動が決まっている実装差分を、製品仕様の質問へ戻しません。

## 手順

1. 曖昧表現、矛盾、欠落、未定義優先順位、判定根拠不足、暗黙仮定等の候補を抽出する
2. 既存質問、回答、現在有効な仕様根拠を確認し、重複・解決済みを除外する
3. 影響成果物と範囲を特定する
4. `ブロッカー` / `要確認` / `仮定可能` / `提案・任意`へ分類する
5. ブロッカー範囲を局所化する
6. 仮定を使う場合は内容、根拠、影響範囲、状態を明示する
7. 回答後は`SPEC` / `DECISION` / `承認済み ASM`のいずれかへ正規化してから、意味が変わる最も早いSkillへ戻す

## 出力

各分類対象の未解決事項について次を伝えます。

- 安定した論点ID
- 分類
- 内容
- 根拠 / 情報源
- 影響する成果物 / 範囲
- 回答がない場合の扱い
- 仮定可能なら仮定案
- ブロック中範囲
- 回答後の正規化先
- 再開先Skill

## 停止・継続判断

- `ブロッカー` → 影響範囲を停止
- `要確認` → 明示したまま継続
- `仮定可能` → 最終判定根拠を確定しない範囲で継続可能
- `提案・任意` → 継続

`gated`モードでは非ブロッカー質問も現在ゲートの成果物として提示しますが、分類自体は変えません。

## 品質ゲート

- 解決済み事項を再質問していない
- ブロッカー判定が下流成果物への実害に基づいている
- 最終PASS条件が未承認仮定に依存する場合をブロッカーとしている
- ブロッカー範囲を必要以上に広げていない
- `要確認`を暗黙の期待挙動へ変えていない
- `仮定可能`を仕様扱いしていない
- `承認済み ASM`は明示承認と正本一覧を根拠にしている
- `ASM`で有効な`SPEC` / `DECISION`を上書きしていない
- 回答後の期待挙動を生の会話情報のまま判定根拠へ流していない
- 実装差分を不要な仕様質問へ戻していない
- 各論点の再開先が正規Skill名で一意に分かる

## 再開先

論点解消後は、意味が変わる最も早い担当Skillへ戻します。

- 仕様モデル / 現在有効な仕様根拠が変わる → `spec-analysis`
- プロダクトリスク / テスト重点が変わる → `test-analysis`
- テスト要求が変わる → `test-requirement-design`
- テスト条件 / カバレッジ項目が変わる → `test-condition-design`
- テストケース / 判定根拠だけが変わる → `test-case-design`

## 出力前自己検証

最終出力前に、実際に利用した入力が本Skillの入力契約を満たし、入力・仕様根拠・判断状態に停止条件へ該当する未解決状態がないか確認します。あわせて、生成した成果物へ本Skillの出力契約と既存の品質ゲートを再適用します。品質基準は本ガイダンスの既存定義を正本とし、自己検証専用のrubricやチェックリストを別定義しません。

1. 実際に利用した入力が入力契約を満たし、停止条件へ該当する未解決状態がないか確認する
2. 生成した成果物が出力契約と既存の品質ゲートを満たしているか確認する
3. 明白かつ局所的で、新しい領域判断を必要としない契約違反だけを最大1回修正する
4. 修正後は修正箇所を含めて最終確認する。解消に新しい仕様根拠、上流判断、他Skillの領域固有ロジックが必要な場合は自力で補完せず、既存の停止条件・ブロック中・ルーティングに従う
5. 最終確認後も本Skill自身の契約違反が残り、既存の停止条件・ブロック中・ルーティングに該当しない場合は、2回目の自動修正を行わず、その成果物を契約適合済み・完成済みとして扱わない。現在残っている契約上の制約だけを明示する

未解決事項の分類や仮定の承認状態を自己検証の名目で変更しません。既存の`ブロック中`定義を未解消ローカル違反へ広げません。自己検証の実行経緯、修正回数、修正前状態、PASS / FAIL等の評価ログは通常成果物へ出力せず、現在有効な状態と未解消の契約上の制約だけを返します。
