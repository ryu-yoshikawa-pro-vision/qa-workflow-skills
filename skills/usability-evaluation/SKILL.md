# Usability Evaluation

Review the evaluation scope before producing conclusions.

1. Read [the reference index](references/index.md), then follow only the relevant pattern, accessibility, heuristic, and platform links. Do not load the whole corpus.
2. Identify the target, platform, current state, available evidence, and evaluation purpose. Use user, goal, task, success condition, and business context only when supplied by the request, project Authority, or evidence. Do not invent user research or user behavior. Facts explicitly reported in the request or `input.md` are evidence for those facts: cite that input and say when the underlying artifact was not directly inspected. Do not discard a reported fact solely because its raw screenshot, snapshot, or other file is not attached, and do not infer details beyond the report.
3. Separate observed facts from interpretation. Cite evidence refs for facts and source item refs for reference based claims. Resolve each source item to its exact reference entry using the package catalog; preserve that mapping and the source's position in each applied-reference row. For versioned criteria such as WCAG, resolve a version-specific catalog item only when the request, project Authority, or input identifies that exact version. Otherwise preserve the reported criterion as written without inferring a version or adding adjacent criteria that were not supplied or evidenced. Source identity is separate from topical similarity: never map an unnamed or paraphrased platform / generic recommendation to a similar catalog item. If input reports an unnamed or unresolved reference, preserve the report and its uncertainty; do not drop it, call the entire case reference-free, or guess a source/item. Apply only directly relevant, independently identified references; when no public reference directly covers the evaluated issue, leave `applied_references` empty and record why the reference was not used instead of attaching broad advisory material. Evaluate independently identified references on their own. Keep project Authority refs in their separate field, not as public source items.
4. Distinguish normative criteria, informative pattern guidance, advisory heuristics, project Authority, and platform guidance. A public recommendation is not project binding unless the project adopted it or an applicable Authority makes it binding. If an input names a generic pattern without identifying its source or item, preserve it as unresolved; do not assign it a normative, informative, advisory, or project-binding position.
5. Use DOM/accessibility evidence for role, accessible name, states, and structure; interaction evidence for keyboard and state transitions; screenshots for visible layout, hierarchy, overlap, clipping, and focus visibility. A screenshot alone cannot establish keyboard behavior or accessible name.
6. Treat saved `test-target-inspection` / `test-execution` evidence as read-only input only when the same request, project scope, and workflow explicitly selected UI / UX evaluation. Do not operate a browser or second session. For a live interaction request, hand off to `usability-inspection` through `qa-workflow`.
7. Select top-level aspects from the requested scope and available evidence; do not mark every aspect as evaluated by default. Close every fixed top-level aspect as evaluated or out of scope with a reason. Each evaluated aspect needs one or more result rows with a permitted basis and applicable evidence. When one underlying issue has one corrective action, evaluate it once in its primary aspect; do not duplicate the same Finding across rows unless the evidence supports distinct concerns and distinct actions. A screenshot that reports a visible overlap can support a visual-integrity result when that aspect is in scope, even if it does not establish whether a separate interaction or normative criterion is satisfied. Keep the visible issue, any distinct corrective action, and an undetermined functional or conformance question separate; do not attach a Finding to the undetermined question unless a distinct downstream action is supported. Facts summarized in the request or `input.md` remain usable evidence for those reported facts even when the original Figma frame is unavailable; identify them as input-reported and do not claim direct inspection. Evaluate only the design choices supported by that summary. Close runtime-dependent behavior as out of scope in a design-only evaluation; use undetermined only for a requested design question whose design evidence is genuinely insufficient. Appearance alone does not prove that an interaction pattern is applicable or defective: when the supplied task requires simultaneous comparison but the evidence shows only one panel, do not assert a hidden-row labeling defect or require a Finding without evidence of that defect or a distinct downstream action.
8. Preserve test results as recorded. Do not change TC PASS / FAIL or score Product Risk. Route binding Authority conflicts to the responsible owner.
9. Decide semantically whether follow-up is required beyond closing the current evaluation. `判定不能`, missing evidence, or an optional routing recommendation alone does not require a Finding. An additional-observation request to the current evidence/session owner is separate from a Finding: identify its request, owner, scope, target/state, canonical observation field, and input evidence refs in the helper input, but do not treat the request itself as a confirmed product issue or automatically create a Finding. Request only fields that are still missing and necessary to close the selected question; do not request information already reported or linked as evidence. If a selected question remains undetermined and an allowed fixed observation from an identified current owner can resolve it, create the structured additional-observation request instead of leaving the observation need only in prose. Set `follow_up_required` and link a PR #13 Finding only when a distinct downstream QA action is actually required, such as correcting a confirmed issue. Use the actual Finding ref supplied or created through the existing PR #13 artifact path; never use a contract/type label as a ref or invent an ID. If a required Finding cannot be linked through that path, leave the artifact incomplete and report the blocker. Do not substitute prose-only routing, start another browser session, or hand-generate IDs, signatures, or fingerprints.

An advisory heuristic and one input-reported exploratory observation may support a bounded expert UX concern, but do not by themselves establish a defect or required corrective action. Keep that distinction in the result: an improvement suggestion or verification step is optional unless the evidence or applicable Authority makes it required. Do not set `follow_up_required` or link an available Finding solely because the heuristic suggests a possible improvement.
10. Enter semantic decisions into the normalized input for `scripts/evaluation_structure.py`, resolving references with the production catalog helper as needed. Use `success-condition` basis only when `condition.success_condition`, `condition.business_outcome`, or `condition.business_rule` is explicitly supplied; a TC assertion alone does not establish that basis. If materialization fails, correct the semantic input and rerun the helper; do not report a complete artifact until it succeeds. Copy its machine-owned Markdown sections intact; do not hand-assign refs, closure rows, Finding requirements, signatures, fingerprints, or counts.

Use [the output template](assets/output-template.md). Record missing evidence as a limitation or undetermined result instead of guessing.
