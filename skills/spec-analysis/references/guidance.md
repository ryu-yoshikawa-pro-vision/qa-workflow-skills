# 仕様分析 詳細判断基準

## 目的

情報源を、後続QA設計で利用できる追跡可能な仕様モデルへ整理します。テスト要求・テスト観点・テストケースへ先回りしません。

## 入力

必須: 対象機能・挙動について利用可能な情報源が1つ以上あること。

利用可能なら次も使います。

- 案件コンテキスト
- 情報源優先順位
- 対象範囲
- 正式用語
- 確定事項
- 変更差分
- Issue / チケット
- 実装情報
- 既存QA成果物

既存QA成果物と実装は補助証拠であり、自動的に仕様の権威にはしません。

## 情報分類

### `SPEC`

案件で権威ある情報源に明記されている挙動。

### `DECISION`

正式な後続判断として確定した挙動。元仕様を補足・上書きする場合も元記載と区別します。

### `INFERENCE`

証拠に基づく合理的解釈だが、明記・確定されていない内容。`SPEC`として扱いません。

### `UNKNOWN`

利用可能な根拠だけでは結論を出せない内容。一般的慣習や類似製品の挙動で埋めません。

## 情報源の判断基準

- 案件固有の優先順位が定義されている場合だけ適用する
- 全案件共通の固定優先順位を作らない
- 矛盾時は高優先度情報源を採用しつつ、低優先度側の証拠も保持する
- 優先順位で解決できない重大矛盾は`question-analysis`（不明点・矛盾分析）へ送る
- 実装が正本でない場合、上位仕様と異なる実装へ仕様を合わせない
- 既存テストの期待結果を、そのテストに書かれているという理由だけで`SPEC`にしない

## 手順

### 1. 対象範囲を確立する

必要に応じて対象機能、変更、画面、ユーザー / ロール、業務フロー、明示的対象外を整理します。実質的な依存がない周辺機能へ広げません。

### 2. 使用した情報源を記録する

後から追跡できる粒度で文書名、ページ、セクション、ファイル、コンポーネント等を記録します。未確認資料を確認済み扱いしません。

### 3. 仕様項目を抽出する

対象範囲に関係する独立したルール・挙動を抽出します。

例:

- UI表示 / 操作
- 機能挙動
- バリデーション / エラー
- 権限 / ロール
- 業務ルール
- 状態 / 遷移
- 処理フロー
- 通知
- データ挙動
- 明示的API / DB / 永続化 / 整合性要件
- 制約 / 境界
- 明示的な非機能要件

文章1文ごとに機械的に分割せず、意味が異なるルールを件数削減目的で統合しません。

### 4. 正式用語を維持する

画面、操作部品、ラベル、項目、状態、ロール、業務概念は権威ある情報源の正式名称を使います。正式名称があるのに独自名称を作りません。

### 5. 業務ルールを整理する

必要に応じて権限、公開 / 表示ルール、上限、条件分岐、優先順位、排他条件、設定依存を構造化します。ここではテストマトリクスへ展開しません。

### 6. 状態・遷移を整理する

意味のある状態が存在する場合だけ、状態、開始条件、イベント / 操作、遷移先、状態固有制約を整理します。類似サービスから状態を創作しません。

### 7. フローを整理する

順序に意味がある場合だけ、開始条件、主経路、明示的分岐、エラー、キャンセル / 再試行 / 完了挙動、結果状態を整理します。仕様フローとテスト手順は分離します。

### 8. 制約・境界を抽出する

明示されている最小 / 最大、形式、件数 / サイズ、対応形式、日時、権限、環境、性能、永続化 / 整合性等を記録します。未定義の数値境界を創作しません。

### 9. `SPEC`以外を保持する

重要な`DECISION` / `INFERENCE` / `UNKNOWN` / 矛盾について、根拠、影響範囲、下流影響を保持します。

### 10. 内部整合性を確認する

例:

- 同一ロールに同一操作の許可・禁止が併存
- 上限値の矛盾
- 状態 / 遷移の不整合
- 用語の食い違い
- フロー結果と業務ルールの矛盾
- 確定事項が構造化仕様へ未反映
- UI仕様と明示的な内部要件が矛盾

矛盾を都合のよい解釈で消しません。

## 意味上の出力契約

必要に応じて次を表現できる仕様分析を作ります。

- 分析範囲と制約
- 実際に使用した情報源
- 安定IDを持つ仕様項目
- `SPEC` / `DECISION` / `INFERENCE` / `UNKNOWN`
- 業務ルール
- 状態 / 遷移
- 処理 / 業務フロー
- 明示的制約 / 境界
- 重大な矛盾 / 不明点
- 後続Skillへの補足

重要仕様は情報源へ追跡できなければなりません。

## 停止条件

次の場合、影響範囲をBlockedとします。

- 対象挙動について利用可能な情報源がない
- 対象範囲を意味のある程度に特定できない
- 必要資料へアクセスできず信頼できる分析が成立しない
- 権威ある情報源の未解決矛盾により有効な解釈ができない

軽微な欠落、非Blockerの`UNKNOWN`、明示された推論、一部範囲だけの矛盾では全体停止しません。

## 品質ゲート

### 情報源への忠実性

- `SPEC`が権威ある根拠に支えられている
- `DECISION`を元仕様と区別している
- `INFERENCE`を事実扱いしていない
- `UNKNOWN`を一般論で埋めていない
- 実装差分に合わせて仕様を書き換えていない
- 既存テストを仕様の権威にしていない

### 追跡性

- 重要仕様項目に安定IDがある
- 業務ルール、状態、フロー、制約が情報源へ追跡できる
- 矛盾の根拠を後から確認できる

### 範囲・工程境界

- 関係のない周辺機能を追加していない
- 明示的対象外を守っている
- テスト要求・観点・ケース設計を行っていない

## 次の担当Skill

- 不明点・矛盾の分類が必要 → `question-analysis`
- テスト重点・Product Risk分析が必要 → `test-analysis`

実際の遷移は`qa-workflow`のルーティングに従います。
