# ローレベルテストケース設計 詳細判断基準

## 目的

Test Condition / Coverage Itemを、**第三者がケース単体を読んで迷わず実施し、PASS / FAILを判断できるローレベルTest Case**へ変換します。

## 入力

必須:

- 対象Test Condition
- 必要なCoverage Item、またはCoverage Item内包済みの具体Test Condition
- 期待挙動を判断できる上流根拠

利用可能なら次も使います。

- Test Requirement
- Specification
- Product Risk / 優先度
- 案件コンテキスト
- テストレベル / 観測方法
- 正式用語
- 既知のデータ / 状態 / 環境制約

## ローレベル完了基準

各重要ケースについて、ケース単体から次を一意に判断できなければなりません。

1. 誰が / どの状態で開始するか
2. 何を準備するか
3. 何を操作するか
4. 何を入力 / 選択するか
5. 何が起きればPASSか

別ケース、口頭説明、暗黙知を読まないと重要部分を判断できる場合は未完成です。

## Oracle Authority

完成済みTest Caseの期待結果は原則として次へ追跡します。

1. `SPEC`
2. `DECISION`
3. `承認済み ASM`

次は単独でOracle Authorityにしません。

- Product Risk
- 実装
- 既存Test Case
- 一般的UI慣習
- 未承認`INFERENCE`
- テスターの常識

期待結果を決められない場合は`question-analysis`（不明点・矛盾分析）へ戻します。

## テストデータ / 状態 / 環境

必要なユーザー、データ、状態、環境は原則として準備可能として設計します。

ただし、設計時点ですでに準備不能と分かる条件はケース化せず、制約 / 残存 / 対象外として扱います。

実施時に初めて準備不能と分かった場合は、その時点で実施対象から除外または見直します。

## 手順

### 1. ケース目的を1つにする

タイトル / 目的から、何を確認するケースか一意に分かるようにします。

複数Coverage Itemを1ケースでまとめてもよいのは、次が実質的に同じ場合です。

- 前提条件
- 操作経路
- テストデータ区分
- Oracle

無関係な目的を1ケースへ詰めません。

### 2. 前提条件を明示する

必要なロール、初期状態、設定、既存データ、画面到達条件を記載します。

別ケース実行後の状態を暗黙に前提にしません。

### 3. テストデータを具体化する

Coverage Itemを実行できる具体データへ変換します。

例:

- 境界値 → 実際に入力する値
- 同値クラス → 代表値
- ロール → 対象ユーザー
- 状態 → 開始時の具体状態
- デシジョンルール → 各条件の具体値

データの準備方法を詳細な運用手順として設計する必要はありません。テスターが何を使うか判断できればよいです。

### 4. 実施手順を書く

操作主体、画面 / 対象、操作、入力 / 選択を明確にします。

「設定する」「確認する」「適切に操作する」など、対象や値が分からない曖昧表現を避けます。

### 5. 期待結果を書く

観測可能な結果を具体的に記載します。

避ける表現:

- 正常に表示される
- 正しく処理される
- 問題ないこと
- 適切なメッセージが出る

仕様に名称・値・状態・メッセージがある場合は正式な内容を使います。

UI中心のシステムテストでは、原則としてUIから観測可能な結果を使います。案件で許可されていないDB / API / ログ観測を勝手にOracleへ追加しません。

### 6. 多段手順と期待結果を対応付ける

中間結果が次操作の成立条件または合否判定に重要な場合は、手順番号と期待結果番号を対応させます。

例:

- 手順1 → 期待結果1
- 手順2 → 期待結果2

単なる画面遷移など、合否へ意味を持たない中間状態まで過剰に分解しません。

### 7. 事後状態 / 後処理を必要時だけ記載する

次の場合だけ明示します。

- ケース実行後の状態が別ケースの独立性へ影響する
- 再実行のための復旧が必要
- 作成データ / 設定変更が残る

### 8. 正式用語を確認する

仕様・UIに正式名称がある場合はそれを使います。AI独自のラベルを作りません。

### 9. 重複を統合する

前提、操作、データ意味、Oracleが同一で、違いが説明列だけの場合は統合を検討します。

統合しても関連Test Condition / Coverage Item IDを失わないようにします。

## ケース分離の判断

分離する主な条件:

- 開始状態が異なる
- 操作経路が異なる
- Oracleが異なる
- 失敗時の意味が異なる
- 独立性のため別実行が必要
- データ区分により挙動が変わる

観点名が違うだけでは分離理由になりません。

## 意味上の出力契約

各Test Caseに必要な情報:

- 安定ID（例: `TC-001`）
- タイトル / 目的
- 関連Test Condition
- 関連Coverage Item（明示時）
- 関連Test Requirement
- 優先度
- 前提条件
- テストデータ
- 実施手順
- 期待結果
- 期待結果の根拠
- 必要時の事後状態 / 後処理

## 停止条件

次の場合、影響ケースをBlockedとします。

- PASS条件を決めるOracle Authorityがない
- 前提状態や操作対象が重大に不明で、具体手順を書けない
- 相反する期待挙動が未解決
- 必要Coverage Itemの意味が曖昧
- 観測手段がなくPASS / FAILを判断できない

データ準備方法が未確定という理由だけでは停止しません。

## 品質ゲート

### 独立性

- 別ケースの実行結果へ暗黙依存していない
- ケース単体で開始状態を作れる前提になっている

### 具体性

各重要ケースについて次が明確か確認します。

- 開始者 / 開始状態
- 準備対象
- 操作
- 入力 / 選択
- 合格条件

### Oracle

- 重要期待結果に`SPEC` / `DECISION` / `承認済み ASM`の根拠がある
- Product Risk / 実装 / 既存テストから未定義Oracleを創作していない
- 観測できない結果を期待結果にしていない

### 追跡性

- 必要Test Condition / Coverage Itemがケースへ落ちている
- 統合後も関連IDが失われていない

### 表現

- 正式用語を使っている
- 曖昧な「正常」「正しい」「適切」を具体結果の代わりに使っていない
- 多段手順の重要中間結果が対応付いている

## 次の担当Skill

- Oracle / 期待挙動不明 → `question-analysis`
- Coverage Item不足 / 条件不備 → `test-condition-design`
- Coverage確認 → `coverage-analysis`
