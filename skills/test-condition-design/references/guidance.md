# テスト観点・条件設計 基本ガイダンス

## 目的

テスト要求を、**どの条件・観点で検証するか**へ展開し、カバレッジ基準と具体的なカバレッジ項目を定義します。実行手順を含むテストケースへ先回りしません。

技法固有の規則は`coverage-techniques.md`を正本とします。

## 入力

必須: 何を検証するかが明確なテスト要求、または同等の成果物。

利用可能なら現在有効な仕様根拠、プロダクトリスク、案件コンテキスト、状態モデル / 業務ルール、不明点・矛盾分析も使います。

## 現在有効な仕様根拠

期待挙動はテスト要求が参照する解決済みの現在有効な仕様根拠へ追跡します。

プロダクトリスク、エラー推測、テスト仮説、実装情報は候補生成に使えますが、未定義の期待結果を確定する仕様根拠にはしません。

## テスト要求の閉鎖

現在レベルの各テスト要求は次のいずれかへ位置づけます。

- 1つ以上のテスト条件へ展開
- 別テストレベル
- 残存リスク
- 対象外
- ブロック中

プロダクトリスクが低いことだけを理由にテスト要求を無言で削除しません。

## カバレッジ設計の基本順序

複数候補を持つ技法・仕様構造では次の順で判断します。

1. 仕様 / テスト要求から候補母集団を識別する
2. カバレッジ基準を定義する
3. カバレッジ基準を満たす具体的なカバレッジ項目を採用する
4. 採用しない候補は扱いと理由を残す

候補母集団を識別せず、最初から「重要なものだけ」を恣意的に選びません。

## カバレッジ候補の扱い

### `対象外`

ユーザー、Project Context、現在有効な仕様根拠の対象範囲から外れる根拠がある場合だけ使用します。低プロダクトリスクだけを理由に使用しません。

### `別テストレベル`

現在レベルでは適切に検証できず、適切な別レベルを説明できる場合に使用します。

### `残存リスク`

対象内だが意図的に未カバーとする場合に使用します。未カバー内容、理由、関連プロダクトリスクを明示します。

### `成立不能`

仕様、状態モデル、データ制約、業務ルール等から、その候補が成立しない根拠を示せる場合だけ使用します。

### `重複`

別のテスト条件 / カバレッジ項目で同じ検証責務を保証でき、具体的なカバー先を示せる場合だけ使用します。

### `ブロック中`

期待挙動、条件、仕様根拠等の不足により、候補の採否自体を妥当に判断できない場合に使用します。

## カバレッジ項目

カバレッジ基準から導かれる、具体的にカバーすべき要素です。

### 独立表示が必要な場合

次のいずれかに該当する場合はカバレッジ項目を明示します。

- 1つのテスト条件を満たすために複数の具体値、パーティション、ルール、状態、遷移、経路、組合せが必要
- 技法の充足状況を項目単位で確認しないと十分性を判断できない
- テスト条件 → テストケースだけでは何を確認済みか一意に判断できない

### テスト条件へ内包してよい場合

次をすべて満たす場合だけ独立カバレッジ項目IDを省略できます。

- テスト条件自体が1つの具体条件を一意に表す
- 必要カバレッジ要素が1つだけ
- テスト条件 → テストケースの対応だけで十分性を判断できる

「境界」「状態」「権限」等の抽象ラベルだけでは内包済みとみなしません。

## 技法選択

問題構造に合う技法だけを選びます。技法名を付けること自体を目的にしません。

技法を採用した後、その技法固有の適用条件・既定カバレッジ・カバレッジ項目規則を確認する必要がある場合は`coverage-techniques.md`を読みます。

## プロダクトリスクによる深度調整

`test-analysis`で決めたプロダクトリスク / 設計深度を入力として使用し、このSkillでリスクマトリクスを再採点しません。

- 高: 選択技法のカバレッジ基準を原則満たし、仕様 / リスクに関連する追加条件を積極的に検討
- 中: 基本カバレッジを満たし、追加条件は根拠があるものに限定
- 低: 主挙動を代表するカバレッジを確保し、一般エッジケースを機械追加しない

低リスクでカバレッジを削減する場合も対象内候補を無言で消さず、妥当な扱いへ位置づけます。

## 優先度継承

テスト条件 / カバレッジ項目は関連テスト要求の最も高い優先度を既定で引き継ぎます。優先度を下げる場合は理由を明示します。

## 手順

1. 対象テスト要求、テストレベル、プロダクトリスク、対象外、未解決事項を確認する
2. テスト条件へ展開しないテスト要求を扱いへ位置づける
3. 挙動を変える条件軸を特定する
4. 問題構造に合う技法だけを選ぶ
5. 必要なら`coverage-techniques.md`の採用技法の規則を確認する
6. 候補母集団を識別する
7. カバレッジ基準を定義する
8. カバレッジ項目を採用し、採用しない候補を扱いへ位置づける
9. 組合せ爆発・重複を抑制する
10. テスト要求 / 現在有効な仕様根拠への追跡性を確認する

カバレッジ項目ID例: `TCN-001-CI01`。

## 出力

各テスト条件について次を表現します。

- 安定ID
- 観点 / 条件
- 関連テスト要求 / 現在有効な仕様根拠
- 関連プロダクトリスク / 優先度
- 適用技法
- カバレッジ基準
- カバレッジ項目（必要時）

採用しないテスト要求 / カバレッジ候補には扱いと理由が必要です。`重複`の場合はカバー先も必要です。技法固有の追加証拠は`coverage-techniques.md`の規則に従います。

## 停止条件

次の場合、影響範囲をブロック中とします。

- テスト要求の意味が曖昧で条件へ展開できない
- 現在有効な仕様根拠を解決できない
- 期待挙動を未承認推論で補完しないと条件を作れない
- カバレッジ基準または期待挙動の確定に必要な状態 / 権限 / 境界定義の矛盾が未解決
- カバレッジ基準を定義するために不可欠な仕様がない

低リスクの追加観点が不明、任意のエラー推測仮説が不足、全組合せが巨大という理由だけでは停止しません。

## 品質ゲート

- 各テスト要求がテスト条件または扱いへ閉じている
- 複数候補を持つ構造で候補母集団を識別している
- 採用しない候補に妥当な扱いと理由がある
- `対象外`を低プロダクトリスクだけの理由で使用していない
- `成立不能`に仕様 / モデル / 制約根拠がある
- `重複`に具体的カバー先がある
- 適用技法にカバレッジ基準がある
- カバレッジ項目の明示 / 内包判断が基準に従っている
- 採用技法がある場合、`coverage-techniques.md`の該当規則を満たしている
- プロダクトリスクから未定義の期待結果を創作していない
- テストケースへ先回りしていない
- 優先度を理由なく下げていない

## 次の担当Skill

- 不明点・期待挙動不明 → `question-analysis`
- 詳細テストケース設計 → `test-case-design`

## 出力前自己検証

最終出力前に、実際に利用した入力が本Skillの入力契約を満たし、入力・仕様根拠・判断状態に停止条件へ該当する未解決状態がないか確認します。あわせて、生成した成果物へ本Skillの出力契約と既存の品質ゲートを再適用します。品質基準は本ガイダンスと、採用技法について必要な場合に参照する`coverage-techniques.md`の既存定義を正本とし、自己検証専用のrubricやチェックリストを別定義しません。

1. 実際に利用した入力が入力契約を満たし、停止条件へ該当する未解決状態がないか確認する
2. 生成した成果物が出力契約と既存の品質ゲートを満たしているか確認する
3. 明白かつ局所的で、新しい領域判断を必要としない契約違反だけを最大1回修正する
4. 修正後は修正箇所を含めて最終確認する。解消に新しい仕様根拠、上流判断、他Skillの領域固有ロジックが必要な場合は自力で補完せず、既存の停止条件・ブロック中・ルーティングに従う
5. 最終確認後も本Skill自身の契約違反が残り、既存の停止条件・ブロック中・ルーティングに該当しない場合は、2回目の自動修正を行わず、その成果物を契約適合済み・完成済みとして扱わない。現在残っている契約上の制約だけを明示する

自己検証を理由にカバレッジ戦略を根本から再設計したり、未定義の期待結果や判定根拠を追加したりしません。既存の`ブロック中`定義を未解消ローカル違反へ広げません。自己検証の実行経緯、修正回数、修正前状態、PASS / FAIL等の評価ログは通常成果物へ出力せず、現在有効な状態と未解消の契約上の制約だけを返します。
