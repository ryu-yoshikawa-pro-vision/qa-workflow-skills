# Project Contextの発見・初期化・更新

初回確認では、案件固有の許可された探索範囲、既存候補ref、read権限、案件識別子、保存先の正本を確認します。全候補の列挙が終わって初めて「不存在確認済み」とします。アクセス不能・重複・案件不一致は候補を失わず再開条件を示します。

初回作成には既存16節templateを使用し、情報源の優先順位、正式用語、テスト範囲、環境条件、DEC/ASM、既存QA成果物への参照をそのまま残します。未確定欄を推測せず、必要な項目だけ収集します。案件名が不明な場合は作成せずに確認します。

更新は元文書の参照とexpected revision、変更項目、根拠source ref/revision、理由を記録します。stable field更新だけでその他の章・表・DEC/ASMを再生成しません。DEC/ASMを編集する必要がある場合は既存project_context_ids.pyのmaterializeを正本ownerの場合だけ使用します。Section 14の正本参照・配置方針の更新は人間合意と対象schemaの整合確認の後に行います。

既存配置の維持を第一候補にし、編集対象の正式owner、場所、編集可能範囲、生成専用ファイル、共通条件の配置、機能別参照入口を調べます。保存場所変更、正本owner移管、生成一覧の手編集は既存合意の対象変更として検出します。承認refがあるだけでは真正性を保証せず、外部認証と権限・scope・revision・有効期間を保存直前に照合します。

prepare-create / prepare-updateの戻り値はdraftです。保存provider固有の原子的条件付き操作とreadbackが確認されるまでcurrentと報告しません。保存・外部認可がblockされても、案件資料の読取・機能候補の分析を継続できます。

Section 12/13がDEC/ASMの正本である案件では、`prepare-ids`で既存のID helperにID採番を委譲します。元の表の前後にある自由記述を残し、表以外の節を更新しません。元IDの消失や正本owner不一致は拒否します。新たに作ったdraftは保存済みの正本ではありません。

既存成果物の配置方針を新規に記録するには`prepare-placement`でDECのID履歴とSection 14の正本参照を同じ更新候補に含めます。正本の現在revision、合意の対象scope・editable_scope・feature_index_ref、承認元参照が一致しない場合は別の方針として扱い、無承認移動をしません。旧Section 12/13の行はexisting_decisions／existing_assumptionsで維持し、未確認の既存IDを削除せずにblockedとします。

Section 1〜11・15の既存の説明や環境資料を根拠付きで改版するときは`prepare-sections`を使います。Section 12/13は`prepare-ids`、14は`prepare-placement`、16は`prepare-update`を使い、互いの正本領域を無断で上書きしません。初回案件では`prepare-create`の`section_updates`に確認済み資料のみ指定できます。

Section 12に既存の有効配置DECがあれば、`prepare-placement`は`existing_policy.decision_id`とSection 14の参照を照合します。変更は旧DECを置換済みにしたうえで新DECを追加し、置換先IDを記録します。旧DECを正本に残したまま新方針を同時に有効化しません。Git管理の既存Markdownは同一Git branch／pathを正本として`GitArtifactStore`で条件付き保存でき、SQLite正本への無断移行はしません。
