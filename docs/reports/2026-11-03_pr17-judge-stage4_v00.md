# PR #17 Judge審査・診断評価（Stage 4）

## 結論

Judgeを既存Codexセッションの別サブエージェント呼出しで実行し、その応答を既存`normalize_judge_response()`へ取り込むhandoff経路を追加した。固定QTS Judge fixture 11件すべてについて、正解rating・承認状態をJudge promptへ渡さず、同一promptで2回ずつ診断呼出しを行った。応答JSONは既存normalizerで検査し、呼出し別に保存した。

これはJudge経路の**開発用診断実行**である。fixture承認は0件で、使用したStage 2 baselineは現Evaluator revisionと異なり、必須runtime evidenceや独立runtime replayが不足している。そのためJudgeの正確性、fixtureの期待rating、QTS成果物の合否はいずれも正式検証できていない。反復で確認した判定差は多数決で解消していない。Stage 4は未受入であり、Stage 5の`improve.py`ライブ改善には進んでいない。

## 実装

commit `2a79b44c312d1f6c076a8164f9d6e3da72dbaca4`で次を変更した。

- `judge_validation.py`に、別ホスト呼出し用のprompt/request準備と応答取込を追加した。Pythonはサブエージェントを起動しない。request・prompt hash・attempt identityを照合し、重複取込、不正JSON、秘密形状データを拒否して既存normalizerへ渡す。結果は`diagnostic_response_valid`で保存し、正解との一致や実効modelの検証を主張しない。
- 初回Judgeに過去のJudge PASSを要求する循環条件を外し、`judge_status=not_run`の`needs_review`を候補として扱えるようにした。他の出力完全性、target integrity、runtime、trace、artifact契約等の適格条件は維持した。既存Stage 2 baselineはこれらの条件を満たさず、不適格のまま。
- `major-violation-001`のmutationが既にskippedのrouteに対して実質無変更になる場合、またはlinked test artifactがない場合にfixture作成を拒否する。
- READMEとJudge Planにホスト管理handoff、baseline条件、未検証情報の扱いを記録し、関連回帰テストを追加した。
