# QAワークフロー共通運用契約

利用者とAgentの責務、進行、質問、承認、保存、再開、完了を定める。[共通設計原則](qa-skill-design-principles.md)、[成果物マトリクス](qa-workflow-artifact-matrix.md)、[利用者マニュアル](qa-workflow-user-guide.md)を参照する。工程固有の入出力・実行条件は担当SKILL.mdとreference、全体routingと実行条件は[qa-workflow](../../skills/qa-workflow/SKILL.md)および[詳細契約](../../skills/qa-workflow/references/guidance.md)を正本とする。

本書は利用時の共通契約を定める。設計判断は共通設計原則、実行可能な操作・必須条件は担当契約に従う。実操作では担当Skill・Runtimeの必須条件と、適用される[保存・承認契約](../plans/2026-11-07_170134_qa-full-process-implementation_02_storage-approval-reporting.md)、[配置契約](../plans/2026-11-07_122247_development-qa-traceability.md)、[人間編集契約](../plans/2026-11-07_170134_qa-full-process-implementation_08_human-artifact-editing.md)を満たす。必要な能力・権限・検証が不足する操作は停止し、独立した分析は継続する。原則の記載だけで自動化・実行成功・制約解除を保証しない。

## 責務分担

<!-- dprint-ignore -->
| 主体 | 担当 |
| --- | --- |
| 利用者・権限者 | 目的・対象・成果物の指定、委ねていない仕様決定・必要な計画承認・操作許可・リスク受容 |
| 呼出し側 | 必要な入力、保存先、実行環境、権限、外部起動・結果受渡し |
| qa-workflow | Skill選択、順序、依存、再利用、停止・再開、変更影響、要求の完了 |
| 担当Skill | 既存根拠と委ねられた範囲での専門QA判断、必要な成果物・根拠・検証・引継ぎ、自己解決できない必要事項の質問 |
| Runtime・Helper | 採番、技法の決定論的処理、形式・参照検証、ファイル処理 |
| レビュー担当 | 独立反証、指摘、修正先の提示 |

採番・資料確認・形式検証・質問JSONとHTMLおよび回答の対応確認・再利用判断はAgentが行う。担当Skillは他ownerの正本を無断変更しない。対象repo・branch・commit等はQA情報源として利用できる。案件管理・成果物のGit管理・保存技術の選択に関する設計境界は共通設計原則Q06・Q07に従う。利用時は必要なProject Context・配置・編集条件を担当契約に従って確認する。

## 進行・質問・承認

進行モードは[qa-workflowの契約](../../skills/qa-workflow/references/guidance.md)に従い、利用者の明示指示、案件コンテキスト、continuousの順に適用する。gatedでは現在のSkillの成果物提示後に進行指示を待つ。工程進行、仕様判断、保存、実操作認可、リリース判断は別に扱う。

<!-- dprint-ignore -->
| 利用者の介入 | Agentの対応 |
| --- | --- |
| 依頼開始・変更 | 目的、対象、要求成果物、必要な情報源・保存先・許可範囲の不足だけ確認 |
| 仕様・仮定の未解決事項 | 根拠、影響、質問、未回答時の扱い、再開先を提示 |
| QA要求・方式・計画の確定 | 委ねられた範囲は担当Skillが判断し、未委任の決定や正式承認が必要な場合に限り判断を得る |
| 破壊的変更・削除・必要な外部操作 | 対象、差分、操作権限、上限、cleanup等の必要条件を確認 |
| 報告・改善採否・リリース | 結果、未実行、残存リスク、終了基準を提示し必要な判断を得る |

QAの専門判断は担当Skillが行い、依頼者にしか決められない事項を確認する。正式な承認は担当契約が要求する承認主体・権限・決定事実を確認する。対話上の回答だけで認証済み承認を成立させない。判断の対象・内容・必要な適用範囲を記録し、保留・推定・推奨案を承認としない。有効な既存回答・承認を再利用し、承認の意味・対象・権限に影響する変更時だけ再確認する。まとめて質問する場合も独立した回答単位を保つ。

### 質問と回答の処理

1. 担当Skillは情報源優先順位、既存DEC/ASM、質問・回答、関連するQA知識を必要範囲で参照し、有効な根拠の組合せと適用範囲から自己解決を優先する。判断に必要な根拠が足りない場合は追加調査を行い、利用者の回答が必要な論点だけ質問する。確定済み期待仕様との実装差異を仕様質問へ戻さない。
2. [question-analysis](../../skills/question-analysis/references/guidance.md)で安定Q ID、根拠、影響、停止範囲、正規化先、再開先を明確にする。ブロッカーは影響scopeだけ停止し、要確認・提案は明示して継続する。仮定は承認済み期待結果と区別する。
3. 単発は対話/Markdown、必要な複数質問は[agent-answer-form](../../skills/agent-answer-form/SKILL.md)を利用する。Agentが質問JSON・HTMLの整合を確認し、フォームの元定義・Q IDと回答を対応付け、定義変更時は回答照合に必要な旧HTML・元質問・回答履歴を保全する。意味が変わった質問へ過去回答を自動適用しない。秘密情報を含めない。
4. 継続作業で必要な成果物・未解決質問・再開情報を許可範囲で保存する。保存不能でも質問と安全な再開情報は提示し、未保存または保存結果不明の範囲と、別sessionでの復元を保証できないことを明示する。
5. 回答を元質問・根拠と照合する。期待挙動の仕様根拠に関する回答は担当契約に従い、権威ある仕様はSPEC、正式決定はDEC、明示承認された暫定合意は承認済みASMへ正規化する。ASMで有効なSPEC/DECISIONを上書きしない。実行URL、実行データ、保存先、操作許可など仕様根拠ではない回答は、仕様の正規化と区別して該当する担当契約の実行条件・成果物に反映する。現行question-analysisの正規化・再開先の契約を明確化する改善は[OPS-01/18](../reports/2026-11-25_qa-workflow-operating-improvements.md)で扱う。担当ownerが必要な正式反映を行い、質問一覧は未解決のみ、使用済みIDは必要な履歴に残して別論点へ流用しない。意味が変わる最も早い工程から依存scopeだけ再検証する。

## 成果物の保存・更新

成果物作成・継続利用では必要な保存を依頼に含め、担当契約に従って保存対象・タイミング・保存先・承認要否を判断する。単発相談・読取・レビュー・調査は原則対話回答のみ。明示の非保存指示を尊重し、必要な保存条件が不足する場合は確認する。正式保存に必要な承認・権限・保存能力・検証を省略せず、満たせない条件と確認できた保存状態を報告する。

<!-- dprint-ignore -->
| 保存対象 | タイミング・扱い |
| --- | --- |
| 正式成果物・継続作業 | 処理完了、質問提示前、回答反映後、中断、引継ぎ前に必要分を保全。担当契約で許可される保存のみ行い、承認済み意味と未承認候補を区別 |
| 保護証跡 | 実行前条件、実行後・異常停止時の必要な結果・Run/Attempt・観測・cleanup。保存許可、機密性、アクセス、保持条件に従う |
| テストコード | 変更許可された対象repoの既存構成。実装・検証結果と必要な参照を保持 |

既存正本と指定ディレクトリを優先する。アクセス不能・重複・列挙不全を不存在とみなさず無断で別正本を作らない。相対配置・形式は担当契約を参照し、機密raw証跡・一時作業物は安全な許可領域に限定する。成果物や秘密情報をSkill assetsへ無断保存・共有しない。一時物のcleanupで必要な履歴・再開情報を失わない。

必要な更新保証は共通設計原則に従い、該当経路の保存・承認・競合・履歴契約を適用する。内容の確定・承認状態と保存状態を区別する。draftでも保存済みの場合がある。必要な保存確認を満たせば保存済み、今回の書込みが行われなかったと確認できれば未保存、結果を確定できなければ保存結果不明とする。書込み後の読戻し失敗等では未保存・旧版のまま・保存成功と断定せず、必要な実保存結果を照合する。部分保存時は確認済み範囲と未確定範囲を分離し、必要な依存整合が成立するまで下流の採用を保留する。無条件上書き、無断rollback、有害な副作用の盲目的再試行を行わない。

人間による編集は許可範囲と担当ownerの編集契約に従う。正式な意味変更・生成領域・機械管理IDの扱いを通常文書へ一律拡大しない。UI target packageの編集制約は[専用契約](../../skills/spec-analysis/references/ui-test-target-analysis.md)を参照する。

## 中断・再開・引継ぎ

開始・完了時に元依頼、要求成果物、必須scope、除外候補を照合する。再利用は必要な入力母集団・依存関係・情報源revision・利用したコンテキスト・成果物の有効性を確認して判断する。入力revisionの一致だけで入力列挙の完全性を保証しない。

保存済み成果物と必要なstateから再開し、変更の影響scopeだけ再検証する。引継ぎは担当owner、scope、実成果物ref、根拠、必要なrevision・依存・検証結果・承認、未解決理由・再開先を必要範囲で渡す。既存成果物から取得可能な情報を重複保存しない。

副作用操作は必要な権限、実開始、実保存、cleanup、共有資源の分離・予約を担当契約に従って確認する。結果不明時は元操作を照合してから再開し、同じ副作用を盲目的に再実行しない。現行は共有予約・分離が確認できるまで同一案件の並列workflowを避ける。必要な隔離・予約が確認できない共有環境では該当操作を開始しない。実際に競合する成果物・環境・共有資源・操作に制約を限定する改善は[OPS-06](../reports/2026-11-25_qa-workflow-operating-improvements.md#ops-06-必要な副作用共有資源の実行安全-p0)で扱い、改修・必要な受入までは現行制約を維持する。Skillの指示はsandbox・hook・OS権限の代替ではない。適用される[運用制約](../implementation/pr22/merge-decision-2026-11-14.md)を守る。

## 完了判定

<!-- dprint-ignore -->
| 判定軸 | 意味 |
| --- | --- |
| 成果物完成 | 担当Skillの意味・形式契約と必要な検証を満たす |
| 保存 | 要求された保存が成功し、必要な確認を満たす |
| 内容承認・採用可否 | 必要な明示判断・有効性・根拠を確認する |
| 実行完了 | 実開始、予定母集団、観測、収集、必要cleanupを確認する |
| テスト合否 | PASS/FAIL/未実行/判定不能等を観測結果で判定する |
| 報告・終了基準 | 取得完全性、計画母集団、指標、終了基準を別々に判定する |
| Workflow完了 | 元依頼と必須scope、必要な成果物・保存・実行・検証・報告を充足する |
| リリース承認 | 権限者が残存リスクを判断する |

FAILは必要工程の完了と両立し得る。必要な未実行・判定不能・未検証・cleanup不明・必要な保存の未確認が残るscopeは完了としない。母集団不明時は全体率・終了判定をundeterminedとする。実行経路が要求するRuntime gate・owner検証を満たし、自己申告や単一の成功フラグのみで完了・承認・実行成功を証明しない。現行Runtimeは要求外のscopeも検証対象とする。必須工程および必須成果物が依存する工程と、独立した補助工程の完了判定を分離する改善は[OPS-05](../reports/2026-11-25_qa-workflow-operating-improvements.md#ops-05-qa品質完了検証契約の適正化-p0)で扱う。改修前にRuntimeの必須条件を省略しない。必要な検証を満たさない除外によって完了分母を縮小しない。未完了の理由と再開先を明示する。
