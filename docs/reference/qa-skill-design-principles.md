# QA Skill設計・開発の共通原則

2026-11-25 利用者合意。リポジトリ全体のQA Skill、Helper、Workflow、実装Plan、評価・レビューに適用する前提。新規・改修に優先適用し、未改修の既存契約との差異は対象Planで解消する。文書の変更だけで既存実装・受入済みとしない。開発用Git保護・実行権限を緩める指示ではない。

## 思考原則

| ID | 原則 | 判断基準 |
| --- | --- | --- |
| PRN-01 | KISS | 目的を満たす最も単純な構造・手順を選ぶ。 |
| PRN-02 | YAGNI | 実要求・確認済み問題・具体的リスクがない機能、設定、拡張点、抽象化を作らない。 |
| PRN-03 | SRP | 各Skillは専門責務に集中する。必要な外部責務は境界で受け取り、不要な責務は移管せず削除する。 |
| PRN-04 | DRY | 既存正本・標準機能・Helperを優先し、実際の重複だけを必要範囲で共通化する。 |
| PRN-05 | Fail-safe | 防御は現実のリスクに比例させる。保証不能な操作のみ停止し、独立分析は継続する。 |
| PRN-06 | 人間中心 | 成果物の発見・閲覧・編集・理解、利用者の判断負担を重視する。AIや保存技術の都合だけで決めない。 |
| PRN-07 | 決定論的処理 | 機械的に確定できる処理はHelper、意味判断はSkill。AIに不要な判断をさせない。 |
| PRN-08 | 段階的詳細化 | SKILL.mdは短い選択条件・責務・入出力・手順に集中。必要なreferenceだけ読む。 |

## 確定前提（Q01〜Q08）

<!-- dprint-ignore -->
| ID | 項目 | 確定方針 |
| --- | --- | --- |
| Q01 | 単体利用・移植性 | 特定ハーネスを必須にしない。直接指定でも必要な入力・権限があれば実行する。保存先未指定でも分析可能。保存が必要な場合のみ場所を確認する。 |
| Q02 | 保存時点 | 許可範囲の保存対象成果物は処理完了、質問提示前、回答反映後、中断、次工程引継ぎ前に必要分を自動保存。同一時点の重複保存は不要。単発相談・読取は原則保存しない。 |
| Q03 | 保存と承認 | 許可済みroot内の通常保存・非破壊的更新・質問/回答記録は都度承認不要。未承認内容も候補として保存し、未承認と明示。正式決定、仮定採用、承認済み仕様の意味変更、破壊的変更/削除、必要な外部操作は承認する。 |
| Q04 | 正本・形式 | 人間が扱う分析・設計・質問・報告はMarkdown等の読みやすい構造化文書を優先。機械状態・証跡はJSON等、回答/閲覧UIはHTML等を用途別に選択。全成果物のJSON化・二形式化は不要。正本は一つ。 |
| Q05 | 履歴 | 継続文書は安定ファイル名、Q/DEC/ASM等は安定ID、実行はRun/Attempt、必要な過去根拠・正式報告はSnapshot/既存履歴。全更新への版番号・複製は不要。再現に必要な履歴を失わない。Git等はSkill外。 |
| Q06 | qa-workflow | QAのSkill選択、順序、依存、局所停止・再開、引継ぎ、要求されたQAの完了確認。案件・配置・認証・保存技術、汎用状態基盤、共有資源の排他実装を持たない。QA固有の状態判断は維持。 |
| Q07 | project-context | QA目的、対象、用語、業務ルール、決定・仮定、環境・制約の意味管理を残す。案件・Repository・保存配置・Provider管理は除外。残存専門責務から独立Skillの必要性を評価。廃止は未決定。 |
| Q08 | Helper | 採番、同値分割/境界値等の決定論的生成、形式/参照検証、ファイル処理を担当。技法選択、リスク、仮説、仕様矛盾・不足、適用判断はSkill。実際の重複のみ共通化し巨大なHelperを作らない。 |

## 責任範囲と保存境界

- 成果物の分類・発見・保存は指定root配下のディレクトリに統一する。相対配置と意味契約はSkill、root・実行条件・許可範囲は呼出し側（ハーネスまたは直接利用時の明示入力）。案件識別・探索・切替、branch、Provider・認証方式選択はSkillに持たせない。新規の意味identityに案件識別子を必須としない。別rootの同名refは同じ成果物ではない。
- 通常のローカル保存は既存の実行権限・ファイル操作を利用する。専用認証サービス、承認トークン、独自CAS、分散lockを一律要求しない。共有・並行更新や外部操作など実リスクがある場合だけ必要な一意性・条件付き保存・認可を確認する。単一writerの隔離を仮定で保証しない。必要能力が未確認なら該当操作のみ止める。
- 保存済み、内容承認済み、現在採用可能、実行完了、テスト合否は別。候補保存は正式仕様変更ではない。保存失敗・結果不明を報告し、必要なreadback・依存・履歴を確認する。対話質問は保存不能でも提示可。永続的副作用は必要条件を満たす場合だけ実行する。
- 破壊的変更・無断移行・権限外操作・機密漏えい・必要な履歴消失・誤完了・未承認の正式仕様採用は許容しない。開発用Git保護は適用範囲が別であり、成果物保存の簡素化を理由に回避しない。

## Plan・実装・レビューの判断

1. 目的・ユーザー要求・専門責務を確認する。
2. 不要な処理を先に削除し、残る責務をSkill・既存Helper・呼出し側へ分離する。
3. 既存契約・標準機能で成立するかを先に確認する。追加機能、抽象化、設定、防御、再確認、永続化は具体的な必要性と効果がある場合だけ採用する。
4. 防御は現実の失敗モード・影響・権限・共有条件に比例させる。想定可能という理由だけで全Skill共通の複雑な機構を作らない。実リスクの未検証を安全の証明にもしない。
5. 最小構成でQA品質、必要な履歴・再現性・安全性を検証する。専門外判断・読込・質問・設定・重複処理の削減を評価する。対象外、未達、判断理由を必要範囲で記録する。

この判断は既存Plan・レビュー・評価に統合し、新しいチェックリストや承認ゲートを増やさない。新規Skill、管理基盤、保存層、認証、汎用抽象化、追加防御を作る場合は既存手段の具体的不足を示す。固定削減目標・新規評価基盤は必要性と比較可能なbaselineが確認されるまで要求しない。
