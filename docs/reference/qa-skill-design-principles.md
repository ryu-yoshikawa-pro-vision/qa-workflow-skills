# QA Skill設計・開発の共通原則

リポジトリ全体のコード、QA Skill、Helper、Workflow、文書、設定、テスト、Plan、評価・レビューに適用する設計・開発原則と、QA活動の基本原則。本書は設計・改修の判断基準である。利用時の実行条件は[共通運用契約](qa-workflow-operating-contract.md)と担当Skill・Runtimeの現行契約に従う。未改修の条件を本書だけで変更しない。変更は対象Plan・作業権限に従う。

## QA活動の基本原則

ISTQB・IVECを参照し、QAの専門的な判断を次のように整理する。工程ごとの技法・入力・出力・検証条件は担当Skillが定める。

- 品質に関する有用な情報を提供し、利用者・業務へのリスクを低減する。テストの件数、全PASS、成果物の完成だけで品質を保証しない。欠陥が検出されないことと目的を満たすことは別であり、検証範囲・限界・残存リスクを伝える。
- 目的、製品・業務の構造、利用者、状態、環境、制約、変更影響を理解して、必要な活動・テストレベル・タイプ・技法・深度を選ぶ。全数テストや一律の工程実行を前提にせず、欠陥の偏在や過去の実績を重点化に活用する。既に有効な成果物・テストは再利用する。
- 仕様・要求の段階から矛盾、欠落、テスト可能性、利用者への影響を調べ、欠陥予防につなげる。実装・既存テスト・自身の出力を無条件に正しいとせず、期待結果を支える有効な根拠と実際の観測を分ける。必要な独立レビュー・判定方法を選び、観測不能をPASSとしない。
- 担当Skillは依頼されたQA活動に必要な専門判断を自律的に行う。有効な仕様・決定・承認済み仮定の適用範囲と例外を踏まえ、単一または複数の根拠から判断を導出する。必要な情報を自ら調査し、既存根拠で解決できない仕様決定やリスク受容など、利用者・権限者の判断が必要な事項を確認する。
- 過去の合意、対象知識、観察、欠陥、成果物を必要範囲で参照し、関連機能への適用を検討する。正式な根拠と探索・観点生成の手掛かりは区別する。再利用価値がある教訓を既存の担当成果物・Knowledgeに反映する。観察の蓄積・横断的な法則候補の分析が必要な場合はAgentが担当Skillを選択して実施し、明示的な無効指定を尊重する。既存のテストが現在も目的・リスクに対して有効かを必要時に再評価する。
- 活動中に得た教訓を、原因と改善対象に応じて案件の知識・計画・設計、またはSkill・評価資産の改善につなげる。案件の活動評価はtest-evaluation、Skill自体の評価はEVALS.mdを参照する。明示指定がない限りハーネス・モデルの選定、比較、最適化を対象にしない。

参照: [ISTQB CTFL v4.0.1](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/) §1.3〜1.5・§2〜5、[CTAL-TA v4.0](https://istqb.org/certifications/certified-tester-advanced-level-test-analyst/)（テスト分析・設計、欠陥予防）、[CTAL-TM v3.0](https://istqb.org/certifications/certified-tester-advanced-level-test-management-ctal-tm-v3-0/)（リスク・活動改善）、[IVECシラバス](https://www.ivia.or.jp/item43/item38) v3.2.0（テスター §4、デザイナー §4.1〜4.2、アーキテクト §4.1〜4.3）。上記は本リポジトリの判断方針であり、公式資料の原文や認定適合の宣言ではない。

| Q04 | 正本・形式 | 利用者の指定・有効な既存規則を優先し、指定がない場合は用途に合う標準形式を用いる。人間が扱う分析・設計・質問・報告は通常Markdownを優先。機械処理用データはJSON、元の実行証跡は必要な形式、回答/閲覧UIはHTML等を用途別に選択。全成果物のJSON化・二形式化は不要。正本は一つ。Runtime・validatorの都合だけで正本形式や派生物を増やさない。 |
| Q05 | 履歴 | 継続文書は安定ファイル名、Q/DEC/ASM等は安定ID、実行はRun/Attempt、必要な過去根拠・正式報告はSnapshot/既存履歴。全更新への版番号・複製は不要。再現に必要な履歴を失わない。Git等はSkill外。 |
| Q06 | qa-workflow | QAのSkill選択、順序、依存、局所停止・再開、引継ぎ、要求されたQAの完了確認。案件・配置・認証・保存技術、汎用状態基盤、共有資源の排他実装を持たない。QA固有の状態判断は維持し、既存成果物から復元できる情報の二重管理を避ける。 |
| Q07 | project-context | QA目的、対象、用語、業務ルール、決定・仮定、環境・制約の意味管理を残す。案件・Repository・保存配置・Provider管理は除外。独立Skillの必要性は専門責務から判断する。 |
| Q08 | Helper | 採番、同値分割/境界値等の決定論的生成、形式/参照検証、ファイル処理を担当。技法選択、リスク、仮説、仕様矛盾・不足、適用判断はSkill。実際の重複のみ共通化し巨大なHelperを作らない。 |
| Q09 | 保存対象の既定 | 仕様分析、観点・ケース作成、更新、テスト実行など成果物作成を目的とする依頼は、保存指示がなくても原則自動保存。実行証跡は必要かつ保存可能な範囲のみ。単発相談・読取・レビュー・調査は原則対話回答。保存依頼・継続利用目的がある場合に加え、再利用価値のある知識は許可済み保存先に必要分だけ自律保存する。任意蓄積のために通常回答を止めない。明示の非保存指示を優先し、許可済み保存先がなく保存が必要なら場所・許可を確認する。 |
| Q10 | 内容承認の成立 | 内容承認が必要な事項では現在の依頼者の明示回答・承認を採用する。回答対象・決定内容・必要な適用範囲を記録し、AIの推定を承認としない。別の権限者、組織の決裁契約、外部操作権限の確認が必要な場合はその既存経路を利用する。通常の内容承認に専用認証・Git push・本人性証明を一律要求しない。依頼者にない権限を推定しない。 |
| Q11 | 進行モード | qa-workflowはcontinuousを既定とし、gatedは利用者が現在明示した場合または有効な既存の利用者承認済み規則がある場合だけ適用する。旧実装の既定値や根拠不明の設定だけで停止しない。案件単位の進行モード設定を新規に要求しない。continuousではQA活動の基本原則に従って自律的に進行し、必要な仕様質問・正式承認・実操作許可の不足が影響する範囲だけ停止する。gatedは指定された工程境界で進行指示を待つ。 |
| Q12 | 改善完了 | 改善候補の全件実装を目標としない。対応済みは再実装せず、一部対応は不足部分のみ、不要・責務外・現時点で不要は理由を記録して除外または必要時のみ外部へ委譲、受入のみ必要なら検証する。必要な改善と受入が完了し、目的達成を確認した場合だけ完了。必要な未対応・未検証を対象外と読み替えない。 |

## 責任範囲と保存境界

- 成果物の分類・発見・保存は許可済みroot配下のディレクトリを基本とする。利用者の指定・有効な既存規則を優先し、指定がなければSkillの標準相対配置・命名・形式・履歴・運用契約を利用する。root・実行条件・許可範囲は既存Agent環境または呼出し側から取得する。案件識別・探索・切替、branch、Provider・認証方式選択はSkillに持たせない。意味identityに案件識別子を必須としない。別rootの同名refは同じ成果物ではない。Repository・branch・commit・PR差分等を指定されたQAの情報源として取得・分析することは対象理解・変更影響分析の責務であり、成果物のGit管理・案件管理とは区別する。情報源の読取許可は更新許可ではない。
- 保存の強度は用途・影響・共有条件に合わせる。単独実行の新規文書は通常のファイル保存と結果確認、既存文書更新は対象確認と必要な内容保全を基本とする。共有writer・競合の可能性がある更新は必要な条件付き保存や一意性を既存手段で確認し、過去根拠の再取得が必要なら必要な履歴を維持する。外部副作用は必要な認可・結果確認・再実行防止を行う。専用認証サービス、承認トークン、全成果物CAS、分散lock、独立readbackやrevision metadataの一律追加は不要。単一writerの隔離を仮定で保証せず、必要な境界が確認できない操作のみ止める。保存手段は既存実行環境・Helperの能力と必要な保証に基づいて扱う。利用者には保存・形式・運用上の指定の有無や、解決に必要な判断だけを確認し、Provider・CAS等の実現手段を通常の利用条件にしない。指定が必須の意味契約・安全条件と両立しない場合は具体的な制約を説明する。
- 保存済み、内容承認済み、現在採用可能、実行完了、テスト合否は別。候補保存は正式仕様変更ではない。保存失敗・結果不明を報告し、必要なreadback・依存・履歴を確認する。対話質問は保存不能でも提示可。永続的副作用は必要条件を満たす場合だけ実行する。承認済み仕様と候補を既存文書内の区分や既存の候補形式で識別し、必要性のない別draft・状態台帳は作らない。未承認でも後続の調査・設計案は可能だが、承認済み期待結果には使わない。
- 破壊的変更・無断移行・権限外操作・機密漏えい・必要な履歴消失・誤完了・未承認の正式仕様採用は許容しない。開発用Git保護は適用範囲が別であり、成果物保存の簡素化を理由に回避しない。

通常のQA成果物は、利用者指定・有効な既存規則がなければ人間向けMarkdown、機械処理用JSONを通常のファイル操作で保存する。SQLiteは今回の実装Planで廃止する。CAS、専用provider、全revision履歴、保存receipt、汎用claim/reservationは標準にせず、既存実装の不要な経路から除く。機械入力・source版・Entity依存・実結果の検証は保存技術と別に維持する。成果物から復元できる状態を重複記録しない。並行作業は担当・保存先・実行環境の分離を優先する。実際の競合・外部副作用に必要な既存制御とQAの検証、根拠・証跡・データ保護を維持する。同じ情報の二重正本やDB相当のファイル管理基盤を作らない。

## 責務・検証強度の削減基準

- QAの未解決質問・仕様根拠・設計成果物・実行結果は担当ownerの正本、次工程・局所再開・要求充足はqa-workflowの意味判断とする。Agentプロセス、必要な環境条件・権限は呼出し側。既存成果物から復元できない継続情報だけ必要に応じてstateに保持する。不要な状態管理を他層へ移管しない。
- Runtime・validator・Helperは用途、影響、後続再利用、実行・承認の証明要件に応じて必要な意味・形式・参照検証に限定する。QA技法、元依頼の要求完全性、根拠追跡、対象との対応、必要な再利用・実行・承認の証明、完了判定を維持する。特定の登録方式・保存証拠・JSON packet・専用CLI・metadataを維持すること自体を目的としない。契約変更はPlanで特定し必要な回帰を検証する。
- 人間による通常の文書編集は許可範囲内の非破壊的な編集と必要な差分・根拠確認を基本とする。生成領域・機械管理ID・承認済み仕様等の変更には該当ownerの必要な制約を適用する。UI package固有のwriterや編集提出・承認・履歴管理を他のMarkdownへ一律適用しない。

## 正本の維持（PRN-09）

- 文書、コード、Skill、Helper、設定、テスト・評価資産は有効な仕様と実装に合わせて更新する。変更に伴う参照先、入力・出力契約、schema、実装、検証、利用方法を同じ変更範囲で同期する。
- リファレンス、仕様書、README、利用ガイド、SKILL.mdは有効な内容だけを記載する。改訂時は追記だけで済ませず、置換・統合・不要記述の除去を行う。旧版との比較、調査時点の記録、変更経緯、実装予定・進捗を運用正本に混在させない。参照元には必要な概要と正本へのリンクを置く。
- 不要になったコード、分岐、設定、Skill、コメント、参照、テスト・評価資産は、依存と必要な機能・検証を確認して除去する。旧版や未使用実装を念のため残さない。必要な互換性、移行処理、回帰fixture、テスト証拠、履歴、監査・再現性のための記録は目的と保持条件に従って維持する。
- 変更予定・実装契約はPlan、調査・検証結果はReport、過去の版と変更経緯はGit履歴で扱う。正式報告や再現に必要なsnapshotを最新文書で置き換えない。未実装・未検証を実装済み・検証済みと記載しない。
- 最新性は採用済みで有効な仕様・実装との一致を意味し、依存ライブラリの無条件な最新版追従や無断移行・削除を意味しない。変更権限、必要な安全条件、作業範囲を守る。

## Plan・実装・レビューの判断

1. 目的・ユーザー要求・専門責務を確認する。
2. 不要な処理を先に削除し、残る責務をSkill・既存Helper・呼出し側へ分離する。
3. 既存契約・標準機能で成立するかを先に確認する。追加機能、抽象化、設定、防御、再確認、永続化は具体的な必要性と効果がある場合だけ採用する。
4. 防御は現実の失敗モード・影響・権限・共有条件に比例させる。想定可能という理由だけで全Skill共通の複雑な機構を作らない。実リスクの未検証を安全の証明にもしない。
5. 最小構成でQA品質、必要な履歴・再現性・安全性を検証する。専門外判断・読込・質問・設定・重複処理の削減を評価する。対象外、未達、判断理由を必要範囲で記録する。

この判断は既存Plan・レビュー・評価に統合し、新しいチェックリストや承認ゲートを増やさない。新規Skill、管理基盤、保存層、認証、汎用抽象化、追加防御を作る場合は既存手段の具体的不足を示す。固定削減目標・新規評価基盤は必要性と比較可能なbaselineが確認されるまで要求しない。
