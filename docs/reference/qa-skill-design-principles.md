# QA Skill設計・開発の共通原則

リポジトリ全体のコード、QA Skill、Helper、Workflow、文書、設定、テスト、Plan、評価・レビューに適用する設計・開発原則。設計・改修の判断基準であり、実行時の必須条件を単独で置き換えない。変更は対象Plan・作業権限に従い、必要な契約と安全性を検証する。

## 思考原則

| ID | 原則 | 判断基準 |
| --- | --- | --- |
| PRN-01 | KISS | 目的を満たす最も単純な構造・手順を選ぶ。 |
| PRN-02 | YAGNI | 実要求・確認済み問題・具体的リスクがない機能、設定、拡張点、抽象化を作らない。 |
| PRN-03 | SRP | 各Skillは専門責務に集中する。必要な外部責務は境界で受け取り、不要な責務は移管せず削除する。 |
| PRN-04 | DRY | 既存正本・標準機能・Helperを優先し、実際の重複だけを必要範囲で共通化する。 |
| PRN-05 | Fail-safe | 防御は現実のリスクに比例させる。保証不能な操作のみ停止し、独立分析は継続する。 |
| PRN-06 | 人間中心 | 成果物の発見・閲覧・編集・理解、利用者の判断負担を重視する。AIや保存技術の都合だけで決めない。 |
| PRN-07 | 決定論的処理 | 機械的に確定できる処理はHelper、意味判断はSkill。AIに不要な判断をさせない。 |
| PRN-08 | 段階的詳細化 | SKILL.mdは短い選択条件・責務・入出力・手順に集中。必要なreferenceだけ読む。 |
| PRN-09 | 最新性・単一正本 | コード・Skill・文書・設定・テストは有効な仕様と実装に同期する。不要な旧実装・旧記述・重複を残さず、必要な正本のみ維持する。 |

## 設計・運用原則

<!-- dprint-ignore -->
| ID | 項目 | 方針 |
| --- | --- | --- |
| Q01 | 単体利用・移植性 | 特定ハーネスを必須にしない。直接指定でも必要な入力・権限があれば実行する。保存先未指定でも分析可能。保存が必要な場合のみ場所を確認する。 |
| Q02 | 保存時点 | 保存対象の成果物は処理完了、質問提示前、回答反映後、中断、次工程引継ぎ前に許可範囲で必要分だけ自動保存する。同一内容の重複保存は不要。保存対象はQ09に従う。 |
| Q03 | 保存と承認 | 許可済みroot内の通常保存・非破壊的更新・質問/回答記録は都度承認不要。未承認内容は正式仕様・承認済み決定を失わない候補欄等に保存し、未承認と明示。候補保存で正本の承認済み意味を変更しない。正式決定、仮定採用、承認済み仕様の意味変更、破壊的変更/削除、必要な外部操作は承認する。 |
| Q04 | 正本・形式 | 人間が扱う分析・設計・質問・報告はMarkdown等の読みやすい構造化文書を優先。機械状態・証跡はJSON等、回答/閲覧UIはHTML等を用途別に選択。全成果物のJSON化・二形式化は不要。正本は一つ。Runtime・validatorの都合だけで正本形式や派生物を増やさない。 |
| Q05 | 履歴 | 継続文書は安定ファイル名、Q/DEC/ASM等は安定ID、実行はRun/Attempt、必要な過去根拠・正式報告はSnapshot/既存履歴。全更新への版番号・複製は不要。再現に必要な履歴を失わない。Git等はSkill外。 |
| Q06 | qa-workflow | QAのSkill選択、順序、依存、局所停止・再開、引継ぎ、要求されたQAの完了確認。案件・配置・認証・保存技術、汎用状態基盤、共有資源の排他実装を持たない。QA固有の状態判断は維持し、既存成果物から復元できる情報の二重管理を避ける。 |
| Q07 | project-context | QA目的、対象、用語、業務ルール、決定・仮定、環境・制約の意味管理を残す。案件・Repository・保存配置・Provider管理は除外。独立Skillの必要性は専門責務から判断する。 |
| Q08 | Helper | 採番、同値分割/境界値等の決定論的生成、形式/参照検証、ファイル処理を担当。技法選択、リスク、仮説、仕様矛盾・不足、適用判断はSkill。実際の重複のみ共通化し巨大なHelperを作らない。 |
| Q09 | 保存対象の既定 | 仕様分析、観点・ケース作成、更新、テスト実行など成果物作成を目的とする依頼は、保存指示がなくても原則自動保存。実行証跡は必要かつ保存可能な範囲のみ。単発相談・読取・レビュー・調査は原則対話回答のみ。保存依頼・継続利用目的があれば必要分を保存。明示の非保存指示を優先し、許可済み保存先がなく保存が必要なら場所・許可を確認する。 |
| Q10 | 内容承認の成立 | 通常のQA上の判断は現在の依頼者の明示回答・承認を採用する。回答対象・決定内容・必要な適用範囲を記録し、AIの推定を承認としない。別の権限者、組織の決裁契約、外部操作権限の確認が必要な場合はその既存経路を利用する。通常の内容承認に専用認証・Git push・本人性証明を一律要求しない。依頼者にない権限を推定しない。 |
| Q11 | 進行モード | qa-workflowはcontinuousを既定とし、gatedは利用者が明示した場合だけ適用する。案件単位の進行モード設定は不要。continuousでも必要な仕様質問・正式承認・実操作許可を省略せず、局所ブロッカーだけ停止する。gatedは指定された工程境界で進行指示を待つ。 |
| Q12 | 改善完了 | 改善候補の全件実装を目標としない。対応済みは再実装せず、一部対応は不足部分のみ、不要・責務外・現時点で不要は理由を記録して除外または必要時のみ外部へ委譲、受入のみ必要なら検証する。必要な改善と受入が完了し、目的達成を確認した場合だけ完了。必要な未対応・未検証を対象外と読み替えない。 |

## 責任範囲と保存境界

- 成果物の分類・発見・保存は指定root配下のディレクトリに統一する。相対配置と意味契約はSkill、root・実行条件・許可範囲は呼出し側（ハーネスまたは直接利用時の明示入力）。案件識別・探索・切替、branch、Provider・認証方式選択はSkillに持たせない。意味identityに案件識別子を必須としない。別rootの同名refは同じ成果物ではない。Repository・branch・commit・PR差分等を指定されたQAの情報源として取得・分析することは対象理解・変更影響分析の責務であり、成果物のGit管理・案件管理とは区別する。情報源の読取許可は更新許可ではない。
- 保存の強度は用途・影響・共有条件に合わせる。単独実行の新規文書は通常のファイル保存と結果確認、既存文書更新は対象確認と必要な内容保全を基本とする。共有writer・競合の可能性がある更新は必要な条件付き保存や一意性を既存手段で確認し、過去根拠の再取得が必要なら必要な履歴を維持する。外部副作用は必要な認可・結果確認・再実行防止を行う。専用認証サービス、承認トークン、全成果物CAS、分散lock、独立readbackやrevision metadataの一律追加は不要。単一writerの隔離を仮定で保証せず、必要な境界が確認できない操作のみ止める。Skillに保存技術の選択をさせない。
- 保存済み、内容承認済み、現在採用可能、実行完了、テスト合否は別。候補保存は正式仕様変更ではない。保存失敗・結果不明を報告し、必要なreadback・依存・履歴を確認する。対話質問は保存不能でも提示可。永続的副作用は必要条件を満たす場合だけ実行する。承認済み仕様と候補を既存文書内の区分や既存の候補形式で識別し、必要性のない別draft・状態台帳は作らない。未承認でも後続の調査・設計案は可能だが、承認済み期待結果には使わない。
- 破壊的変更・無断移行・権限外操作・機密漏えい・必要な履歴消失・誤完了・未承認の正式仕様採用は許容しない。開発用Git保護は適用範囲が別であり、成果物保存の簡素化を理由に回避しない。

## 責務・検証強度の削減基準

- QAの未解決質問・仕様根拠・設計成果物・実行結果は担当ownerの正本、次工程・局所再開・要求充足はqa-workflowの意味判断とする。Agentプロセス、必要な環境条件・権限は呼出し側。既存成果物から復元できない継続情報だけ必要に応じてstateに保持する。不要な状態管理を他層へ移管しない。
- Runtime・validator・Helperは用途、影響、後続再利用、実行・承認の証明要件に応じて必要な意味・形式・参照検証に限定する。QA技法、元依頼の要求完全性、根拠追跡、対象との対応、必要な再利用・実行・承認の証明、完了判定を維持する。特定の登録方式・保存証拠・JSON packet・専用CLI・metadataを維持すること自体を目的としない。契約変更はPlanで特定し必要な回帰を検証する。
- 人間による通常の文書編集は許可範囲内の非破壊的な編集と必要な差分・根拠確認を基本とする。生成領域・機械管理ID・承認済み仕様等の変更には該当ownerの必要な制約を適用する。UI package固有のwriterや編集提出・承認・履歴管理を他のMarkdownへ一律適用しない。

## 正本の維持（PRN-09）

- 文書、コード、Skill、Helper、設定、テスト・評価資産は有効な仕様と実装に合わせて更新する。変更に伴う参照先、入力・出力契約、schema、実装、検証、利用方法を同じ変更範囲で同期する。
- リファレンス、仕様書、README、利用ガイド、SKILL.mdは有効な内容だけを記載する。改訂時は追記だけで済ませず、置換・統合・不要記述の除去を行う。旧版との比較、調査時点の記録、変更経緯、実装予定・進捗を運用正本に混在させない。参照元には必要な概要と正本へのリンクを置く。
- 不要になったコード、分岐、設定、Skill、コメント、参照、テスト・評価資産は、依存と必要な機能・検証を確認して除去する。旧版や未使用実装を念のため残さない。必要な互換性、移行処理、回帰fixture、テスト証拠、履歴、監査・再現性のための記録は目的と保持条件に従って維持する。
- 変更予定・実装契約はPlan、調査・検証結果はReport、過去の版と変更経緯はGit履歴で扱う。正式報告や再現に必要なsnapshotを最新文書で置き換えない。未実装・未検証を実装済み・検証済みと記載しない。
- 最新性は採用済みで有効な仕様・実装との一致を意味し、依存ライブラリの無条件な最新版追従や無断移行・削除を意味しない。変更権限、必要な安全条件、作業範囲を守る。

## Plan・実装・レビューの判断

1. 目的・ユーザー要求・専門責務を確認する。
2. 不要な処理を先に削除し、残る責務をSkill・既存Helper・呼出し側へ分離する。
3. 既存契約・標準機能で成立するかを先に確認する。追加機能、抽象化、設定、防御、再確認、永続化は具体的な必要性と効果がある場合だけ採用する。
4. 防御は現実の失敗モード・影響・権限・共有条件に比例させる。想定可能という理由だけで全Skill共通の複雑な機構を作らない。実リスクの未検証を安全の証明にもしない。
5. 最小構成でQA品質、必要な履歴・再現性・安全性を検証する。専門外判断・読込・質問・設定・重複処理の削減を評価する。対象外、未達、判断理由を必要範囲で記録する。

この判断は既存Plan・レビュー・評価に統合し、新しいチェックリストや承認ゲートを増やさない。新規Skill、管理基盤、保存層、認証、汎用抽象化、追加防御を作る場合は既存手段の具体的不足を示す。固定削減目標・新規評価基盤は必要性と比較可能なbaselineが確認されるまで要求しない。
