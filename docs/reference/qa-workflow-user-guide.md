# QAワークフロー利用者マニュアル

[共通運用契約](qa-workflow-operating-contract.md)と[Skill別マトリクス](qa-workflow-artifact-matrix.md)の利用者向け入口。依頼に必要なSkillだけを利用する。特定のハーネスは前提としない。利用方法は担当Skillの実行契約に従う。必要な入力・実行条件を満たせない操作は停止し、可能な分析は継続する。

## 依頼時に指定すること

<!-- dprint-ignore -->
| 項目 | 利用者の対応 |
| --- | --- |
| 目的・対象・情報源 | 対象機能、仕様書、デザイン、既存成果物、必要なrepo/branch/commit等を指定 |
| QA計画 | 必要な業務上の重点、品質目標、対象範囲・制約を提示 |
| 保存・編集 | 保存先・形式・命名・運用規則に指定があれば伝える。必要な許可範囲と現行担当契約で必要な条件を確認 |
| 進行 | continuousまたはgatedを指定可能。指定なしの場合は案件コンテキスト、未設定ならcontinuous |
| 実行環境 | 実行依頼の場合はURL、必要な権限・データ、許可操作・上限・cleanupを提示 |
| 継続QA | 必要なRegression方針・履歴・外部Issue先等を指定 |
| 横断コンテキスト分析 | 必要時に対象・分析範囲、補助/必須の扱いと保存先を指定。無効・未指定では起動しない |

初回に全設定を埋める必要はない。既に提示済みの有効な情報・成果物は再入力不要。秘密情報の実値は仕様・コンテキスト・回答フォームへ貼らない。

## 利用者の対応が必要な場面

<!-- dprint-ignore -->
| 場面 | 対応 |
| --- | --- |
| 情報不足・仕様ブロッカー | 必要な資料、質問への回答、正式決定・仮定承認 |
| QA要求・方式・計画の確定 | 現行契約で必要な内容・対象範囲を承認 |
| 保存・実行に必要な承認・権限・条件 | 必要な場所・許可・条件を提示し、担当契約で必要な保存承認を行う。特別な承認操作が必要な場合は「保存・編集」を参照 |
| 破壊的変更・外部操作・別権限者による判断 | 必要な対象・差分・許可・承認を確認 |
| gated | 指定工程の成果物を確認し、修正または次工程を指示 |
| 結果・改善判断 | 必要なリスク受容、改善採否、引継ぎ・リリース判断 |

採番、既存成果物・合意・知識の発見、適用範囲内の判断、技法選択・適用、形式検証、質問と回答の対応確認、変更影響・再利用判断はAgentが担当する。continuousでは依頼されたQA活動を進め、利用者による意思決定や現行契約で必要な承認・操作許可を確認する。任意提案への回答を進行条件としない。

## 依頼例

以下は自然言語の例でありCLIコマンドではない。

- 初回設計：「対象機能Aの仕様から詳細TCまで作成。既存成果物を利用し、仕様ブロッカーは質問して。保存先は指定ディレクトリ。」
- 観点のみ：「既存TRを利用してTCNとCIを更新。ケース作成や実行は不要。」
- 変更影響：「PR #123の差分を現在の仕様とTCに照合し、影響scopeだけ再分析して。」
- 再開：「前回の成果物の場所を参照して再開して。未解決質問と最後に完了した工程から続けて。」
- E2E実行のみ：「既存Playwrightの対象testを合意済み環境で実行し、結果とcleanupを報告して。」
- 探索：「機能Aの失敗回復を30分のtimeboxで探索。許可済み操作だけ実施して。」
- 統合報告：「承認済み計画と今回のRunを集計し、終了基準・未実行・残存リスクを報告して。」

横断コンテキスト分析では単一情報源の観察記録、複数workflowの法則候補分析を依頼できる。補助分析の失敗は元のQA完了を妨げないが、必須分析は必要な保存・検証まで行う。候補は正式仕様と区別する。通常の指定root保存に専用認証host・都度承認は不要で、正式仕様変更や必要な外部操作は担当契約に従う。

PRやrelease検知、定期起動は呼出し側の仕組みが必要。Skill自体は監視を開始しない。

## 質問に答える

提示された質問の内容・根拠・影響を確認し、回答する。HTMLフォームを利用する場合は回答を入力し、出力された回答Markdownを返す。対話・Markdownで直接回答してもよい。質問ID、質問JSONとHTMLの整合、回答と元質問の対応、過去回答の再利用可否はAgentが確認し、意味・根拠の変更により再回答が必要な場合だけ質問する。利用者がJSONやHTMLの構造を検証する必要はない。

<!-- dprint-ignore -->
| 回答 | 例 | Agent側 |
| --- | --- | --- |
| 仕様更新 | Q-001：仕様書を改版した（参照、版） | SPECとして再分析 |
| 正式決定 | Q-002：正式挙動はAと決定する | DECへ正規化 |
| 暫定仮定 | Q-003：今回のscopeに限りAと仮定することを承認 | ASMへ正規化 |
| 保留 | Q-004：確認中、未確定 | ブロッカーなら該当scopeのみ停止 |

保留・推奨案は承認ではない。表は期待挙動に関する回答例であり、URL・データ・保存先・操作許可などへの回答は該当する担当契約に従って扱う。専門QA判断はAgentが行う。正式承認は担当契約に従い、必要な権限者・承認経路で確認する。必要な回答がないscopeだけ停止する。

今回の対象から外したい場合は対象と変更理由を伝える。現行Runtimeでは開始後の必須scopeの除外承認を確定できないため、除外の回答だけで元の依頼を完了扱いにはできない。依頼自体を変更した場合は元の依頼の未完了範囲と区別して扱う。

## 保存・編集

成果物作成・継続利用では必要な保存も依頼に含まれる。Agentが指定・既存規則と担当Skillの契約を確認し、利用できる保存方法を判断する。必要時は「保存先・形式・運用ルールに指定はありますか」と確認し、指定がなければ現行契約で利用できる標準方法を使う。利用者が技術的な保存条件を選ぶ必要はなく、判断・操作が必要な不足だけ具体的に説明する。単発相談・レビュー・調査は原則対話回答のみ。非保存を指定できるが、保存済み証拠が必須の現行Runtime経路では必要な保存を行わない限り正式完了にはならない。正式保存に認証済み承認が必要な場合は指定された経路で対応する。保存条件を満たせない場合は不足条件・確認できた保存状態・必要な再開情報を受け取る。内容承認・進行指示・保存・操作許可は別である。

現行契約でGitによる正式保存承認が必要な場合は、Agentが提示する操作・対象・差分を確認して同意し、書込権限のある自身の認証済みアカウントで通常pushする。Agentが実行者・保存前後の版を照合する。照合できない場合は承認済みとしない。詳細は[保存・承認契約](../plans/2026-11-07_170134_qa-full-process-implementation_02_storage-approval-reporting.md)を参照。

人間による編集は許可範囲・担当Skillの編集契約に従う。正式仕様の意味変更と通常の文書編集を区別し、承認済み内容を未承認候補で置換しない。生成領域・機械管理IDは担当契約に従い、[UI target packageの編集規則](../../skills/spec-analysis/references/ui-test-target-analysis.md)を他のMarkdownへ一律適用しない。

## 中断・再開・結果確認

再開に必要な成果物の場所またはworkflow refを指定する。Agentが一意に解決できる場合は再指定不要。必要な保存済み情報を用いて、未解決範囲・変更影響だけ再開する。保存結果や外部操作結果が不明な場合は、元操作を確認するまで再実行を指示しない。

<!-- dprint-ignore -->
| 状態 | 利用者が確認すること |
| --- | --- |
| 完了 | 依頼の必須範囲と必要な成果物・検証・保存・cleanupを充足 |
| 部分完了 / blocked | 完了範囲、未完了理由、必要な回答・権限・再開先 |
| 未検証 | 必要な検証が未実施または未確認。正式完了の根拠にしない |
| stale / 要再検証 | 変更・依存根拠不足等により現在の採用条件を満たさない。変更確認済みと現在の有効性が未確認の場合を区別し、担当契約に従って再検証する。過去の完了記録とは別 |
| draft | 内容が未確定。保存済みの場合もあるため保存状態と必要な承認を別に確認 |
| 未保存 | 今回の書込みが行われていないことを確認済み。必要な保存先・条件を確認 |
| 保存済み | 必要な保存確認を充足。内容承認とは別に確認 |
| 保存結果不明 | 書込み後の読戻し失敗等で結果を確定できない。未保存・保存成功と断定せず実保存結果を照合し、盲目的再書込みはしない |

実行報告では対象・環境・母集団、実行済み/未実行、PASS/FAIL・判定不能、cleanup、残存リスク、保存状態を確認する。母集団不明時は全体率・終了判定を確定しない。成果物完成・実行完了・テスト合否・終了基準・リリース承認は別である。個別Skillの完了とWorkflowの正式完了も区別する。現行の汎用完了検証では未登録scopeが残るとWorkflowは完了しない（[共通運用契約](qa-workflow-operating-contract.md#完了判定)）。現行は共有予約・分離が確認できるまで同一案件の並列workflowを避ける。必要な分離・予約・権限が確認できない共有環境で並行実行しない。
