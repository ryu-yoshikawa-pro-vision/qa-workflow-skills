# QAワークフロー利用者マニュアル

[共通運用契約](qa-workflow-operating-contract.md)と[Skill別マトリクス](qa-workflow-artifact-matrix.md)の利用者向け入口。全Skillを毎回実行する必要はない。

## 初回・変更時に決めること

Agentへ対象製品、repo/branch、依頼目的、既存仕様・QA成果物の場所を伝える。既存Project Contextがあれば利用し、初回正式書込み前に不足項目・配置維持案を確認する。探索入口は案件・repo/branch・既存資料の場所を基準に許可範囲でAgentが調べる。候補が読めない場合は新規作成せず、アクセスまたは判断を依頼する。

<!-- dprint-ignore -->
| 項目 | 利用者の対応 | 区分 | 再確認 |
| --- | --- | --- | --- |
| 対象・情報源 | repo/branch、仕様書、デザイン、既存TC等の入口と優先順位 | 必須（不足時） | 変更時 |
| QA目的 | 重要業務、対象範囲、品質目標、レベル/タイプ | 条件付き：QA目的・計画 | 目的変更時 |
| 保存・編集 | 正本の場所、provider、編集可能範囲、承認policy | 条件付き：継続保存・編集 | 変更時 |
| 進行 | continuous（既定）またはgated | 任意（既定あり） | 任意 |
| 実行環境 | URL、role、認証取得方法、データ準備、許可操作・上限・cleanup | 条件付き：実行依頼 | 実行が必要な場合と条件変更時 |
| 継続QA | Regression方針、knowledge root、外部Issue先等 | 条件付き：継続活動 | 必要時 |

秘密情報の実値をProject Contextや回答フォームへ貼らない。保存先未設定でも独立読取分析は可能だが正式保存はできない。

初回から全設定を埋める必要はなく、今回の依頼に必要なものだけ確定する。配置合意・正式保存・実行認可は別。Agentに既存成果物発見・ID採番・形式検証・変更影響・再利用判断を任せる。既存合意が有効なら再入力不要。

## 利用者の介入一覧

<!-- dprint-ignore -->
| 場面 | 要否 | 利用者の行動 |
| --- | --- | --- |
| 新規依頼 | 必須 | 目的・対象・要求成果物を指定。不足情報のみ提示 |
| 初回正式保存・配置変更 | 条件付き | G1で正本・配置・編集範囲・権限を合意 |
| 仕様ブロッカー | 条件付き | G2でQへ回答・決定・仮定承認 |
| 要確認・任意提案 | 任意 | 回答可能なら回答。独立scopeは継続 |
| QA要求・方式・計画確定 | 条件付き | G3で必要内容を承認 |
| 正式保存・副作用操作 | 条件付き | G4で対象・revision・差分・許可範囲を確認 |
| gated | 条件付き | 現在Skillの成果物確認・次工程指示 |
| 結果・改善判断 | 条件付き | G5で必要なリスク受容・改善採否・リリース判断 |

条件付きは該当条件での必要対応であり、承認省略の意味ではない。

## 依頼例

以下は自然言語の例でありCLIコマンドではない。

- 初回設計：「対象機能Aの仕様から詳細TCまで作成。既存Project Contextと成果物を優先しcontinuousで進めて。仕様ブロッカーは質問して。」
- 観点のみ：「既存TRを利用してTCNとCIを更新。ケース作成や実行は不要。」
- 変更影響：「PR #123の差分を現在の仕様とTCに照合し、影響scopeだけ再分析して。」
- 再開：「前回のworkflow refを再開して。未解決質問と最後に完了した工程から続けて。」
- E2E実行のみ：「既存Playwrightの対象testを合意済み環境で実行し、結果とcleanupを報告して。」
- 探索：「機能Aの失敗回復を30分のtimeboxで探索。許可済み操作だけ実施して。」
- 統合報告：「承認済み計画と今回のRunを集計し、終了基準・未実行・残存リスクを報告して。」

PRやrelease検知、定期起動は呼出し側の仕組みが必要。Skill自体は監視を開始しない。

## 質問に答える

AgentはQ ID、根拠、影響、未回答時の扱い、再開先を示す。複数質問のHTMLフォームが必要な場合は、受け取った質問JSONとHTMLに対応する定義を確認し、入力後にMarkdown出力をAgentへ返す。Markdownや対話で直接回答してもよい。保留は承認ではない。改版後は旧回答を自動適用せず、意味・根拠が変わった質問を再確認する。

<!-- dprint-ignore -->
| 回答 | 例 | Agent側 |
| --- | --- | --- |
| 仕様更新 | Q-001：仕様書を改版した（参照、版） | SPECとして再分析 |
| 正式決定 | Q-002：正式挙動はAと決定する | DECへ正規化 |
| 暫定仮定 | Q-003：今回のscopeに限りAと仮定することを承認 | ASMへ正規化 |
| 保留 | Q-004：確認中、未確定 | ブロッカーなら該当scopeのみ停止 |

回答と承認は別。正式DEC/ASMは権限者の明示判断が必要で、ASMは有効なSPEC/DECISIONを上書きできない。承認の真正性が必要な操作では案件の認証済み承認経路を利用する。質問前の中間保存は既に許可された作業領域のみ。正式保存承認は省略しない。保存不能なら未保存の候補・再開情報を受け取る。横断自動保存は未実証。

## 保存・承認・人間編集

正式保存時はAgentが提示する操作・scope・保存先branch・before revision・差分を確認し、必要な承認だけを明示する。Git既定方式では対話同意後に認証済みアカウントで通常pushし、activity APIのactor/before/afterと保存内容を確認する。push成功だけで承認済みとはならない。対象revision・権限が変われば再確認。認証・provider不足ではblocked。応答消失時は失敗と決めつけず、Agentが実保存先を独立再取得するまで同じ書込みを再指示しない。

continuousでは各TR/TCN/TC工程ごとに進行指示を出す必要はない。gatedでは成果物確認後に修正または次工程への進行を指示する。進行指示は保存・副作用の包括許可ではない。

人間が編集する場合は、Agentに編集可能な正本参照・元revision・scope・作業用branch/copyを示させる。許可されたMarkdown等だけ編集し、差分と根拠を提出する。canonical rootを直接置換しない。ui-target-v1の場合はMANIFEST、生成README metadata、機械生成CHANGELOG、Machine Entity、標準heading/file名を直接変更しない。新規行はdraft keyで提案し、手動ID・行削除を確定採番・廃止にしない。他成果物は各owner契約に従う。作業branchへのpushは編集提出であり正本更新承認とは別。ownerレビューと必要承認後に正式writerで反映。競合・直接改変時は編集案と元revisionを保全し無断復旧しない。

## 利用シナリオ（運用例）

現行責務と運用指針に沿う例。全provider・自動再開が実証済みという意味ではない。

<!-- dprint-ignore -->
| シナリオ | 利用者 | Agent | 停止・再開条件 |
| --- | --- | --- | --- |
| 初回継続設計 | 目的・資料入口、必要な配置/編集合意 | 既存Context探索→分析→必要scope設計→検証・必要保存 | 不足根拠はG2、正式保存はG4。独立読取は先行可 |
| ブロッカー・部分回答 | Q IDで回答・保留指定 | 許可済み領域に候補・Q・再開先を保全、正規化、依存範囲のみ再開 | 未承認・未保存を明示、保留scopeは停止 |
| 既存成果物の変更 | PR/改版参照指定 | 入力母集団・依存revision・正本を確認し局所更新 | 配置変更・新承認が必要な場合のみ確認 |
| 別session再開 | 必要ならworkflow ref/場所 | 保存済みstateと正本を再取得、未完了・stale特定 | 結果不明は独立照合、盲目的再実行なし |
| 実行・報告 | 環境・操作認可、結果判断 | preflight、必要予約、実行、raw/cleanup、集計 | 認可・予約不足は実開始前block、合否と完了分離 |
| 単発読取 | 対象・質問指定 | 許可範囲の読取・分析・報告のみ | 不要な配置合意・永続保存を要求しない |

## 中断・再開・結果確認

再開時は既存workflow refまたは成果物の場所を指定（Agentが一意に解決できる場合は不要）。元依頼・入力母集団・依存revision・利用案件設定・成果物currentnessを確認できれば再利用し、変更scopeだけ再実行する。入力revision同一だけでは列挙漏れを検出できない。外部操作結果不明時は元実行・保存結果・cleanup・claim/予約を確認するまで同じ操作を再実行しない。

報告で対象build・環境・母集団・実行済み/未実行・PASS/FAIL・判定不能・cleanup・残存risk・保存状態を確認する。

<!-- dprint-ignore -->
| 状態 | 利用者が確認すること |
| --- | --- |
| 完了 | 元依頼と要求scope、必要owner検証・cleanup・保存要求を充足。成果物完成・合否・終了基準・リリース承認とは別 |
| 部分完了 / blocked | 完了済み範囲、未完了理由、必要な回答・権限・再開先 |
| unverified / stale | owner verifier・currentness・保存/承認証拠不足。正式完了ではない |
| draft / 未保存 | 正式保存を確認していない候補。必要な保存先・承認を設定 |
| 保存結果不明 | 実書込みの成否は未確定。最後の検証済みbaselineを保全し、実保存先再取得まで再書込みしない |

必要時は権限者が欠陥候補のIssue操作、リスク受容、改善採用、引継ぎ受領、リリース判断を行う。計画母集団不明の直接報告は全体率・終了判定がundetermined。共有予約・実行環境の分離が確認されるまで同一案件の並列workflowは避ける。現行の未接続provider・未登録owner等は[改善一覧](../reports/2026-11-25_qa-workflow-operating-improvements.md)と[PR #22の残存制約](../implementation/pr22/merge-decision-2026-11-14.md)を参照。
