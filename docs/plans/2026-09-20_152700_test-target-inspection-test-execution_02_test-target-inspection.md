## 2. `SKILL.md` 契約

`description`は次の発火境界を識別できる内容にします。

- 実対象を確認し、テスト設計 / 実装 / 実行向けの参照資料を作成する
- 既存のテスト対象資料を実対象に合わせて更新する
- POM相当のUI構造・操作・状態情報を整理する
- Playwrightコード実装、E2E実装可否だけのinspection、TC作成、テスト実行では発火しない

### 必須入力

最低限、次を識別できることを要求します。

- 調査対象: 機能、画面、領域、ユーザー操作経路等
- 今回確認すべき事実と、その確認に利用できる実対象またはrepo / workspace

通常の`test-target-inspection`では実対象の事実を正本とし、repo / workspaceは補助情報源として使用します。ユーザーが現在の実画面・実対象の確認を要求している場合、repo / workspaceの確認だけで`実対象確認済み`とは扱いません。ユーザーがrepoだけの調査を明示した場合は、その限定範囲の成果物として扱い、実対象事実まで確認済みとは表現しません。確認元ごとに`実対象` / `repo` / `ユーザー提供情報` / `未確認`を区別します。

更新要求では、既存のテスト対象資料またはその参照先を入力にします。

永続更新を要求された場合は、保存先と書込可能性を確認します。保存先不明時に独自の既定パスを作りません。永続保存・更新そのものが要求成果物なら、保存先不明、書込不能、安全な差分更新不能、保存後不整合が残る場合は完成した候補を返してもSkillを完了扱いにしません。

### 補助入力

利用可能な場合だけ使用します。

- 対象URL / origin
- browser / computer操作能力
- repo branch / commit / working tree
- version / build ID
- 既存Page Object / fixture / helper
- 関連するテストケース
- 現在有効な仕様根拠

仕様根拠は、テスト対象資料へ期待結果を転記するための必須入力にはしません。仕様と観測実装を比較する要求がある場合だけ参照し、両者を別事実として保持します。

## 3. 調査手順

`references/guidance.md`では次の順序を固定します。

1. 対象範囲と要求成果物を確認する
2. 既存テスト対象資料の有無、成果物単位、鮮度情報、更新元revision / content identityを確認する
3. repo / workspaceの確認が要求範囲や後続作業に必要な場合だけ、route、UI識別方針、関連実装等を補助情報として確認し、repo事実を利用した場合はbranch / commitだけでなくworking tree状態も保持する。Page Object / fixture / helperとの対応表作成自体を必須目的にしない
4. 今回必要な実対象事実がある場合は実対象へ到達する。アクセス・権限・操作能力等により到達できない場合は、その事実を`確認不能`として残す。ユーザーがrepoだけの調査を明示した場合は実対象到達を必須にしない
5. 状態・遷移確認に永続的な副作用が必要な場合は、対象origin、許可範囲、最大回数、cleanup方法を確認する。確認できない場合はその操作を実施しない。実施する場合は再試行も最大回数へ含める
6. 対象画面 / 領域、UI要素、状態、遷移、データ / 権限依存、非同期状態を確認する
7. 既存資料と今回確認事実を比較する
8. 変更がある範囲だけ更新候補を作成し、未確認範囲を推測で書き換えない
9. 各情報が確認元、確認日時、その事実を確認したversion / buildまたはrepo revision、該当事実へ影響するrole / 権限・viewport・locale・feature flag・テストデータ等の確認条件へ辿れるようにする。repo事実では必要に応じてworking tree状態も保持し、今回未再確認の既存情報の確認version / build・revision・確認条件を今回値へ更新しない
10. 更新候補へ出力契約・参照整合を適用する
11. 永続更新を要求する場合は、保存先が提供するSHA / revision / ETag等の条件付き更新に利用できる元状態を手順2の情報から確定する。条件付き更新を利用できない場合だけ、保存直前に更新対象を再読込し、更新元revision / content identityまたは元内容と比較する
12. 保存先と書込能力があり、更新候補が契約を満たす場合だけ対象成果物へ保存する。条件付き更新が競合で失敗した場合、または手順11の比較で途中変更を検出した場合は古い候補で上書きせず、最新内容から候補を作り直す
13. 保存後に読取可能なら再読込し、保存内容が更新候補と一致することを確認する。永続保存・更新が要求成果物なのに保存できない、または保存後不整合が残る場合は該当範囲を完了扱いにしない
14. 保存済み成果物の場所・範囲・鮮度を返す。`qa-workflow`利用時の案件コンテキスト`既存QA成果物`欄への反映は`qa-workflow`が担当し、`test-target-inspection`自身は案件コンテキストを書き換えない

新規作成時も、調査範囲外の周辺画面まで網羅目的で追加しません。保存前検証を省略して壊れた候補を先に永続化しません。

今回確認すべき範囲に必要な`未確認`または`確認不能`が残り、その情報なしでは要求成果物を完成できない場合は、repo由来情報だけでSkillを`完了`にしません。確認済み範囲の成果物は保持しつつ、該当範囲をworkflow上`ブロック中`として返します。

## 5. 対象キーの扱い

新しい全リポジトリ共通ID体系は追加しません。

`対象キー`、`要素キー`、`状態キー`はテスト対象資料内で一意かつ更新時に安定していることを要求します。新規成果物では文書ローカルの正規形式として`target-001`、`element-001`、`state-001`を種類ごとに`001`から未使用番号へ昇順で割り当てます。同じ意味の対象は更新時に同じキーを維持し、表示名、route、locator等の変更だけでは再採番しません。更新処理中に削除したキーを同じ更新処理で即再利用しません。過去versionの削除済みキーを永久管理するtombstone / registryは追加しません。

既存資料に別の安定キー規則がある場合はその規則を維持し、今回形式へ一括置換しません。既存資料に安定キーがない場合は、正規テンプレートへ安全に対応付けられる範囲だけキーを付与し、意味対応が曖昧な項目を推測して全件再採番しません。操作・遷移、データ / 権限依存、未確認事項、既存更新時の`今回の更新`はこれら既存キーを参照し、表示名だけで同一対象を識別しません。任意の既存テスト実装対応も記録する場合は同じキーを参照します。新しい操作IDや関係IDは追加しません。

既存QA IDへ混ぜず、`scripts/skills/evals/deterministic/common.py`の`ID_PATTERNS` / `ALL_ID_RE`を今回の資料キーのためだけに拡張しません。

## 6. 更新原則

既存成果物を更新する場合は次を守ります。

- 今回確認できた範囲だけ更新する
- 未確認の既存項目を「存在しない」と推測して削除しない
- 意味が同じ対象のキーを不要に再採番しない
- repo / 実対象に存在しないPage Object、locator、fixture等を創作しない
- テンプレート外の人間記載内容を無関係に削除しない
- 正規テンプレートまたは構造的に互換性を確認できる既存資料だけを自動差分更新し、任意形式文書向けの汎用merge処理を追加しない
- 構造が曖昧で安全に差分更新できない場合は、更新不能範囲を明示する
- 永続保存前に更新元成果物が候補作成時から変更されていないことを再確認し、変更済みなら古い候補で上書きしない

全対象の再生成を既定にしません。

既存成果物がある場合はその成果物単位を維持します。新規作成では今回要求された調査範囲を1成果物の範囲とし、明示要求なしに製品全体へ広げたり画面単位へ分割したりしません。

削除判定は情報源に合わせます。実対象で確認したUI要素・状態・遷移は、原則として同じ対象条件の実対象で不存在を確認できた場合だけ現在状態の一覧から除外します。任意で記録したrepo対応は、対象revisionのrepoで不存在を確認できた場合だけその対応を削除できます。repoだけから実対象の不存在を証明する場合は、runtime生成・feature flag・branch / build差等を除外できる明確な根拠を残します。今回の調査で見つからなかっただけの項目は削除せず、`未確認`、`確認不能`、または`既存資料から継承・未再確認`として残します。既存成果物から削除した場合は`今回の更新`へ`削除確認`を残します。

鮮度は確認日時だけでcurrent判定しません。同一version / buildは再利用候補とし、version / buildが変わった場合は関連変更が該当範囲へ影響するか確認します。影響なしを確認できれば再利用し、影響不明なら該当範囲だけ再確認します。version / buildを取得できない場合は確認日時時点の観測事実として保持し、現在も有効と断定しません。repo由来事実はbranch / commitだけでなくworking tree状態も確認し、未commit変更に依存して確認した事実をHEAD commitだけでcurrentとみなしません。部分更新後も、継承行はその行を実際に確認したversion / build・revision・確認条件を保持し、成果物上部の今回version / buildで上書きしません。

成果物・証跡にはTC判定や後続作業に不要な個人データ・機密情報を転載しません。secret、cookie、token、storageStateは値そのものを記録しません。screenshot、page snapshot等も必要最小限とし、機密情報を含む可能性がある証跡を自動共有・commit・転載しません。

最終出力前に、`SKILL.md` / guidanceで定義した出力契約を成果物自身へ再適用し、キー一意性・参照整合、確認状態・確認条件・鮮度、未確認事項、更新履歴、保存状態を自己検証します。明白かつ局所的で新しい領域判断を必要としない契約違反だけを最大1回修正し、推測で観測事実やキー対応を補完しません。`evals/deterministic/validator.py`はこのruntime自己検証の実装として呼び出さず、評価専用とします。

`test-target-inspection`は対象製品コード、Page Object、fixture、helper、既存テストコードを変更しません。永続書込は、ユーザーまたは案件が指定したテスト対象資料の作成・更新に限定します。実装修正が必要と判明した場合は観測事実として残し、責任Skillへroutingします。

現在有効なテスト対象資料は`test-case-design`でUI名称、到達方法、具体手順、観測可能性の補助情報として任意利用できます。ただし期待結果・合格条件の根拠には使用しません。

## 7. `e2e-test-inspection`との関係

`e2e-test-inspection`は残します。

現在有効な`test-target-inspection`成果物がある場合は、次の実対象事実を再利用可能にします。

- 対象画面 / 経路
- 実在UI要素
- role / accessible name等
- 状態・非同期動作
- Page Object / fixture / helperのrepo参照
- version / build / repo revision / working tree / 確認日時

ただし`e2e-test-inspection`自身が所有する次の判断は移しません。

- E2E対象の扱い
- Playwright実装可否
- config / project / test固有条件
- E2E固有の認証・setup / cleanup
- 副作用上限
- artifact / reporter条件

資料が古い、対象範囲が不足する、確認元が不明な場合は再利用せず、必要範囲だけ`test-target-inspection`へ戻せるようにします。
