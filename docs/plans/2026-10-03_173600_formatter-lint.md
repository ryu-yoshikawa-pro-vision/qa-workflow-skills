# Formatter / Python lint / Codex開発ハーネス導入Plan

このPlanは、`qa-workflow-skills`の開発を安定させるために、formatter / Python lintと、`qa-training-store`で実運用しているCodex開発ハーネスのうち、このリポジトリで現在必要なものを同じ変更で導入する実装計画です。

段階分けはしません。`qa-training-store`の構成を丸ごとコピーするのではなく、現在の`qa-workflow-skills`の構成、Python中心のruntime、既存CI、既存のPlan / review運用、現在のCodex公式仕様に照らして、必要なものだけを移植します。

Formatter / lintはrepository-wideなコード・文書品質を維持し、Codexハーネスは開発Agentの指示、委譲、安全境界、検証を維持します。QA Skill本体のworkflow / runtime / artifact graphとは別責務として扱います。

## 目的

次を同時に満たします。

- PythonをRuffでformat / lintする
- Markdown / JSON / YAML / TOML / JavaScriptをdprintでformatする
- 評価fixture、過去Plan、history、reportを含め、今回Planで定義した対象拡張子のtracked fileを原則すべてformatする
- format後も現在のSkill契約、runtime、deterministic / semantic / trigger評価、CI結果を変えない
- PR以降に追加された対象拡張子の未formatファイルをGitHub Actionsで検出できるよう、format / lintを継続検査する
- root `AGENTS.md`でCodexの作業範囲、安全性、Plan / review / implementationの基本契約をrepository-localにする
- Plan、review、bounded repairの開発workflowを`.agents/skills/`へ移植する
- 調査専用、限定実装、テスト調査、品質ゲート実行をcustom subagentへ役割分離できるようにする
- Bash tool経路では、execpolicy rulesで静的に判定できる高影響 / 禁止操作を分類し、`PreToolUse` Hookで現在branch等の実行時contextが必要な危険操作とopaqueなnested shellをguardrailとして検査する
- granular approvalで、通常のfeature branch Git mutation、高影響操作の明示承認、永久禁止操作を分離する
- compact後に必要なroot `AGENTS.md`を再注入できるようにする
- WindowsとPOSIXの両方で安全Hookを利用できるようにする
- ハーネス自体のconfig / Hook / Windows launcherをCIで回帰検出する
- `qa-training-store`固有のNodeアプリ、Android、Agentic QA、Run Artifact、textlint、CI待機MCP等は持ち込まない
- QA Skill本体の19 Skill、artifact graph、evaluation contractをCodex開発ハーネスの都合で変更しない

formatやハーネス導入を理由に、QA workflowの責務、評価datasetの意味、runtime契約、validator契約、テストケースの内容を変更しません。

## 採用するツール

### Ruff

PythonのlintとformatにRuffを使用します。

実装時点ではRuff `0.16.8`を固定します。

理由:

- 現在のリポジトリはPython 3.11をCIの正本としている
- Ruff単体でlint、import sorting、Python formatを扱える
- Black + Flake8 + isortを個別導入する必要がない
- `ruff.toml`を利用でき、Python package管理を導入する必要がない

Ruff 0.16系では既定lint ruleが従来より大幅に増えているため、既定ruleへ依存しません。初回導入では現在の目的に必要なruleだけを明示します。

`ruff.toml`の基本方針:

```toml
target-version = "py311"
required-version = "==0.16.8"
extend-exclude = ["*.md"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]

[format]
line-ending = "lf"
```

`required-version`でローカルとCIのRuff version差を実行時にも拒否します。`line-ending = "lf"`でWindows / POSIX間の改行差分を作りません。

共通scriptからRuffを呼ぶときは、repository rootの`ruff.toml`を絶対pathで解決し、すべての`ruff check` / `ruff format`へ`--config <repository-root>/ruff.toml`を明示します。Ruffの「対象fileに最も近いconfigを使う」discoveryへ依存しません。将来、配下に`.ruff.toml` / `ruff.toml` / `[tool.ruff]`を持つ`pyproject.toml`が追加されても、共通script経由ではroot設定だけを適用します。

`*.md`をRuff側で除外するのは、Ruff 0.16系がMarkdown内のPython code blockもformatできるためです。Markdownの所有者はdprintへ一本化し、同一ファイルを2つのformatterが変更する状態を作りません。

初回導入では次を有効にしません。

- `ALL`
- `B`
- `UP`
- `SIM`
- docstring rule
- type checker
- `E501`

formatter / lint導入と直接関係しないリファクタリングや型付けまで変更範囲を広げないためです。追加ruleが必要なら、今回の導入後に実際の必要性を確認して別途追加します。

### dprint

Markdown / JSON / YAML / TOML / JavaScriptのformatにdprintを使用します。

dprint本体は`0.55.2`を固定します。remote Wasm pluginはversionだけでなくchecksumも固定し、実装時に`dprint add --checksum`で生成された設定をcommitします。checksum値を手入力しません。

ローカルとCIで同じdprint本体を使うため、`scripts/format_tracked.py`はdprintを使う処理の開始前に`dprint --version`を1回確認します。stdoutの末尾改行だけを除去した値が`dprint 0.55.2`と完全一致する場合だけ処理へ進み、それ以外はformat / checkを開始せず失敗します。`0.55.2`というversion tokenだけを曖昧に検索する実装にはしません。READMEのversion確認だけに依存しません。

また、すべてのdprint invocationでrepository rootの`dprint.json`を明示し、`--config-discovery=false`を併用します。配下の`dprint.json` / `dprint.jsonc`等を自動発見させず、共通script経由ではroot設定だけを使用します。

採用plugin:

- TypeScript / JavaScript: `0.96.1`
- JSON: `0.25.1`
- Markdown: `0.25.0`
- TOML: `0.8.0`
- Pretty YAML: `0.6.0`

Plan作成時に記載していたMarkdown `0.24.0`は、実装前確認時点のplugin registryで`0.25.0`がcurrentだったため更新します。ほかのpluginも実装開始時にregistryを再確認し、versionを変更する場合はPlanと設定を同時に更新します。

`dprint.json`は少なくとも次を対象にします。

```text
**/*.md
**/*.json
**/*.yml
**/*.yaml
**/*.toml
**/*.js
**/*.cjs
**/*.mjs
**/*.jsx
```

現在の目的はJavaScriptまでです。TypeScript / TSXは今回新規導入しないため`*.ts` / `*.tsx`を対象へ広げません。今回の実装でTypeScript fileを追加する設計にもせず、移植元の`feature-plan/scripts/validate-plan-output.ts`は移植しません。

原則としてディレクトリ単位の除外は設定しません。

したがって、次もformat対象です。

- `skills/**/evals/**/*.json`
- `docs/plans/**`
- `docs/history/**`
- `docs/reports/**`
- `skills/**/SKILL.md`
- `skills/**/references/**`
- `skills/**/assets/**`
- `.github/workflows/*.yml`

- `PLANS.md`

Markdownでは、日本語文書や評価入力の既存改行を必要以上に変えないため、`textWrap = "maintain"`を使用します。改行コードはfile種別ごとではなくglobalにLFへ統一し、incremental cacheへ結果を依存させません。

```json
{
  "newLineKind": "lf",
  "incremental": false,
  "markdown": {
    "textWrap": "maintain",
    "emphasisKind": "asterisks",
    "strongKind": "asterisks",
    "unorderedListKind": "dashes"
  }
}
```

formatter / lintの対象集合はformatter自身のdirectory discoveryではなく、Git tracked fileを正本にします。`.gitignore`、`.git/info/exclude`、global gitignoreの内容で対象が変わらないようにします。

### formatter / lint対象集合

対象列挙とtool呼び出しはPython 3.11標準ライブラリだけの`scripts/format_tracked.py`へ集約します。このscriptはformat ruleを持たず、次だけを担当します。

- repository rootで`git ls-files -z --`を実行してtracked pathを取得する
- Ruff対象を`.py`、dprint対象を`.md` / `.json` / `.yml` / `.yaml` / `.toml` / `.js` / `.cjs` / `.mjs` / `.jsx`へ絞る
- Ruffへtracked Python pathを明示argvとして渡し、repository rootの`ruff.toml`を`--config`で必ず指定する。Ruffは`force-exclude = false`のままにし、明示pathがgitignoreで落ちないことを利用する
- dprintを使う処理では最初に`dprint --version`のstdoutから末尾改行だけを除去し、`dprint 0.55.2`との完全一致を確認する。不一致なら対象fileへ触れる前に失敗する
- dprintへtracked pathをnewline区切りで渡し、repository rootの`dprint.json`を`--config`で指定し、`--config-discovery=false`を付けた`fmt --no-gitignore --stdin-files` / `check --no-gitignore --stdin-files`を使う。`.gitignore`、`.git/info/exclude`、`DPRINT_GLOBAL_GITIGNORE=1`時のglobal gitignoreを対象選定へ反映させず、nested dprint configも利用しない
- 同じroot config固定条件で`dprint file-paths --no-gitignore --stdin-files`の解決結果と期待するtracked対象を比較し、`dprint.json`のincludes / excludesやplugin association等で対象が静かに欠落した場合は失敗する
- shell展開や`xargs`へ依存せず、`subprocess.run(..., shell=False)`でtoolを起動する
- newlineを含むtracked pathは`--stdin-files`で安全に表現できないため明示エラーにする。現行repositoryには存在しない

標準入口は次で固定します。

```bash
python scripts/format_tracked.py ruff-check
python scripts/format_tracked.py import-fix
python scripts/format_tracked.py format
python scripts/format_tracked.py check
```

- `ruff-check`: tracked Pythonだけへread-onlyの`ruff check`
- `import-fix`: tracked Pythonだけへ`ruff check --select I --fix`
- `format`: tracked Pythonへ`ruff format`、tracked dprint対象へ`dprint fmt --no-gitignore --stdin-files`
- `check`: tracked Pythonへ`ruff check`＋`ruff format --check`、tracked dprint対象へ`dprint check --no-gitignore --stdin-files`

CIとREADMEの通常手順はこのscriptを使用し、`ruff check .` / `dprint check`等のdirectory discoveryを正規入口にしません。共通scriptがroot config固定とdprint本体version確認も担当するため、通常手順でformatterを直接起動しません。formatter configの対象patternはplugin associationの契約として維持しますが、対象ファイル集合の正本にはしません。

実装時に意味保持のため個別除外が本当に必要になった場合は、formatter設定だけで静かに除外せず、`scripts/format_tracked.py`の期待対象と理由も同じ変更で更新します。広いdirectory単位の除外は引き続き行いません。

### .gitattributes

Ruff / dprint側でLFを指定するだけでなく、Git checkout時のworking tree改行もformatter対象についてLFへ固定します。既存の`* text=auto`は維持し、次を追加します。

```gitattributes
*.py text eol=lf
*.md text eol=lf
*.json text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
*.toml text eol=lf
*.js text eol=lf
*.cjs text eol=lf
*.mjs text eol=lf
*.jsx text eol=lf
```

既存の`skills/*/scripts/runtime_contract.py text eol=lf`は`*.py text eol=lf`に包含されるため削除し、同じ契約を重複させません。

`.gitattributes`自体はRuff / dprintのformat対象ではなく手動管理します。format完了後に`git ls-files --eol`でformatter対象のindex / working treeがLFであることを確認します。

### `AGENTS.md`

root `AGENTS.md`は常時読み込まれるため、移植元の全文をコピーしません。次の毎回必要な契約だけを保持します。

- ユーザーの明示指示と作業範囲を最優先する
- Plan-only / review-only / investigation-onlyでは実装やGit mutationへ進まない
- 実装・設計前に関連Issue / PR / Plan / code / test / CIを必要な範囲で確認する
- QA Skillの仕様は`README.md`、`EVALS.md`、対象`skills/<name>/SKILL.md`を正本として扱う
- 既存runtime / validator / helperを確認してから新規抽象化を追加する
- default branchへの直接commit / push、force push、branch削除、merge、release等をユーザー指示なしに行わない
- file delete / rename / move等の破壊的変更は明示された対象範囲内だけで行う
- formatter / lint / relevant tests / CI contractを完了前に確認する
- 人間向けエンジニアリング文書は原則日本語で記述する
- Planは`PLANS.md`、reviewは`CODE_REVIEW.md`、安全Hook詳細は`docs/reference/codex-safety-harness.md`へ委譲する
- subagentは親Agentがscopeと完了判定を保持し、childから追加subagentを起動しない
- Codex 0.160.0のPreToolUseへ`exec_command.workdir`が渡らないため、state-changing Git commandはcommand内でcanonical repository rootへ安全に移動してからbare `git <subcommand>`を実行する。Git executable tokenはbare `git` / `git.exe`だけを許可候補とし、path付きGit、`command git ...`、`env ... git ...`等のwrapper経由はG10でdenyする。tool-level `workdir`、`git -C`、`--git-dir`、`--work-tree`等へ安全判定を依存しない

QA workflow固有の詳細アルゴリズムはroot `AGENTS.md`へ複製しません。

### `PLANS.md` / `CODE_REVIEW.md`

`PLANS.md`は現在の`docs/plans/`運用をCodex向けに定義します。Plan-only依頼ではPlan更新だけを行い、目的、現在状態、変更対象、既存実装との関係、実装順序、検証、完了条件、対象外を実装時に迷わない粒度で記載します。

`CODE_REVIEW.md`は、要求・Issue・Plan適合、正しさ、セキュリティ / データ保護、既存runtime / validator / Skill契約、回帰、test / CI、明確な性能問題を先に確認し、過剰設計は追加観点として扱います。review-onlyではコード変更を行わず、修正へ進む場合だけ`repair-loop`へ切り替えます。

### 開発用Agent Skills

`.agents/skills/`には次の3 Skillだけを導入します。

```text
.agents/skills/
├── feature-plan/
├── code-review/
└── repair-loop/
```

移植元のSkillはRun ArtifactやRepository mappingを前提にしているため、SKILL本文をそのままコピーしません。今回のリポジトリで保持・置換・削除する契約を先に固定します。

| Skill | 保持する契約 | qa-workflow-skillsで置換する契約 | 削除する移植元固有契約 |
| --- | --- | --- | --- |

### custom subagent

4 roleに限定します。

- `test_investigator`: 既存test、evaluation、CI failure、flaky候補、未カバー領域の調査専用。編集しないことを`developer_instructions`で要求する

### PreToolUse safety Hook

`qa-training-store`の`pre_tool_use_policy.mjs`はNode標準ライブラリだけを使用し、Scenario Shop固有依存を持たないためparserの大部分を再利用します。ただし移植元の全policyをそのまま正本にはせず、今回の承認モデルへ合わせて境界を変更します。

Hookのmatcherは`^Bash$`だけに限定します。`apply_patch` / `Edit` / `Write`用のpatch parserや、任意のMCP tool inputを解釈するgeneric parserは今回追加しません。file delete / rename / move等のpatch操作は`AGENTS.md`とParent / `implementation_worker`のscope契約で制御し、今回Hookで機械的に防止できるとは主張しません。

静的に判定できる禁止操作はexecpolicy `forbidden`を使い、Hookは次のように、現在branch、複合shell、repository contextなど実行時contextが必要な判定のguardrailを担当します。

- protected branch上のcommit / merge / rebase / cherry-pick / revert / pull / am / `reset`等のcontextual mutation。`reset`はmodeやpath-formを個別に許可せず、protected branch上ではfamily全体をdenyする
- protected branchまたはprotected local refへのpush / fetch / `update-ref` / branch rename・delete / worktree変更
- state-changing Git commandの直前に、canonical repository rootへの単一・絶対path・検証済みのcwd移動がない場合、またはそれ以外のcwd変更が先行する場合
- state-changing Git commandで`git -C`、`--git-dir`、`--work-tree`、`GIT_DIR`、`GIT_WORK_TREE`等のrepository context overrideを使用する場合
- 複数Git invocationやshell chainで安全なcontext判定ができないmutation
- inline commandを隠せるnested shell wrapper
- Hookが正常に起動した後のmalformed input

protected branchは実装者判断にしません。このrepositoryのcanonical default branchである`main`を必ず含め、移植元互換のfallbackとして`master`も含めます。さらに`refs/remotes/origin/HEAD`が解決できる場合は、そのbranch名もprotected集合へ追加します。今回のrepositoryでは`main`がdefault branchであり、複数remoteのdefault branchを汎用探索する仕組みは追加しません。

Codex 0.160.0では、実際の`exec_command`はtool-level `workdir`から実行cwdを決めますが、Bash `PreToolUse`の`tool_input`には`command`しか渡されません。そのためHook processのcwdやtool-level `workdir`をstate-changing Git operationの実行対象として信頼しません。

state-changing Git commandは、**同じshell command内でcanonical repository rootへ安全に移動した直後のbare `git` / `git.exe` + `<subcommand>`**だけを許可候補にします。POSIXでは概念的に`cd -- "<absolute-repository-root>" && git <subcommand> ...`、PowerShellでは`Set-Location -LiteralPath "<absolute-repository-root>" -ErrorAction Stop`の成功後にbare `git`または`git.exe` + `<subcommand> ...`を実行する形です。移動先はHook launcherが解決したこのprojectのcanonical Git rootと同じpathでなければなりません。

Hookは既存のcwd変更検出を全面的に緩めません。state-changing Git commandの直前にあるcwd変更について、次をすべて満たす場合だけ例外として認識します。

- cwd移動が1回だけである
- 移動先が絶対pathである
- canonical project rootと一致する
- 移動失敗時に後続Git commandへ進まない制御構造である
- cwd移動とGit mutationの間に別command、branch変更、Git environment変更がない
- Git invocation自体はbare `git <subcommand>`であり、`git -C`、`--git-dir`、`--work-tree`、`GIT_DIR`、`GIT_WORK_TREE`を使わない

これ以外のcwd変更後mutation、bare Git mutationだけの実行、相対pathへの移動、project root外への移動、複数回のcwd変更、repository context overrideはG10でdenyします。これによりhiddenなtool-level `workdir`が別repository / worktreeを指していても、実際のGit mutationはcommand自身でcanonical project rootへ固定されます。

この形式を採用する理由はexecpolicyとの整合です。Codex 0.160.0はshell compound commandをplain commandへ分解してexecpolicy評価し、`cd <root> && git rebase ...`のGit部分をbare `git rebase ...`として評価できます。一方、`git -C <root> rebase ...`ではprefix rule `["git", "rebase"]`へ一致しません。動的なrepository pathを含むrules生成は追加せず、実際に実行するGit argvとexecpolicyが評価するGit argvを同じbare subcommand契約へ揃えます。

read-only Git commandはcanonical rootへのcwd移動必須契約の対象外です。ただし上記で明示したread-only形式以外はstate-changingとして扱ってfail-closedします。特に`git add`、`git fetch`はstate-changing、`git remote`は引数なし / `-v` / `--verbose` / `get-url` / `show`だけread-onlyで、`add` / `remove` / `rename` / `set-url` / `set-head`等はstate-changingです。remote / foreign execution environmentでcanonical project rootを同一pathとして証明できないGit mutationも許可しません。

canonical rootへの移動後、current branchはそのcwdで`git branch --show-current`を使って取得します。detached HEAD、Git repository外、またはbranch contextを安全に解決できない状態でmutationが要求された場合はG10としてdenyします。`origin/HEAD`が解決できないことだけでは全操作を止めず、`main` / `master` fallbackを使用します。

G10は「protected branchへのpush」だけではありません。次を同じcontextual protectionとして保持します。

- protected branchへの直接push
- fetch / pullでprotected local refを書き換えるrefspec
- protected local refを対象にした`update-ref`
- protected branchのrename / delete
- `worktree add -B`等によるprotected branchのreset、または安全に判定できないforced worktree変更
- protected branch上のcommit / merge / rebase / cherry-pick / revert / pull / am / `reset`。`git reset --soft <commit>`、`git reset <commit>`、`git reset --merge <commit>`、`git reset --keep <commit>`を含め、protected branch上では`reset` family全体をdenyする
- repository / runtime Git context overrideを使って行うcontext-sensitive mutation
- canonical project rootへの検証済みcwd移動以外のbranch / cwd / environment変更後に同一shell command内で続けるcontext-sensitive mutation
- mutation対象やGit contextを安全に決定できない場合

nested shellについてはrecursiveなshell parserを新設しません。`bash` / `sh` / `zsh` / `dash` / `ksh`の`-c` / `-lc`、`pwsh` / `powershell`の`-Command` / `-EncodedCommand`、`cmd` / `cmd.exe`の`/c`、`Invoke-Expression`等、tool inputの内側へ別commandを隠せる実行形はPreToolUseでdenyし、必要なcommandをBash toolへ直接出し直させます。これにより既知のnested shell bypassをprefix ruleだけへ依存させません。

ただし、このrepository-local harnessを任意コード実行に対する完全なsecurity sandboxとは扱いません。例えば`python script.py`や外部MCP toolの内部処理まで意味解析して禁止操作を保証するものではありません。OS sandbox、ユーザー承認、外部tool側の権限制御が別の境界です。

| N1 | `git rm`と`rm` / `del` / `erase` / `Remove-Item` / `rmdir` / `unlink`等、family全体を不要と判断できるcommand-based deletionはexecpolicy `forbidden`で保持する |
| N2 | delete semanticsを持つrsync / robocopy / force move等はHookでdenyし、必要なcommand familyはexecpolicy `prompt`をfallbackにする。prefixで任意位置のdelete optionを完全表現できるとは扱わない |
| N3 | Terraformをこのrepositoryで利用しないため移植しない |
| N4 | download-to-shellはHookでcompound commandをdenyし、`curl` / `wget` / `Invoke-WebRequest` / `Invoke-RestMethod`等のnetwork command familyをexecpolicy `prompt`にする。pipeline末尾までをprefix ruleだけで永久禁止できるとは扱わない |
| A1〜A14 | Hook側のread-only / 通常feature branch / recovery commandのallow baselineとして保持する。execpolicyの`decision = "allow"`とは別であり、通常rebaseは上表の承認境界と矛盾しないよう更新する |
| A15〜A17 | Terraform / Kubernetes / PowerShell `Invoke-Expression`のallow例はこのrepositoryで必要性がないため移植しない |

contract testは、移植元matrixを別の手書き一覧へ複製せず、Hookがexportするcurrent matrixと追加のcontext fixtureを使ってdata-drivenに検証します。

Hookが正常に起動し、Codex schemaに適合する明示的denyまたはblocking exitを返した場合はtool callを止められます。一方、Hook launcher failure、timeout、unsupported / malformed response等ではHook failureとしてtool callが継続し得ます。このため`PreToolUse` Hookを絶対的なsecurity enforcement boundaryとは扱いません。execpolicyのprefix ruleでcommand family全体を安全に表現できる操作だけを`forbidden`へ置きます。危険性が後続optionや引数位置で決まる操作はHookでdenyし、対応するcommand familyのexecpolicy `prompt`をfallbackにして、Hook failure時も無承認では実行させません。

Windowsの`pre_tool_use_policy_windows.ps1`はstdin / stdout / stderr / Node exit codeをtransportするだけにし、安全policyを複製しません。

### compact後の指示再注入

`session_start_context.mjs`は`SessionStart(source=compact)`時だけroot `AGENTS.md`を`additionalContext`へ返します。`startup` / `resume` / `clear`では重複注入しません。

Hook本体が正常に起動した状態でroot解決、Hook input、`AGENTS.md`読込、structured output生成に失敗した場合は、明示的な停止結果を返します。ただしlauncher failureやtimeoutまで絶対的に停止できるとは扱いません。compact後の再注入は`AGENTS.md`の正本を補完する回復手段であり、唯一の安全境界にはしません。

### execpolicy rules

`.codex/rules/`は静的command policyの正本であり、Hookの代替ではなく相互補完です。

- `20-risky-prompt.rules`: merge、通常rebase、通常tag操作、local branch delete、通常のGitHub CLI remote mutationに加え、variant-dependent destructive operationのfallbackとして`git push` / `reset` / `commit` / `restore` / `checkout` / `switch` / `branch` / `tag` / `stash`、必要なnetwork / file-operation familyをfamily単位で`prompt`にする
- `30-destructive-forbidden.rules`: command family全体を禁止できる`gh api`、`gh repo sync`、`git clean`、`git rm`、`rm` / `del` / `erase` / `Remove-Item` / `rmdir` / `unlink`等だけを`forbidden`にする。後続option位置の意味解析が必要なforce push、hard reset、commit amend等をprefixだけで「永久禁止」とは定義しない

Git / GitHub CLIのexecpolicy ruleはWindowsとPOSIXで同じ判定になるよう、実行ファイルtokenをalternativesとして固定します。Git ruleは`["git", "git.exe"]`、GitHub CLI ruleは`["gh", "gh.exe"]`を先頭tokenの候補にし、`git.exe` / `gh.exe`だけ承認・禁止ruleを迂回できる状態を作りません。

通常のread-only commandやworkspace内の通常作業には明示的な`allow` ruleを置きません。Codex 0.160.0では、commandの全segmentが明示的な`allow` ruleへ一致するとsandbox bypassが有効になり得るためです。read-only commandはexecpolicy ruleへ一致させず、通常のsandbox経路で実行します。意図的にsandbox外実行を許可する要件が将来発生しない限り、`decision = "allow"`は追加しません。

branch deleteを`prompt`と`forbidden`の両方へ重複定義しません。`git push` family自体を`prompt`にし、canonical formの単一remote branch deleteもその承認経路へ含めます。`--prune` / `--mirror`、force push、delete refspec等はHookでdenyします。execpolicyのprefix matchingでは`git push origin main --force`のような任意位置optionを完全に`forbidden`へ分離できないためです。通常rebaseも`prompt`とし、protected branch上の禁止はHookの実行時context判定へ分離します。

PreToolUseで直接扱うnative Git subcommandは、現在のrepository運用と既存Hookが意味を判定できる次の集合へ固定します。`add`、`am`、`branch`、`check-ignore`、`checkout`、`cherry-pick`、`clean`、`commit`、`config`、`diff`、`fetch`、`log`、`ls-files`、`merge`、`pull`、`push`、`rebase`、`remote`、`reset`、`restore`、`revert`、`rev-parse`、`rm`、`show`、`stash`、`status`、`switch`、`tag`、`update-ref`、`worktree`だけを許可候補とします。この集合にない`git <subcommand>`は、Git alias / external subcommandを含めて内容を再帰解釈せずG10でdenyします。必要なnative subcommandが今後増えた場合は、用途とread-only / mutation semanticsを確認してallowlistとcontract testを同じ変更で更新します。

Git subcommandの状態変更判定はallowlistとは別に実装者判断へ残しません。常にread-onlyとして扱うのは`status`、`log`、`diff`、`show`、`rev-parse`、`ls-files`、`check-ignore`です。`branch`は一覧 / `--show-current`、`config`は既存のget / list系、`remote`は引数なし / `-v` / `--verbose` / `get-url` / `show`、`worktree`は`list`、`stash`は`list` / `show`、`tag`は一覧系だけをread-onlyとし、それ以外はstate-changingとして扱います。`add`、`fetch`を含む残りのallowlist内subcommandもstate-changingです。read-onlyと明示できない形式はstate-changingへ倒し、canonical repository root固定とcontext判定を必須にします。contract testではallowlist内の全subcommandがread-onlyまたはstate-changingのどちらかへ必ず分類され、未分類がないことを検証します。

GitHub CLIも汎用parserを追加せず、bare `gh` / `gh.exe`の`namespace + subcommand`を有限な分類表で扱います。repository-local harnessがread-onlyとして許可するのは、`--version` / `help` / `status` / `browse` / `auth status`と、`repo view|list|read-file|read-dir|gitignore|license`、`pr view|list|status|checks|diff`、`issue view|list|status`、`run view|list|watch|download`、`workflow view|list`、`release view|list|download`、`cache list`、`secret list`、`variable get|list`、`label list`、`search ...`です。これ以外のremote mutationを承認可能にする場合はexecpolicy `prompt`へ明示分類します。

今回サポートする`prompt`対象は、`pr create|edit|close|merge|ready|reopen|review`、`issue create|edit|close|delete|reopen`、`repo archive|unarchive|delete|edit|rename`、`repo autolink create|delete`、`repo deploy-key add|delete`、`release create|edit|delete|upload`、`workflow enable|disable|run`、`run cancel|delete|rerun`、`secret set|delete`、`variable set|delete`、`cache delete`、`label clone|create|edit|delete`とします。

`gh api`は任意の認証済みGitHub REST / GraphQL APIへ到達でき、refのforce update等の禁止操作まで表現できるため、このrepository-local harnessではfamily全体を`forbidden`とします。`gh repo sync`もsafe / `--force` variantをprefix ruleだけで完全分離できず、今回のrepository workflowで必須ではないためfamily全体を`forbidden`とします。HTTP method / endpoint / request bodyや任意位置flagを解析するgeneric GitHub API / CLI security parserは追加しません。

上記read-only / prompt / forbiddenのどれにも入らない`gh` commandは、現在存在するcommandも将来追加されるcommandもこのharnessではunsupportedとしてPreToolUseでdenyします。`gh alias`、`gh extension`、path付き`gh` / `gh.exe`、`command gh ...` / `env ... gh ...`等のwrapperもdenyします。新しい`gh`操作をサポートする場合はread-only / prompt / forbiddenのいずれかへ分類しcontract testを同じ変更で追加します。

Git mutationのexecpolicy ruleはbare `git` / `git.exe` + `<subcommand>` prefixを正本にします。state-changing Gitを実行するときはHook契約に従い、canonical project rootへの検証済みcwd移動とbare `git` / `git.exe` commandを同じshell command内で組み合わせます。`git -C <dynamic-path> ...`を実運用形式にはせず、repository pathごとのrules生成も行いません。これにより、実際に実行するGit subcommandと`prefix_rule([["git", "git.exe"], ...])`が同じargv形になります。

Codex 0.160.0のexecpolicyはordered prefix matchingであり、`match` / `not_match`はload時の検証例です。したがって`git push origin main --force`や`git reset HEAD --hard`のように危険flagが任意位置へ現れるcommandを、特定flagのprefix ruleだけで完全に`forbidden`へ分類できるとは扱いません。family全体を禁止できない場合はHookでvariantをdenyし、execpolicyではfamily単位`prompt`をfallbackとして使います。これによりHook failure時にも無承認実行を防ぎますが、ユーザー承認後まで機械的に禁止する保証とは区別します。

各`prompt` / `forbidden` ruleは、Codex execpolicyの`match` / `not_match`例に加え、sandbox approvalやHook由来の停止と区別できる短いrule固有`justification`を持たせます。`rules-auto-net`は追加しません。

CIでは固定版Codex CLIを使って`codex execpolicy check --rules ...`を実行し、少なくとも代表的な「rule未一致」 / `prompt` / `forbidden`をCodex自身のparser / evaluatorで確認します。variant-dependent familyではoption位置を前後へ変えたfixtureも評価し、Hook denyとfamily-level `prompt` fallbackの両方を確認します。独自execpolicy parserは作りません。

execpolicy prefix ruleだけでnested shellや任意script内部のcommandまで完全に捕捉できるとは扱いません。Bash tool inputに現れるopaqueなnested shell wrapperはPreToolUseでdenyし、外部MCPや任意program内部のmutationはrepository-local execpolicyの保証範囲外と明記します。

### Hook trust

`docs/reference/codex-safety-harness.md`には次を記載します。

- Codex 0.160.0のHook trust hashはnormalizedされたHook設定identityから計算され、参照先`.mjs` / `.ps1`のsource本文はhash対象ではない。`Trusted`表示をHook source未変更の証拠として扱わない
- `.codex/config.toml`等のHook定義を変更した場合はCodex interactive CLIで`/hooks`を再確認する
- Hook sourceを変更した場合は、既存trustが自動失効する前提を置かず、該当contract testとfresh trusted Codexでのruntime受入を再実行する
- Hookの定義元、command、matcher、timeout、trust状態を確認する
- 実行環境とtrust確認時の`CODEX_HOME`を一致させる
- contract test PASS、Hook sourceの変更確認、実Codex上のtrust / runtime確認は別の証拠として扱う
- Hook source digestをcommandへ埋め込む独自revision機構は追加しない。Hookは絶対的なsecurity boundaryではなく、永久禁止操作はexecpolicy `forbidden`でも防御する
- `--dangerously-bypass-hook-trust`を通常運用へ入れない

## 実装時の注意

初回の一括formatは変更file数が大きくなります。これは今回の目的上許容しますが、format変更と意味変更を混ぜません。

安全Hookはsecurity-sensitiveです。parser全体を書き直さず、移植元で検証済みのshell / Git解析を維持しながら、今回確定したapproval / execpolicy境界に必要な箇所だけ調整します。direct / compound commandは既存parserを維持し、nested shellは再帰解析せずopaque wrapper自体をdenyします。Codex 0.160.0ではPreToolUseへtool-level `workdir`が渡らないため、state-changing Git commandはcommand内でcanonical project rootへfail-closedに移動した直後のbare Git subcommandへ統一します。`git -C`等のrepository context overrideは使わず、Hook process cwdを実行対象repositoryの証拠にもしません。これによりG10のrepository固定とexecpolicyのbare Git prefixを同時に成立させます。protected branch解決とG10は上記契約を正本にします。execpolicy / HookはBash tool経路のguardrailであり、Hook failure、任意program内部、外部MCPまで絶対防止できるとは扱いません。変更したpolicy caseはcontract testを同時に更新します。

一方、移植元のハーネス全体を正しい前提として扱いません。現行Codex仕様で旧aliasや不要な運用になっている箇所は現在仕様へ合わせます。

`AGENTS.md`、Skill、referenceを増やすこと自体を目的にしません。同じ契約を複数文書へコピーせず、rootにはroutingと常時必要な規則、詳細は担当文書へ置きます。移植元SkillのRun Artifact / Repository mapping等も名前だけ消すのではなく、今回の保持 / 置換 / 削除表に従って意味契約を閉じます。

custom agentについては、Codex 0.160.0のrole overrideで実際に強制できる設定と、`developer_instructions`による行動契約を混同しません。実装者がchild TOMLの`sandbox_mode`や`agents.enabled`をsecurity boundaryと誤認しないようにします。
