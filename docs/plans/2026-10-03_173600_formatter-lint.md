# Formatter / Python lint / Codex開発ハーネス導入Plan

このPlanは、`qa-workflow-skills`の開発を安定させるために、formatter / Python lintと、`qa-training-store`で実運用しているCodex開発ハーネスのうち、このリポジトリで現在必要なものを同じ変更で導入する実装計画です。

段階分けはしません。`qa-training-store`の構成を丸ごとコピーするのではなく、現在の`qa-workflow-skills`の構成、Python中心のruntime、既存CI、既存のPlan / review運用、現在のCodex公式仕様に照らして、必要なものだけを移植します。

Formatter / lintはrepository-wideなコード・文書品質を維持し、Codexハーネスは開発Agentの指示、委譲、安全境界、検証を維持します。QA Skill本体のworkflow / runtime / artifact graphとは別責務として扱います。

## 目的

次を同時に満たします。

- PythonをRuffでformat / lintする
- Markdown / JSON / YAML / TOML / JavaScriptをdprintでformatする
- 評価fixture、過去Plan、history、reportを含め、formatter対応可能なtracked fileを原則すべてformatする
- format後も現在のSkill契約、runtime、deterministic / semantic / trigger評価、CI結果を変えない
- PR以降に未formatファイルが追加されないようGitHub Actionsでformat / lintを検査する
- root `AGENTS.md`でCodexの作業範囲、安全性、Plan / review / implementationの基本契約をrepository-localにする
- Plan、review、bounded repairの開発workflowを`.agents/skills/`へ移植する
- 調査専用、限定実装、テスト調査、品質ゲート実行をcustom subagentへ役割分離できるようにする
- execpolicy rulesで静的に判定できる永久禁止操作を拒否し、`PreToolUse` Hookで現在branch等の実行時contextが必要な危険操作をguardrailとして検査する
- granular approvalで、通常のfeature branch Git mutation、高影響操作の明示承認、永久禁止操作を分離する
- compact後に必要なroot `AGENTS.md`を再注入できるようにする
- WindowsとPOSIXの両方で安全Hookを利用できるようにする
- ハーネス自体のconfig / Hook / Windows launcherをCIで回帰検出する
- `qa-training-store`固有のNodeアプリ、Android、Agentic QA、Run Artifact、textlint、CI待機MCP等は持ち込まない
- QA Skill本体の19 Skill、artifact graph、evaluation contractをCodex開発ハーネスの都合で変更しない

formatやハーネス導入を理由に、QA workflowの責務、評価datasetの意味、runtime契約、validator契約、テストケースの内容を変更しません。

## 採用するツール

### Ruff

PythonのlintとformatにRuffを使用します。

実装時点ではRuff `0.16.8`を固定します。

理由:

- 現在のリポジトリはPython 3.11をCIの正本としている
- Ruff単体でlint、import sorting、Python formatを扱える
- Black + Flake8 + isortを個別導入する必要がない
- `ruff.toml`を利用でき、Python package管理を導入する必要がない

Ruff 0.16系では既定lint ruleが従来より大幅に増えているため、既定ruleへ依存しません。初回導入では現在の目的に必要なruleだけを明示します。

`ruff.toml`の基本方針:

```toml
target-version = "py311"
required-version = "==0.16.8"
extend-exclude = ["*.md"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]

[format]
line-ending = "lf"
```

`required-version`でローカルとCIのRuff version差を実行時にも拒否します。`line-ending = "lf"`でWindows / POSIX間の改行差分を作りません。

`*.md`をRuff側で除外するのは、Ruff 0.16系がMarkdown内のPython code blockもformatできるためです。Markdownの所有者はdprintへ一本化し、同一ファイルを2つのformatterが変更する状態を作りません。

初回導入では次を有効にしません。

- `ALL`
- `B`
- `UP`
- `SIM`
- docstring rule
- type checker
- `E501`

formatter / lint導入と直接関係しないリファクタリングや型付けまで変更範囲を広げないためです。追加ruleが必要なら、今回の導入後に実際の必要性を確認して別途追加します。

### dprint

Markdown / JSON / YAML / TOML / JavaScriptのformatにdprintを使用します。

dprint本体は`0.55.2`を固定します。remote Wasm pluginはversionだけでなくchecksumも固定し、実装時に`dprint add --checksum`で生成された設定をcommitします。checksum値を手入力しません。

採用plugin:

- TypeScript / JavaScript: `0.96.1`
- JSON: `0.25.1`
- Markdown: `0.25.0`
- TOML: `0.8.0`
- Pretty YAML: `0.6.0`

Plan作成時に記載していたMarkdown `0.24.0`は、実装前確認時点のplugin registryで`0.25.0`がcurrentだったため更新します。ほかのpluginも実装開始時にregistryを再確認し、versionを変更する場合はPlanと設定を同時に更新します。

`dprint.json`は少なくとも次を対象にします。

```text
**/*.md
**/*.json
**/*.yml
**/*.yaml
**/*.toml
**/*.js
**/*.cjs
**/*.mjs
**/*.jsx
```

現在の目的はJavaScriptまでです。TypeScript / TSXは今回新規導入しないため`*.ts` / `*.tsx`を対象へ広げません。今回の実装でTypeScript fileを追加する設計にもせず、移植元の`feature-plan/scripts/validate-plan-output.ts`は移植しません。

原則としてディレクトリ単位の除外は設定しません。

したがって、次もformat対象です。

- `skills/**/evals/**/cases/**`
- `skills/**/evals/**/*.json`
- `docs/plans/**`
- `docs/history/**`
- `docs/reports/**`
- `skills/**/SKILL.md`
- `skills/**/references/**`
- `skills/**/assets/**`
- `.github/workflows/*.yml`
- `AGENTS.md`
- `PLANS.md`
- `CODE_REVIEW.md`
- `.agents/skills/**`
- `.codex/**/*.toml`
- `.codex/**/*.mjs`

Markdownでは、日本語文書や評価入力の既存改行を必要以上に変えないため、`textWrap = "maintain"`を使用します。改行コードはfile種別ごとではなくglobalにLFへ統一し、incremental cacheへ結果を依存させません。

```json
{
  "newLineKind": "lf",
  "incremental": false,
  "markdown": {
    "textWrap": "maintain",
    "emphasisKind": "asterisks",
    "strongKind": "asterisks",
    "unorderedListKind": "dashes"
  }
}
```

dprintは`.gitignore`を尊重した通常のfile discoveryを使用します。今回の対象はtracked fileなので、`--no-gitignore`を標準手順にはしません。

### `AGENTS.md`

root `AGENTS.md`は常時読み込まれるため、移植元の全文をコピーしません。次の毎回必要な契約だけを保持します。

- ユーザーの明示指示と作業範囲を最優先する
- Plan-only / review-only / investigation-onlyでは実装やGit mutationへ進まない
- 実装・設計前に関連Issue / PR / Plan / code / test / CIを必要な範囲で確認する
- QA Skillの仕様は`README.md`、`EVALS.md`、対象`skills/<name>/SKILL.md`を正本として扱う
- 既存runtime / validator / helperを確認してから新規抽象化を追加する
- default branchへの直接commit / push、force push、branch削除、merge、release等をユーザー指示なしに行わない
- file delete / rename / move等の破壊的変更は明示された対象範囲内だけで行う
- formatter / lint / relevant tests / CI contractを完了前に確認する
- 人間向けエンジニアリング文書は原則日本語で記述する
- Planは`PLANS.md`、reviewは`CODE_REVIEW.md`、安全Hook詳細は`docs/reference/codex-safety-harness.md`へ委譲する
- subagentは親Agentがscopeと完了判定を保持し、childから追加subagentを起動しない

QA workflow固有の詳細アルゴリズムはroot `AGENTS.md`へ複製しません。

### `PLANS.md` / `CODE_REVIEW.md`

`PLANS.md`は現在の`docs/plans/`運用をCodex向けに定義します。Plan-only依頼ではPlan更新だけを行い、目的、現在状態、変更対象、既存実装との関係、実装順序、検証、完了条件、対象外を実装時に迷わない粒度で記載します。

`CODE_REVIEW.md`は、要求・Issue・Plan適合、正しさ、セキュリティ / データ保護、既存runtime / validator / Skill契約、回帰、test / CI、明確な性能問題を先に確認し、過剰設計は追加観点として扱います。review-onlyではコード変更を行わず、修正へ進む場合だけ`repair-loop`へ切り替えます。

### 開発用Agent Skills

`.agents/skills/`には次の3 Skillだけを導入します。

```text
.agents/skills/
├── feature-plan/
├── code-review/
└── repair-loop/
```

移植元のSkillはRun ArtifactやRepository mappingを前提にしているため、SKILL本文をそのままコピーしません。今回のリポジトリで保持・置換・削除する契約を先に固定します。

| Skill | 保持する契約 | qa-workflow-skillsで置換する契約 | 削除する移植元固有契約 |
| --- | --- | --- | --- |
| `feature-plan` | Plan-onlyでは実装しない、実装前のrepository調査、前提 / 対象外 / リスク / 検証 / 完了条件を明示する | Repository mappingと保存規約は`PLANS.md`、保存先は既存`docs/plans/`へ置換する | active Run、Run Artifact lifecycle、移植元固有のreport保存契約 |
| `code-review` | 根拠に基づくfinding、影響に比例したseverity、review-onlyでは修正しない | repositoryのreview契約は`CODE_REVIEW.md`を正本とし、永続reportはユーザーが明示的に要求した場合だけ作成する | active Run、移植元固有のreport artifact、自動的な外部review実行契約 |
| `repair-loop` | boundedなReview → Repair → Validate、findingの仕分け、変更範囲制限、`needs_human`を含む停止条件 | 入力は実際のreview finding / test / CI failureとParent指定scope、反復結果はParentへ返し、Git diff / Plan / PR / CIをrepository上の証拠として扱う | Repository mapping、Run Artifactへのappend、移植元のFailure Taxonomy file、sanitization command、report artifact |

各Skillは、上表で残した意味契約だけを`SKILL.md`と必要な`references/`へ反映します。`feature-plan`のplan templateは、今回の`PLANS.md`と矛盾しない内容に調整したうえで保持します。

移植元には3 Skillのtrigger eval、`feature-plan` / `code-review`のsemantic output eval、`feature-plan/scripts/validate-plan-output.ts`があります。ただしdatasetは`pnpm`、`scripts/codex-task.ps1`、`harness-improvement`等の移植元固有契約を含み、移植先には同じeval runnerもありません。これらを動かすためだけにTypeScript / Node package管理や新しいLLM eval基盤を追加しません。

代わりに、今回導入するSkill契約そのものを次で検証します。

- `tests/codex/test_development_skills.py`で3 Skillのfrontmatter、必須reference、Plan / review / repairの責務境界、移植元固有のRun Artifact依存が残っていないことをstdlibだけで検証する
- fresh Codex sessionで代表的なpositive / negative依頼を実行し、`feature-plan`はPlan依頼、`code-review`はreview-only依頼、`repair-loop`は明示されたfinding / validation failureの修正依頼で選択されることを確認する
- negative側では、単純な直接修正を`feature-plan`へ強制しない、review-onlyで修正へ進まない、repair対象がないのに`repair-loop`を起動しないことを確認する

継続的なLLM trigger / semantic eval基盤が必要になった場合は、実際の必要性を確認して別変更で導入します。

### `.codex/config.toml`

project-local configは現行Codex schemaへ合わせます。通常のfeature branch作業、高影響操作の承認、永久禁止操作を同じ`never`へ押し込めず、granular approvalで分離します。

```toml
sandbox_mode = "workspace-write"
approval_policy = { granular = { sandbox_approval = true, rules = true, mcp_elicitations = false, request_permissions = false, skill_approval = false } }
approvals_reviewer = "user"
allow_login_shell = false

[sandbox_workspace_write]
network_access = true
writable_roots = []

[shell_environment_policy]
inherit = "core"

[features]
hooks = true
multi_agent = true

[agents]
max_concurrent_threads_per_session = 3

[agents.code_researcher]
description = "Read-only investigation of code, contracts, dependencies, tests, and CI before implementation."
config_file = "agents/code_researcher.toml"

[agents.implementation_worker]
description = "Scoped implementation of Parent-approved changes without Git mutation, deletion, rename, or scope expansion."
config_file = "agents/implementation_worker.toml"

[agents.test_investigator]
description = "Read-only investigation of tests, evaluations, CI failures, flaky candidates, and missing coverage."
config_file = "agents/test_investigator.toml"

[agents.quality_gate_runner]
description = "Validation-only execution of Parent-specified commands without source edits, dependency installation, or Git mutation."
config_file = "agents/quality_gate_runner.toml"
```

移植元の旧alias `max_threads`は使いません。repository configでは特定のmodel名やreasoning effortを固定しません。モデル世代変更やユーザー側設定と不要に競合させないためです。

承認境界は次で固定します。

| 操作 | 期待する扱い |
| --- | --- |
| read-only command、通常のworkspace内source変更 | sandboxとParent scopeの範囲で実行し、execpolicyのprompt対象にはしない |
| `.git`、`.agents`、`.codex`等、sandboxが保護するpathへの必要な書込み | `sandbox_approval = true`でユーザー承認経路を持つ |
| feature branchの通常`git add` / `git commit` / `git push` | Hook / rulesで一律denyしない。sandbox承認が必要な場合はユーザーへ要求する |
| merge、通常rebase、通常tag操作、local / remote branch delete、`gh pr merge` / `gh pr close`、`gh issue close`、release操作 | execpolicyの`prompt`とし、`rules = true`でユーザー承認を表面化する。ただしprotected branch等のcontextual guardに違反する場合はHook側でdenyする |
| force push、hard reset、destructive clean、commit amend、force restore / checkout、force branch / tag rewrite、stash drop / clear、command-based deletion、download-to-shell | execpolicyの`forbidden`を主防御にして承認では突破できない |

`approvals_reviewer = "user"`を明示し、granular approvalを自動reviewへ委譲しません。`mcp_elicitations`、`request_permissions`、`skill_approval`は今回のrepository-local harnessで承認経路を増やす目的がないためfalseにします。将来必要になった場合はその利用経路を確認して別途変更します。

custom agentのRole名・選択ガイダンスは親`.codex/config.toml`の`[agents.<name>]`と`description`を正本とします。Codex 0.160.0では、親configの`config_file`から読み込んだrole fileに対してrole名がhintとして渡され、child file側の`name` / `description`は必須ではありません。この宣言方式を維持し、移植元のトップレベル`name` / `description`をchild fileへ重複コピーしません。

子`.codex/agents/*.toml`は`developer_instructions`と、Codex 0.160.0で実際にrole overrideとして適用される設定だけを持たせます。`sandbox_mode`や`[agents] enabled = false`をchild fileへ書いてsecurity boundaryとして扱いません。0.160.0のrole適用処理はこれらをchild overrideへ反映しないためです。

### custom subagent

4 roleに限定します。

- `code_researcher`: code / contract / dependency / test / CIの調査専用。編集しないことを`developer_instructions`で要求する
- `implementation_worker`: 親Agent指定のfile / scopeだけを変更する。不要なrefactor、delete / rename / move、Git mutation、追加subagentを行わないことを`developer_instructions`で要求する
- `test_investigator`: 既存test、evaluation、CI failure、flaky候補、未カバー領域の調査専用。編集しないことを`developer_instructions`で要求する
- `quality_gate_runner`: 親Agent指定のvalidationだけを実行し、formatter write、source変更、dependency install、Git mutationを行わないことを`developer_instructions`で要求する

Codex 0.160.0では、custom roleから`sandbox_mode`や`agents.enabled`をchild固有の強制設定として適用できません。そのため上記のread-only、Git mutation禁止、再委譲禁止は**Roleの行動契約**であり、security boundaryとは扱いません。

機械的な安全境界はParent session側のsandbox、execpolicy、PreToolUse Hookが担当します。Parentはchildへ対象file・scope・禁止事項を明示し、完了判定を保持します。childから追加subagentを起動しないことも`developer_instructions`で要求しますが、`[agents] enabled = false`や`agents.max_depth`で保証できるとは記載しません。`max_depth`はMulti-agent V2では無視されるため追加しません。

今回、childごとのhard permission boundaryを新設するwrapperや別sandboxは追加しません。今回の目的は役割分離と誤操作抑止であり、Parentとchildで別のsecurity principalを構築することではありません。

### PreToolUse safety Hook

`qa-training-store`の`pre_tool_use_policy.mjs`はNode標準ライブラリだけを使用し、Scenario Shop固有依存を持たないためparserの大部分を再利用します。ただし移植元の全policyをそのまま正本にはせず、今回の承認モデルへ合わせて境界を変更します。

Hookのmatcherは`Bash`だけに限定します。`apply_patch` / `Edit` / `Write`用のpatch parserは今回追加しません。file delete / rename / move等のpatch操作は`AGENTS.md`とParent / `implementation_worker`のscope契約で制御し、今回Hookで機械的に防止できるとは主張しません。

静的に判定できる永久禁止操作はexecpolicy `forbidden`を主防御にします。Hookは次のように、現在branch、remote、複合shell、repository contextなど実行時contextが必要な判定のguardrailを担当します。

- protected branch上のcommit / merge / rebase等のcontextual mutation
- protected branchへ向けたpush
- `git -C`、`--git-dir`、`--work-tree`等のrepository context変更
- 複数Git invocationやshell chainで安全なcontext判定ができないmutation
- Hookが正常に起動した後のmalformed input

移植元Hookのpolicy matrixは、今回の承認モデルに合わせて次のように扱います。

| 移植元ID | 今回の扱い |
| --- | --- |
| G1 | hard resetは永久禁止として保持する |
| G2 | 通常rebaseの一律Hook denyは外し、feature branchではexecpolicy `prompt`へ移す。protected branch上のrebaseはcontextual Hook denyとする |
| G3 | commit amendは永久禁止として保持する |
| G4 | destructive cleanは永久禁止として保持する |
| G5 | destructive / force restore・checkout・switchは永久禁止として保持する。通常のfeature branch switchまで一律禁止しない |
| G6 | stash drop / clearは永久禁止として保持する |
| G7 | force pushは永久禁止として保持する |
| G8 | remote branch deleteの一律Hook denyは外し、execpolicy `prompt`へ移す |
| G9 | local branch deleteはexecpolicy `prompt`へ移す。force branch rename / copyとforce tag rewriteは永久禁止として保持する |
| G10 | protected branchへ向けたpushをcontextual Hook denyとして保持する |
| N1 | command-based deletionを永久禁止として保持する |
| N2 | delete semanticsを持つrsync / force move等を永久禁止として保持する |
| N3 | Terraformをこのrepositoryで利用しないため移植しない |
| N4 | download-to-shellを永久禁止として保持する |
| A1〜A14 | repositoryで意味のあるread-only / 通常feature branch / recovery commandのallow baselineとして保持する。ただし上表のrebase承認境界と矛盾しないよう更新する |
| A15〜A17 | Terraform / Kubernetes / PowerShell `Invoke-Expression`のallow例はこのrepositoryで必要性がないため移植しない |

contract testは、移植元matrixを別の手書き一覧へ複製せず、Hookがexportするcurrent matrixと追加のcontext fixtureを使ってdata-drivenに検証します。

Hookが正常に起動し、Codex schemaに適合する明示的denyまたはblocking exitを返した場合はtool callを止められます。一方、Hook launcher failure、timeout、unsupported / malformed response等ではHook failureとしてtool callが継続し得ます。このため`PreToolUse` Hookを絶対的なsecurity enforcement boundaryとは扱いません。永久禁止操作は可能な限りexecpolicy `forbidden`へ置き、Hookはcontext-dependent guardrailとして`AGENTS.md`、sandbox、rulesを補完します。

Windowsの`pre_tool_use_policy_windows.ps1`はstdin / stdout / stderr / Node exit codeをtransportするだけにし、安全policyを複製しません。

### compact後の指示再注入

`session_start_context.mjs`は`SessionStart(source=compact)`時だけroot `AGENTS.md`を`additionalContext`へ返します。`startup` / `resume` / `clear`では重複注入しません。

Hook本体が正常に起動した状態でroot解決、Hook input、`AGENTS.md`読込、structured output生成に失敗した場合は、明示的な停止結果を返します。ただしlauncher failureやtimeoutまで絶対的に停止できるとは扱いません。compact後の再注入は`AGENTS.md`の正本を補完する回復手段であり、唯一の安全境界にはしません。

### execpolicy rules

`.codex/rules/`は静的command policyの正本であり、Hookの代替ではなく相互補完です。

- `20-risky-prompt.rules`: merge、通常rebase、通常tag操作、local / remote branch delete、`gh pr merge` / `gh pr close`、`gh issue close`、release操作等
- `30-destructive-forbidden.rules`: force push、hard reset、destructive clean、commit amend、force restore / checkout、force branch / tag rewrite、stash drop / clear、command-based deletion、download-to-shell等

通常のread-only commandやworkspace内の通常作業には明示的な`allow` ruleを置きません。Codex 0.160.0では、commandの全segmentが明示的な`allow` ruleへ一致するとsandbox bypassが有効になり得るためです。read-only commandはexecpolicy ruleへ一致させず、通常のsandbox経路で実行します。意図的にsandbox外実行を許可する要件が将来発生しない限り、`decision = "allow"`は追加しません。

branch deleteを`prompt`と`forbidden`の両方へ重複定義しません。通常rebaseも`prompt`とし、protected branch上の禁止はHookの実行時context判定へ分離します。

各`prompt` / `forbidden` ruleは、Codex execpolicyの`match` / `not_match`例に加え、sandbox approvalやHook由来の停止と区別できる短いrule固有`justification`を持たせます。`rules-auto-net`は追加しません。

CIでは固定版Codex CLIを使って`codex execpolicy check --rules ...`を実行し、少なくとも代表的な「rule未一致」 / `prompt` / `forbidden`をCodex自身のparser / evaluatorで確認します。独自execpolicy parserは作りません。

### Hook trust

`docs/reference/codex-safety-harness.md`には次を記載します。

- `.codex/config.toml`のHook定義を変更したときだけ再確認する
- Codex interactive CLIで`/hooks`を実行する
- Hookの定義元、command、matcher、timeout、trust状態を確認する
- 実行環境とtrust確認時の`CODEX_HOME`を一致させる
- contract test PASSと実Codex上のtrust / runtime確認は別の証拠として扱う
- `--dangerously-bypass-hook-trust`を通常運用へ入れない

### ハーネスのログ

`log_event.mjs`は移植せず、ユーザーprompt本文、tool input preview、session transcript等をrepository配下へ独自複製しません。必要な開発証跡はGit diff、Plan、PR、CI、テスト結果で確認します。

execpolicy rulesは固定版Codex CLI自身で検証します。

- `git status --short`等のread-only代表commandが明示ruleへ一致しない
- merge / rebase / branch delete等の高影響代表commandが`prompt`
- force push / hard reset / destructive clean / command-based deletion等が`forbidden`
- `prompt` / `forbidden` ruleがrule固有`justification`を持つ
- `match` / `not_match`例を持つruleがload時検証をPASSする

実Codexでの受入確認では、fresh trusted sessionを`--strict-config`で起動し、config schema errorがないことを確認します。その後`/hooks`でHook定義元、command、matcher、timeout、trust状態を確認します。

`execpolicy check --rules ...`とは別に、同じtrusted projectの通常shell実行経路でproject-local `.codex/rules/`のdiscoveryも確認します。破壊的操作そのものは実行せず、次の安全なprobeを使います。

- read-only: `git status --short`を実行し、rule approvalなしで通常sandbox経路を通ることを確認する
- prompt: `git rebase --help`等、実行されてもmutationしない形を使い、rule固有`justification`を含む承認要求が出ることを確認して承認せず終了する
- forbidden: `git reset --hard --help`等、実行されてもmutationしない形を使い、rule固有`justification`を伴って実行前に拒否されることを確認する

probe commandは実装時に対象ruleのpatternとGitの実際の引数解釈を確認し、ruleが効かなかった場合にもrepository stateを変更しないものだけを採用します。sandbox approvalやHook denyだけを観測してexecpolicy discovery成功とは判定しません。

## 実装時の注意

初回の一括formatは変更file数が大きくなります。これは今回の目的上許容しますが、format変更と意味変更を混ぜません。

安全Hookはsecurity-sensitiveです。parser全体を書き直さず、移植元で検証済みのshell / Git解析を維持しながら、今回確定したapproval / execpolicy境界に必要な箇所だけ調整します。静的な永久禁止はexecpolicyを主防御、branch等の実行時context判定はHookのguardrailとし、Hook failure時まで絶対防止できるとは扱いません。変更したpolicy caseはcontract testを同時に更新します。

一方、移植元のハーネス全体を正しい前提として扱いません。現行Codex仕様で旧aliasや不要な運用になっている箇所は現在仕様へ合わせます。

`AGENTS.md`、Skill、referenceを増やすこと自体を目的にしません。同じ契約を複数文書へコピーせず、rootにはroutingと常時必要な規則、詳細は担当文書へ置きます。移植元SkillのRun Artifact / Repository mapping等も名前だけ消すのではなく、今回の保持 / 置換 / 削除表に従って意味契約を閉じます。

custom agentについては、Codex 0.160.0のrole overrideで実際に強制できる設定と、`developer_instructions`による行動契約を混同しません。実装者がchild TOMLの`sandbox_mode`や`agents.enabled`をsecurity boundaryと誤認しないようにします。

QA Skill本体の`skills/**`と開発Agent用`.agents/skills/**`は別責務です。開発SkillをQA workflowの19 Skillへ追加せず、既存Skill countや評価datasetを変更しません。

lintで実コード修正が必要になった場合は、可能ならformatの機械的差分と分けて確認できる状態にします。特に`F`系の指摘を直す際は、unused importに副作用がないこと、public importとして使われていないことを確認してから削除します。

Markdown / JSON / YAMLのformatは、見た目の統一より既存契約の維持を優先します。全件formatできる場合は全件を対象とし、問題がある箇所だけ最小限の例外にします。
