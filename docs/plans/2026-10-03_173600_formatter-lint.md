# Formatter / Python lint / Codex開発ハーネス導入Plan

このPlanは、`qa-workflow-skills`の開発を安定させるために、formatter / Python lintと、`qa-training-store`で実運用しているCodex開発ハーネスのうち、このリポジトリで現在必要なものを同じ変更で導入する実装計画です。

段階分けはしません。`qa-training-store`の構成を丸ごとコピーするのではなく、現在の`qa-workflow-skills`の構成、Python中心のruntime、既存CI、既存のPlan / review運用、現在のCodex公式仕様に照らして、必要なものだけを移植します。

Formatter / lintはrepository-wideなコード・文書品質を維持し、Codexハーネスは開発Agentの指示、委譲、安全境界、検証を維持します。QA Skill本体のworkflow / runtime / artifact graphとは別責務として扱います。

## 目的

次を同時に満たします。

- PythonをRuffでformat / lintする
- Markdown / JSON / YAML / TOML / JavaScriptをdprintでformatする
- 評価fixture、過去Plan、history、reportを含め、formatter対応可能なtracked fileを原則すべてformatする
- format後も現在のSkill契約、runtime、deterministic / semantic / trigger評価、CI結果を変えない
- PR以降に未formatファイルが追加されないようGitHub Actionsでformat / lintを検査する
- root `AGENTS.md`でCodexの作業範囲、安全性、Plan / review / implementationの基本契約をrepository-localにする
- Plan、review、bounded repairの開発workflowを`.agents/skills/`へ移植する
- read-only調査、限定実装、テスト調査、品質ゲート実行をcustom subagentへ分離できるようにする
- `PreToolUse` Hookとexecpolicy rulesでforce push、破壊的Git操作、default branch上の危険なmutation等を機械的に防ぐ
- compact後に必要なroot `AGENTS.md`を再注入できるようにする
- WindowsとPOSIXの両方で安全Hookを利用できるようにする
- ハーネス自体のconfig / Hook / Windows launcherをCIで回帰検出する
- `qa-training-store`固有のNodeアプリ、Android、Agentic QA、Run Artifact、textlint、CI待機MCP等は持ち込まない
- QA Skill本体の19 Skill、artifact graph、evaluation contractをCodex開発ハーネスの都合で変更しない

formatやハーネス導入を理由に、QA workflowの責務、評価datasetの意味、runtime契約、validator契約、テストケースの内容を変更しません。

## 採用するツール

### Ruff

PythonのlintとformatにRuffを使用します。

実装時点ではRuff `0.16.8`を固定します。

理由:

- 現在のリポジトリはPython 3.11をCIの正本としている
- Ruff単体でlint、import sorting、Python formatを扱える
- Black + Flake8 + isortを個別導入する必要がない
- `ruff.toml`を利用でき、Python package管理を導入する必要がない

Ruff 0.16系では既定lint ruleが従来より大幅に増えているため、既定ruleへ依存しません。初回導入では現在の目的に必要なruleだけを明示します。

`ruff.toml`の基本方針:

```toml
target-version = "py311"
extend-exclude = ["*.md"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]
```

`*.md`をRuff側で除外するのは、Ruff 0.16系がMarkdown内のPython code blockもformatできるためです。Markdownの所有者はdprintへ一本化し、同一ファイルを2つのformatterが変更する状態を作りません。

初回導入では次を有効にしません。

- `ALL`
- `B`
- `UP`
- `SIM`
- docstring rule
- type checker
- `E501`

formatter / lint導入と直接関係しないリファクタリングや型付けまで変更範囲を広げないためです。追加ruleが必要なら、今回の導入後に実際の必要性を確認して別途追加します。

### dprint

Markdown / JSON / YAML / TOML / JavaScriptのformatにdprintを使用します。

実装時点ではdprint `0.55.2`を固定します。

pluginは実装時点の次のversionを固定し、可能なものはchecksumも設定します。

- TypeScript / JavaScript: `0.96.1`
- JSON: `0.25.1`
- Markdown: `0.24.0`
- TOML: `0.8.0`
- Pretty YAML: `0.6.0`

`dprint.json`は少なくとも次を対象にします。

```text
**/*.md
**/*.json
**/*.yml
**/*.yaml
**/*.toml
**/*.mjs
```

原則としてディレクトリ単位の除外は設定しません。

したがって、次もformat対象です。

- `skills/**/evals/**/cases/**`
- `skills/**/evals/**/*.json`
- `docs/plans/**`
- `docs/history/**`
- `docs/reports/**`
- `skills/**/SKILL.md`
- `skills/**/references/**`
- `skills/**/assets/**`
- `.github/workflows/*.yml`
- `AGENTS.md`
- `PLANS.md`
- `CODE_REVIEW.md`
- `.agents/skills/**`
- `.codex/**/*.toml`
- `.codex/**/*.mjs`

Markdownでは、日本語文書や評価入力の既存改行を必要以上に変えないため、`textWrap = "maintain"`を使用します。

既存Markdownの記法に合わせ、少なくとも次を固定します。

```json
{
  "markdown": {
    "textWrap": "maintain",
    "emphasisKind": "asterisks",
    "strongKind": "asterisks",
    "newLineKind": "lf",
    "unorderedListKind": "dashes"
  }
}
```

dprintは`.gitignore`を尊重した通常のfile discoveryを使用します。今回の対象はtracked fileなので、`--no-gitignore`を標準手順にはしません。

全件確認を毎回再現できるよう、incremental formattingには依存しません。設定または実行引数で全対象を確認する状態にします。

### `AGENTS.md`

root `AGENTS.md`は常時読み込まれるため、移植元の全文をコピーしません。次の毎回必要な契約だけを保持します。

- ユーザーの明示指示と作業範囲を最優先する
- Plan-only / review-only / investigation-onlyでは実装やGit mutationへ進まない
- 実装・設計前に関連Issue / PR / Plan / code / test / CIを必要な範囲で確認する
- QA Skillの仕様は`README.md`、`EVALS.md`、対象`skills/<name>/SKILL.md`を正本として扱う
- 既存runtime / validator / helperを確認してから新規抽象化を追加する
- default branchへの直接commit / push、force push、branch削除、merge、release等をユーザー指示なしに行わない
- file delete / rename / move等の破壊的変更は明示された対象範囲内だけで行う
- formatter / lint / relevant tests / CI contractを完了前に確認する
- 人間向けエンジニアリング文書は原則日本語で記述する
- Planは`PLANS.md`、reviewは`CODE_REVIEW.md`、安全Hook詳細は`docs/reference/codex-safety-harness.md`へ委譲する
- subagentは親Agentがscopeと完了判定を保持し、childから追加subagentを起動しない

QA workflow固有の詳細アルゴリズムはroot `AGENTS.md`へ複製しません。

### `PLANS.md` / `CODE_REVIEW.md`

`PLANS.md`は現在の`docs/plans/`運用をCodex向けに定義します。Plan-only依頼ではPlan更新だけを行い、目的、現在状態、変更対象、既存実装との関係、実装順序、検証、完了条件、対象外を実装時に迷わない粒度で記載します。

`CODE_REVIEW.md`は、要求・Issue・Plan適合、正しさ、セキュリティ / データ保護、既存runtime / validator / Skill契約、回帰、test / CI、明確な性能問題を先に確認し、過剰設計は追加観点として扱います。review-onlyではコード変更を行わず、修正へ進む場合だけ`repair-loop`へ切り替えます。

移植元からSKILL本文、実際に参照される`references/`、`feature-plan`のplan template等の必要assetだけを持ち込みます。`.agents/skills/**/evals`は、移植先に開発用Skill eval runnerがなく実行されないため追加しません。

project-local configは現行Codex schemaへ合わせます。


移植元の旧alias `max_threads`は使いません。repository configでは特定のmodel名やreasoning effortを固定しません。モデル世代変更やユーザー側設定と不要に競合させないためです。

custom agentは現行仕様の`agents.<name>.config_file`で明示宣言します。`mcp_servers.ci_wait`は追加しません。

### custom subagent

4 roleに限定します。

- `code_researcher`: read-onlyでcode / contract / dependency / test / CIを調査する。`implementation_researcher`の重複責務を統合する
- `implementation_worker`: 親Agent指定のfile / scopeだけを変更する。不要なrefactor、delete / rename / move、Git mutation、追加subagentを禁止する
- `test_investigator`: read-onlyで既存test、evaluation、CI failure、flaky候補、未カバー領域を調査する
- `quality_gate_runner`: 親Agent指定のvalidationだけを実行し、formatter write、source変更、dependency install、Git mutationを行わない

`quality_gate_runner`は通常のcache / test生成物が必要なため、必要なら`workspace-write`を維持します。

### PreToolUse safety Hook

`qa-training-store`の`pre_tool_use_policy.mjs`はNode標準ライブラリだけを使用し、Scenario Shop固有依存を持たないことを確認済みです。security-sensitiveなcommand parserなので、Pythonへ書き直さず既存ロジックを可能な限り維持します。

少なくとも次の契約を維持します。

- malformed Hook inputのfail-close
- force push禁止
- hard reset / destructive clean等の破壊操作禁止
- branch / tagの強制変更禁止
- command-based deletion禁止
- default branch上の保護対象mutationの防止
- repository contextを変更するGit optionの検査
- shell chain内で安全に判定できないcontext-sensitive mutationのfail-close
- safeなread-only commandや通常のfeature branch作業をblanket denyしない

Windowsの`pre_tool_use_policy_windows.ps1`はstdin / stdout / stderr / Node exit codeをtransportするだけにし、安全policyを複製しません。

### compact後の指示再注入

`session_start_context.mjs`は`SessionStart(source=compact)`時だけroot `AGENTS.md`を`additionalContext`へ返します。`startup` / `resume` / `clear`では重複注入しません。

root解決、Hook input、`AGENTS.md`読込、structured output生成に失敗した場合は、必須指示を欠いたまま継続しないfail-close契約を維持します。

### execpolicy rules

`.codex/rules/`はHookの代替ではなくdefense-in-depthです。

- `10-readonly-allow.rules`: `git status`、`git diff`、`git log`、`git show`、`rg`等のread-only command
- `20-risky-prompt.rules`: merge / rebase / tag、branch delete、`gh pr merge` / `gh pr close`、`gh issue close`、release操作等
- `30-destructive-forbidden.rules`: force push、hard reset、destructive clean、force branch / tag、stash drop / clear、command-based deletion等

`rules-auto-net`は追加しません。

### Hook trust

`docs/reference/codex-safety-harness.md`には次を記載します。

- `.codex/config.toml`のHook定義を変更したときだけ再確認する
- Codex interactive CLIで`/hooks`を実行する
- Hookの定義元、command、matcher、timeout、trust状態を確認する
- 実行環境とtrust確認時の`CODEX_HOME`を一致させる
- contract test PASSと実Codex上のtrust / runtime確認は別の証拠として扱う
- `--dangerously-bypass-hook-trust`を通常運用へ入れない

### ハーネスのログ

`log_event.mjs`は移植せず、ユーザーprompt本文、tool input preview、session transcript等をrepository配下へ独自複製しません。必要な開発証跡はGit diff、Plan、PR、CI、テスト結果で確認します。

## format対象から除外する条件

最初から評価fixtureや履歴文書を除外しません。

次のいずれかを実際に確認した場合だけ、個別fileまたは必要最小の範囲へ`dprint-ignore`または除外設定を追加します。

- formatter後に既存validatorが同じ入力を解釈できなくなる
- Markdown内のliteral text、code block、machine-readable blockの意味が変わる
- semantic evalの入力・referenceとして意図した文字列が変わる
- frontmatterやYAML / JSONの構造が変わる
- 既存テストが、format以外の契約差分によって失敗する

除外する場合は、広い`skills/**/evals/**`や`docs/history/**`単位ではなく、問題が発生する最小のfile / blockへ限定します。

単にdiffが大きい、履歴文書である、fixtureであるという理由だけでは除外しません。

## Python lint修正方針

lint導入時に`ruff check --fix .`を無条件では実行しません。

まずread-onlyで、

```bash
ruff check .
```

を実行し、現在の違反を分類します。

import sortingはformatと同じ機械的変更として、

```bash
ruff check --select I --fix .
```

で処理できます。

`E4` / `E7` / `E9` / `F`で検出された問題は内容を確認し、現在の挙動を変えない最小修正を行います。unused importの削除など、import時副作用や公開境界へ影響する可能性がある変更を一括適用しません。

lint違反を消すためだけの広範なリファクタリング、関数分割、型追加、命名変更は行いません。

## 実装順序

1. 最新`main`、現在branch、Plan-only差分を確認する
2. formatter / lint / ハーネス導入前の既存CI相当検証を実行し、baselineを確認する
3. `qa-training-store`の移植対象を最新`main`から再確認し、Planの移植 / 非移植判断に変化がないことを確認する
4. `.gitignore`から`.agents`、`.codex`、`AGENTS.md`、`CODE_REVIEW.md`、`PLANS.md`のignoreを外す
5. `AGENTS.md`、`PLANS.md`、`CODE_REVIEW.md`を移植先向けに作成する
6. `feature-plan`、`code-review`、`repair-loop`の必要ファイルだけを移植する
7. 4 custom agentを移植し、`implementation_researcher`の責務を`code_researcher`へ統合する
8. `.codex/config.toml`を現行schemaへ合わせ、4 roleを`config_file`で明示する
9. safety Hook、Windows launcher、compact用SessionStart Hookを移植する
10. common `.codex/rules/` 3ファイルとREADMEを移植・調整する
11. `docs/reference/codex-safety-harness.md`を移植先向けに作成する
12. Codex config / Hook / Windows launcher contract testを追加する
13. `ruff.toml`を追加する
14. TypeScript / JavaScript pluginを含む`dprint.json`を追加する
15. `ruff check .`をread-onlyで実行して違反を分類する
16. 現在の挙動を変えない必要なlint修正だけを行う
17. `ruff check --select I --fix .`でimport順を統一する
18. `ruff format .`でPythonを全件formatする
19. `dprint fmt`でMarkdown / JSON / YAML / TOML / JavaScriptを全件formatする
20. formatter再実行で追加差分が出ないことを確認する
21. format前後で評価fixture、Hook、configの意味が変わっていないことを確認する
22. `code-quality.yml`と`codex-harness.yml`を追加する
23. READMEへローカル実行方法とCodexハーネス入口を追加する
24. formatter / lint / Codexハーネスcontract / 既存Skill eval / runtime testをすべて実行する

27. 最終diffをformat差分、Codexハーネス差分、必要なlint修正に分け、無関係な変更がないことを確認する

format前baselineが失敗している場合は、既存失敗と今回差分を分離します。今回の変更で新しいfailureを既存問題として扱いません。

## 実装時の注意

初回の一括formatは変更file数が大きくなります。これは今回の目的上許容しますが、format変更と意味変更を混ぜません。

安全Hookはsecurity-sensitiveです。移植を理由にparserを書き直さず、移植元で検証済みのロジックを維持し、必要なrepo固有調整だけを行います。変更した場合はその分のcontract testを追加・更新します。

一方、移植元のハーネス全体を正しい前提として扱いません。現行Codex仕様で旧aliasや不要な運用になっている箇所は現在仕様へ合わせます。

`AGENTS.md`、Skill、referenceを増やすこと自体を目的にしません。同じ契約を複数文書へコピーせず、rootにはroutingと常時必要な規則、詳細は担当文書へ置きます。

QA Skill本体の`skills/**`と開発Agent用`.agents/skills/**`は別責務です。開発SkillをQA workflowの19 Skillへ追加せず、既存Skill countや評価datasetを変更しません。

lintで実コード修正が必要になった場合は、可能ならformatの機械的差分と分けて確認できる状態にします。特に`F`系の指摘を直す際は、unused importに副作用がないこと、public importとして使われていないことを確認してから削除します。

Markdown / JSON / YAMLのformatは、見た目の統一より既存契約の維持を優先します。全件formatできる場合は全件を対象とし、問題がある箇所だけ最小限の例外にします。
