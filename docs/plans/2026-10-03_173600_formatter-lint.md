# Formatter / Python lint / Codex開発ハーネス導入Plan

このPlanは、`qa-workflow-skills`の開発を安定させるために、formatter / Python lintと、`qa-training-store`で実運用しているCodex開発ハーネスのうち、このリポジトリで現在必要なものを同じ変更で導入する実装計画です。

段階分けはしません。`qa-training-store`の構成を丸ごとコピーするのではなく、現在の`qa-workflow-skills`の構成、Python中心のruntime、既存CI、既存のPlan / review運用、現在のCodex公式仕様に照らして、必要なものだけを移植します。

Formatter / lintはrepository-wideなコード・文書品質を維持し、Codexハーネスは開発Agentの指示、委譲、安全境界、検証を維持します。QA Skill本体のworkflow / runtime / artifact graphとは別責務として扱います。

## 目的

次を同時に満たします。

- PythonをRuffでformat / lintする
- Markdown / JSON / YAML / TOML / JavaScriptをdprintでformatする
- 評価fixture、過去Plan、history、reportを含め、今回Planで定義した対象拡張子のtracked fileを原則すべてformatする
- format後も現在のSkill契約、runtime、deterministic / semantic / trigger評価、CI結果を変えない
- PR以降に追加された対象拡張子の未formatファイルをGitHub Actionsで検出できるよう、format / lintを継続検査する
- root `AGENTS.md`でCodexの作業範囲、安全性、Plan / review / implementationの基本契約をrepository-localにする
- Plan、review、bounded repairの開発workflowを`.agents/skills/`へ移植する
- 調査専用、限定実装、テスト調査、品質ゲート実行をcustom subagentへ役割分離できるようにする
- Codex CLI `0.160.0`を検証済みruntimeとして固定し、Hook / execpolicy / granular approval / Code Mode経路を実runtimeで確認する
- execpolicyは高影響操作を`prompt`、今回の通常workflowで不要かつ危険性が明確な少数のcommand familyを`forbidden`へ分類する
- `PreToolUse` Hookはprotected branchや明確な破壊操作など、実行時contextが必要な誤操作防止のguardrailへ限定する。別security principalや任意programを隔離するhard security boundaryにはしない
- read-only Gitは「refs、staged contents、working-tree contents、repository config、remote / worktree等を**意図的に変更する操作ではない**」というcommand semanticsで分類する。Git自身のindex stat refresh等の内部cache更新までlocal file writeなしとは保証しない
- Gitがtrusted repository / user configurationやattributesに従って起動するfilter、GPG、pager、Hook、credential / transport helper等をrepository-local Hookが完全にsandbox化するとは扱わない。これらはtrusted runtime / repository configurationの境界とし、generic Git child-process security frameworkを追加しない
- `--output`、`--ext-diff`、`--textconv`、`--show-token`等、モデルがcommand lineから明示的に要求できる既知の副作用・secret露出経路は低コストなdefense-in-depthとして必要な範囲で拒否する。ただし、これでGit内部の全副作用や外部program実行を閉じたとは主張しない
- state-changing Gitをcontext判定する場合は、Hookが対象repositoryを一意に把握できるよう、command内でcanonical repository rootへ移動してからdirectな`git` / `git.exe`を実行する形式に限定する
- protected branch上のstate-changing Gitはdenyし、remote / history rewrite等の高影響GitとGitHub CLI mutationはexecpolicyのユーザー承認へ送る
- `features.unified_exec_tty = false`でpersistent interactive TTYを無効化し、通常文字列の`write_stdin`でPreToolUseを迂回できないことをruntime受入する
- compact後にroot `AGENTS.md`全文をmodel-visibleな`additionalContext`として再注入し、Hook output spillによるhead / tailだけの注入を完了扱いにしない
- WindowsとPOSIXの両方でHook transportと主要guardrailを検証する
- ハーネス自体のconfig / Hook / Windows launcherをCIで回帰検出する
- `qa-training-store`固有のNodeアプリ、Android、Agentic QA、Run Artifact、textlint、CI待機MCP等は持ち込まない
- QA Skill本体の19 Skill、artifact graph、evaluation contractをCodex開発ハーネスの都合で変更しない

formatやハーネス導入を理由に、QA workflowの責務、評価datasetの意味、runtime契約、validator契約、テストケースの内容を変更しません。

## 採用するツール

### Ruff

PythonのlintとformatにRuffを使用します。

実装時点ではRuff `0.16.8`を固定します。

理由:

- 現在のリポジトリはPython 3.11をCIの正本としている
- Ruff単体でlint、import sorting、Python formatを扱える
- Black + Flake8 + isortを個別導入する必要がない
- `ruff.toml`を利用でき、Python package管理を導入する必要がない

Ruff 0.16系では既定lint ruleが従来より大幅に増えているため、既定ruleへ依存しません。初回導入では現在の目的に必要なruleだけを明示します。

`ruff.toml`の基本方針:

```toml
target-version = "py311"
required-version = "==0.16.8"
extend-exclude = ["*.md"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]

[format]
line-ending = "lf"
```

`required-version`でローカルとCIのRuff version差を実行時にも拒否します。`line-ending = "lf"`でWindows / POSIX間の改行差分を作りません。

共通scriptからRuffを呼ぶときは、repository rootの`ruff.toml`を絶対pathで解決し、すべての`ruff check` / `ruff format`へ`--config <repository-root>/ruff.toml`を明示します。Ruffの「対象fileに最も近いconfigを使う」discoveryへ依存しません。将来、配下に`.ruff.toml` / `ruff.toml` / `[tool.ruff]`を持つ`pyproject.toml`が追加されても、共通script経由ではroot設定だけを適用します。

`*.md`をRuff側で除外するのは、Ruff 0.16系がMarkdown内のPython code blockもformatできるためです。Markdownの所有者はdprintへ一本化し、同一ファイルを2つのformatterが変更する状態を作りません。

初回導入では次を有効にしません。

- `ALL`
- `B`
- `UP`
- `SIM`
- docstring rule
- type checker
- `E501`

formatter / lint導入と直接関係しないリファクタリングや型付けまで変更範囲を広げないためです。追加ruleが必要なら、今回の導入後に実際の必要性を確認して別途追加します。

### dprint

Markdown / JSON / YAML / TOML / JavaScriptのformatにdprintを使用します。

dprint本体は`0.55.2`を固定します。remote Wasm pluginはversionだけでなくchecksumも固定し、実装時に`dprint add --checksum`で生成された設定をcommitします。checksum値を手入力しません。

ローカルとCIで同じdprint本体を使うため、`scripts/format_tracked.py`はdprintを使う処理の開始前に`dprint --version`を1回確認します。stdoutの末尾改行だけを除去した値が`dprint 0.55.2`と完全一致する場合だけ処理へ進み、それ以外はformat / checkを開始せず失敗します。`0.55.2`というversion tokenだけを曖昧に検索する実装にはしません。READMEのversion確認だけに依存しません。

また、すべてのdprint invocationでrepository rootの`dprint.json`を明示し、`--config-discovery=false`を併用します。配下の`dprint.json` / `dprint.jsonc`等を自動発見させず、共通script経由ではroot設定だけを使用します。

採用plugin:

- TypeScript / JavaScript: `0.96.1`
- JSON: `0.25.1`
- Markdown: `0.25.0`
- TOML: `0.8.0`
- Pretty YAML: `0.6.0`

Plan作成時に記載していたMarkdown `0.24.0`は、実装前確認時点のplugin registryで`0.25.0`がcurrentだったため更新します。ほかのpluginも実装開始時にregistryを再確認し、versionを変更する場合はPlanと設定を同時に更新します。

Markdownでは、日本語文書や評価入力の既存改行を必要以上に変えないため、`textWrap = "maintain"`を使用します。改行コードはfile種別ごとではなくglobalにLFへ統一し、incremental cacheへ結果を依存させません。

```json
    "strongKind": "asterisks",
    "unorderedListKind": "dashes"

}
```

### formatter / lint対象集合

対象列挙とtool呼び出しはPython 3.11標準ライブラリだけの`scripts/format_tracked.py`へ集約します。このscriptはformat ruleを持たず、次だけを担当します。

- repository rootで`git ls-files -z --`を実行してtracked pathを取得する
- Ruff対象を`.py`、dprint対象を`.md` / `.json` / `.yml` / `.yaml` / `.toml` / `.js` / `.cjs` / `.mjs` / `.jsx`へ絞る
- Ruffへtracked Python pathを明示argvとして渡し、repository rootの`ruff.toml`を`--config`で必ず指定する。Ruffは`force-exclude = false`のままにし、明示pathがgitignoreで落ちないことを利用する
- dprintを使う処理では最初に`dprint --version`のstdoutから末尾改行だけを除去し、`dprint 0.55.2`との完全一致を確認する。不一致なら対象fileへ触れる前に失敗する
- dprintへtracked pathをnewline区切りで渡し、repository rootの`dprint.json`を`--config`で指定し、`--config-discovery=false`を付けた`fmt --no-gitignore --stdin-files` / `check --no-gitignore --stdin-files`を使う。`.gitignore`、`.git/info/exclude`、`DPRINT_GLOBAL_GITIGNORE=1`時のglobal gitignoreを対象選定へ反映させず、nested dprint configも利用しない
- dprint対象のtracked pathが0件なら、dprint 0.55.2のempty `--stdin-files`へ依存せず、`file-paths` / `fmt` / `check --stdin-files`を起動しない。対象0件を正常状態として扱い、untracked fileやconfig includesへフォールバックしない
- 同じroot config固定条件で`dprint file-paths --no-gitignore --stdin-files`の解決結果と期待するtracked対象を比較し、`dprint.json`のincludes / excludesやplugin association等で対象が静かに欠落した場合は失敗する
- shell展開や`xargs`へ依存せず、`subprocess.run(..., shell=False)`でtoolを起動する
- newlineを含むtracked pathは`--stdin-files`で安全に表現できないため明示エラーにする。現行repositoryには存在しない

標準入口は次で固定します。

```bash
python scripts/format_tracked.py ruff-check
python scripts/format_tracked.py import-fix
python scripts/format_tracked.py format
python scripts/format_tracked.py check
```

- `ruff-check`: tracked Pythonだけへread-onlyの`ruff check`
- `import-fix`: tracked Pythonだけへ`ruff check --select I --fix`
- `format`: tracked Pythonへ`ruff format`、tracked dprint対象が1件以上なら`dprint fmt --no-gitignore --stdin-files`。0件ならdprintを起動せず正常終了する
- `check`: tracked Pythonへ`ruff check`＋`ruff format --check`、tracked dprint対象が1件以上なら`dprint check --no-gitignore --stdin-files`。0件ならdprintを起動せず正常終了する

CIとREADMEの通常手順はこのscriptを使用し、`ruff check .` / `dprint check`等のdirectory discoveryを正規入口にしません。共通scriptがroot config固定とdprint本体version確認も担当するため、通常手順でformatterを直接起動しません。formatter configの対象patternはplugin associationの契約として維持しますが、対象ファイル集合の正本にはしません。

実装時に意味保持のため個別除外が本当に必要になった場合は、formatter設定だけで静かに除外せず、`scripts/format_tracked.py`の期待対象と理由も同じ変更で更新します。広いdirectory単位の除外は引き続き行いません。

### .gitattributes

Ruff / dprint側でLFを指定するだけでなく、Git checkout時のworking tree改行もformatter対象についてLFへ固定します。既存の`* text=auto`は維持し、次を追加します。

```gitattributes
*.py text eol=lf
*.md text eol=lf
*.json text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
*.toml text eol=lf
*.js text eol=lf
*.cjs text eol=lf
*.mjs text eol=lf
*.jsx text eol=lf
```

既存の`skills/*/scripts/runtime_contract.py text eol=lf`は`*.py text eol=lf`に包含されるため削除し、同じ契約を重複させません。

`.gitattributes`自体はRuff / dprintのformat対象ではなく手動管理します。format完了後に`git ls-files --eol`でformatter対象のindex / working treeがLFであることを確認します。

### `AGENTS.md`

root `AGENTS.md`は常時読み込まれるため、移植元の全文をコピーしません。次の毎回必要な契約だけを保持します。

- ユーザーの明示指示と作業範囲を最優先する
- Plan-only / review-only / investigation-onlyでは実装やGit mutationへ進まない
- 実装・設計前に関連Issue / PR / Plan / code / test / CIを必要な範囲で確認する
- QA Skillの仕様は`README.md`、`EVALS.md`、対象`skills/<name>/SKILL.md`を正本として扱う
- 既存runtime / validator / helperを確認してから新規抽象化を追加する
- default branchへの直接commit / push、force push、branch削除、merge、release等をユーザー指示なしに行わない
- Codex 0.160.0でmulti-agent作業またはapproval pending中にreconnect / recovered queueが発生した場合、recovered approvalを承認して継続せずfresh sessionで作業状態を再確認する。別session由来と疑われるapproval / outputが見えた場合も停止する
- Codex 0.160.0のrepository safety contractを使うfresh runtimeは`--no-daemon`でshared background app-serverを使わない。managed/shared app-serverへ接続したsessionはapprovalのsession isolationを保証できないためsupportedとして扱わない
- file delete / rename / move等の破壊的変更は明示された対象範囲内だけで行う
- formatter / lint / relevant tests / CI contractを完了前に確認する。完了判定に使う独立したvalidationは原則1 command = 1 tool callで実行し、改行区切り・`;`・複数commandを1回のshell実行へまとめたaggregate exit codeだけでPASS判定しない。Parentは各validationの成功結果を個別に確認する
- Codex 0.160.0では選択model / runtimeのeffective tool modeを確認する。Directではdirect `exec_command`、Code Mode / CodeModeOnlyでは`exec`内のnested `tools.exec_command()`についてrepository-owned `Bash` `PreToolUse`とexecpolicyのfresh runtime受入を通し、該当経路がPASSした場合だけstate-changing Gitをsupportedとして扱う。未検証または受入FAILのmodel / runtimeではstate-changing Gitを実行せず停止する
- 人間向けエンジニアリング文書は原則日本語で記述する
- Planは`PLANS.md`、reviewは`CODE_REVIEW.md`、安全Hook詳細は`docs/reference/codex-safety-harness.md`へ委譲する
- subagentは親Agentがscopeと完了判定を保持し、childから追加subagentを起動しない

このPRで検証済みとしてサポートするCodex CLIは`0.160.0`です。Hook payload、execpolicy、custom role override、granular approval、Hook trustの安全契約を0.160.0の実装へ照合しているため、CIとfresh runtime受入では`codex --version`のstdoutから末尾改行だけを除去し、`codex-cli 0.160.0`との完全一致を必須確認します。異なる出力・versionでは受入成功と判定しません。

Codex 0.160.0には外側のCode Mode `exec`自体が`PreToolUse`を発火しないopen issue `openai/codex#23411`があり、0.160.0の`CodeModeExecuteHandler`にも`pre_tool_use_payload`実装はありません。ただし、0.160.0のnested tool dispatchは`ToolCallSource::CodeMode`から通常の`ToolCallRuntime` / `ToolRouter` / `ToolRegistry`へ渡され、`ExecCommandHandler`はnested `tools.exec_command()`に対して`Bash`の`PreToolUsePayload`を生成します。0.160.0のupstream integration testにも、Code Mode内のnested `exec_command`を`PreToolUse`で実行前denyするcaseと`updatedInput`で書き換えるcaseがあります。またCode Mode `exec`のruntime contractはraw JavaScriptにNode / file system / network / consoleを提供せず、外部副作用は有効なnested tool経路へ委譲する設計です。

このため#23411を理由にCode Mode全体を一括でunsupportedにはしません。一方、外側`exec`にrepository-owned Hookを追加したとみなしたり、raw JavaScriptを解析するgeneric policy engineを実装したりもしません。このrepositoryのPreToolUse guardrailとexecpolicyはshell / Git経路の契約として、Directではdirect `exec_command`、Code Mode / CodeModeOnlyではnested `tools.exec_command()`に適用します。選択model / runtimeごとにfresh runtime acceptanceで、nested commandがrepository-owned `Bash` `PreToolUse`を実際に通ること、denyが実行前に止まり副作用を残さないこと、execpolicyのrule未一致 / `prompt` / `forbidden`が同じnested経路で成立することを確認します。これらをPASSしたCode Mode / CodeModeOnly runtimeはsupportedに含め、FAILまたは経路を確認できないruntimeはsupportedにしません。外部MCPやこのPlanでpolicy対象にしていないnested tool familyは、従来どおりrepository-local shell policyの保証範囲外です。

Codex 0.160.0には、独立した複数commandを1回の`exec_command`へまとめたとき前段失敗が後段成功のexit code 0で隠れ得るopen issue `openai/codex#50301`があります。このrepositoryではCLI自体をwrapperで修復せず、完了判定に使う独立したvalidationを個別tool callで実行し、Parentがformatter / lint / test / eval / runtime等の成功結果を個別に確認します。`quality_gate_runner`と`repair-loop`も同じ契約を持ち、aggregate shell exit codeだけを完了根拠にしません。

Codex 0.160.0には、multi-agent利用中のpending approval / outputがdisconnect・reconnect後に別sessionへ表示されるcross-session leakageのopen bug `openai/codex#50233`があります。加えて`openai/codex#50355`では、reconnectなしでも同じshared app-serverへ接続した独立CLI session間でsubagent approval dialogが別windowへ表示される再現があります。このrepository-local harnessはupstreamのsession routingを修復できないため、0.160.0についてmanaged/shared app-server上のapproval session isolationを保証しません。

そのためCodex 0.160.0のfresh runtime受入は、**`codex --no-daemon --strict-config`でshared background serverを使わないembedded runtime**を正本にします。managed/shared app-serverへ接続したsessionは、version一致や単一sessionのapproval probeが成功してもsupported runtimeとしてPASSにしません。repository側でdaemonを停止・再起動・更新する処理や、複数session isolationを再現する独自proxy / wrapperは追加しません。

multi-agent作業またはapprovalがpendingの状態でdisconnect / reconnect、recovered queue、別session由来と疑われるapproval / outputが発生した場合も、そのsessionを安全な継続状態とはみなしません。recovered approvalを承認せずfresh `--no-daemon` sessionで対象作業を再確認します。root `AGENTS.md`と`docs/reference/codex-safety-harness.md`へ#50233 / #50355とこの運用制約を記載します。

別versionをサポート対象へ追加する場合は、Hook / execpolicy / role override / granular approval / Hook trust / Code Mode経路に加え、#50233 / #50355相当のapproval / output session isolationが解消または受入可能であることを再確認し、CIの固定version、`docs/reference/codex-safety-harness.md`、contract test、完了条件を同じ変更で更新します。自動version managerは導入しません。

Hookは`features.hooks = true`だけでなく、`.codex/config.toml`へ次の登録契約を明示します。

| event | matcher | POSIX handler | Windows handler | timeout | その他 |
| --- | --- | --- | --- | ---: | --- |
| `PreToolUse` | `^Bash$` | Git rootを`git rev-parse --show-toplevel`で解決し、`node <root>/.codex/hooks/pre_tool_use_policy.mjs`を実行する | Git rootを解決して`.codex/hooks/pre_tool_use_policy_windows.ps1`を実行し、stdin / stdout / stderr / exit codeをNode Hookへ透過する | 30秒 | `type = "command"`、`statusMessage = "Checking Bash command safety policy"` |
| `SessionStart` | `^compact$` | stdinを保持したままGit rootを解決し、`node <root>/.codex/hooks/session_start_context.mjs`を実行する。launcher側でroot / Node / Hook解決に失敗した場合は停止結果を返す | 同じfail-closed launcher semanticsをPowerShellで実装し、repository rootの`session_start_context.mjs`へstdinを渡す | 10秒 | `type = "command"`、`additionalContextLimit = 0` |

Codex 0.160.0のWindows command Hook runnerは、cmd-style shellでは`cmd.exe /C`へcommand line全体を外側のdouble quoteで包んで渡します。OpenAI Codex issue #38168で報告されているとおり、`powershell.exe ... -Command "..."`のように`command_windows`自身がembedded double quoteを持つ形式は、この境界で誤解釈され得ます。このため、このrepositoryの`PreToolUse.command_windows` / `SessionStart.command_windows`は次を固定契約にします。

- command lineは`powershell.exe -NoProfile -NonInteractive -EncodedCommand <base64>`形式とし、`command_windows`文字列自身にliteral `"`を含めない
- `<base64>`は実装時に人間が読めるPowerShell payloadをUTF-16LEでencodeして生成し、移植元のopaqueなbase64文字列をコピーしない
- encoded payload内で`git rev-parse --show-toplevel`によりrepository rootを解決し、実Windows pathや空白を含むrepository pathはdecoded PowerShell側で扱う。absolute repository pathを`command_windows`文字列へ埋め込まない
- `PreToolUse`のencoded payloadはroot解決後にrepository-ownedの`.codex/hooks/pre_tool_use_policy_windows.ps1`へstdinを透過し、同launcherはtransport-onlyのまま維持する
- `SessionStart`のencoded payloadは同じroot解決 / fail-closed契約でrepository rootの`session_start_context.mjs`へstdinを渡す
- contract testはbase64をdecodeして期待するPowerShell処理と一致することを検証し、encoded文字列そのものを読めない正本にしない

さらにWindows contract testでは、`command_windows`を直接起動するだけでなく、Codex 0.160.0のcmd-style Hook runnerと同じ`cmd.exe /C "<command_windows>"`境界を通して同じ結果になることを確認します。repository pathに空白を含む一時checkoutでもこの経路を検証します。

`SessionStart`のPOSIX / Windows launcherは、Hook本体を起動できない場合にもcompact後の必須指示欠落を見逃さないよう、移植元のfail-closed launcher semanticsを維持します。新しいWindows launcher fileは追加せず、上記の検証可能な`-EncodedCommand` payloadで実装します。

承認境界は次で固定します。

| 操作 | 期待する扱い |
| --- | --- |
| read-only command、通常のworkspace内source変更 | 原則としてsandboxとParent scopeの範囲で実行する。Git内部cache更新やtrusted config由来child processがないことまでは保証しない |
| `.git`、`.agents`、`.codex`等、sandboxが保護するpathへの必要な書込み | `sandbox_approval = true`でユーザー承認経路を持つ |
| feature branch上の通常`git add` / restore / switch等 | protected branch guardrailに違反しない範囲で一律禁止しない |
| `git commit` / merge / rebase / fetch / pull / push / reset / am / cherry-pick / revert、branch / tag rewrite、`git config` / `remote` / `worktree` / `stash`のmutationを含み得るfamily | execpolicy `prompt`でユーザー承認へ送る。prefix制約でread-only formも同familyへ入る場合は、その承認を許容し、独自option parserを増やさない |
| GitHub CLIのPR / Issue / repository / workflow / run / release / secret / variable / cache / label等のremote mutation | execpolicy `prompt`でユーザー承認へ送る |
| force push、hard reset、commit amend、force branch / tag rewrite、opaque nested shell等 | Hookで既知の危険variantをblockし、対応familyの`prompt`をfallbackにする |
| `gh api`、`gh repo sync`、`git clean`、`git rm`、`git update-ref`、command-based deletion | 今回の通常workflowでは不要なためexecpolicy `forbidden`にする |

remote URL、refspec、SSH helper、`insteadOf`、`core.sshCommand`、Git filter / GPG / pager / Hook等をこの承認表の成立条件として個別列挙しません。remote mutationはユーザー承認、Git内部挙動はtrusted runtime / repository configurationの境界として扱います。

`approvals_reviewer = "user"`を明示し、granular approvalを自動reviewへ委譲しません。`mcp_elicitations`、`request_permissions`、`skill_approval`は今回のrepository-local harnessで承認経路を増やす目的がないためfalseにします。将来必要になった場合はその利用経路を確認して別途変更します。

この承認表はBash / shell経路のrepository-local harness契約です。今回の`.codex/config.toml`にはmutation-capable MCP serverを追加しません。ユーザー設定やpluginから利用可能なMCP toolはrepository-local execpolicyの対象ではなく、MCP側の`approval_mode`やユーザー側設定が別の安全境界になります。`mcp_elicitations = false`をMCP tool mutationの承認制御とは扱いません。

custom agentのRole名・選択ガイダンスは親`.codex/config.toml`の`[agents.<name>]`と`description`を正本とします。Codex 0.160.0では、親configの`config_file`から読み込んだrole fileに対してrole名がhintとして渡され、child file側の`name` / `description`は必須ではありません。この宣言方式を維持し、移植元のトップレベル`name` / `description`をchild fileへ重複コピーしません。

子`.codex/agents/*.toml`は`developer_instructions`と、Codex 0.160.0で実際にrole overrideとして適用される設定だけを持たせます。`sandbox_mode`や`[agents] enabled = false`をchild fileへ書いてsecurity boundaryとして扱いません。0.160.0のrole適用処理はこれらをchild overrideへ反映しないためです。

### custom subagent

4 roleに限定します。

- `code_researcher`: code / contract / dependency / test / CIの調査専用。編集しないことを`developer_instructions`で要求する
- `implementation_worker`: 親Agent指定のfile / scopeだけを変更する。不要なrefactor、delete / rename / move、Git mutation、追加subagentを行わないことを`developer_instructions`で要求する
- `test_investigator`: 既存test、evaluation、CI failure、flaky候補、未カバー領域の調査専用。編集しないことを`developer_instructions`で要求する
- `quality_gate_runner`: 親Agent指定のvalidationだけを実行し、formatter write、source変更、dependency install、Git mutationを行わないことを`developer_instructions`で要求する。完了判定対象の独立したvalidationは1 command = 1 tool callで実行し、複数validationを改行区切り・`;`等で1回のshell invocationへまとめない。各結果を個別にParentへ返し、先行failureを後続successで上書きしない

Codex 0.160.0では、custom roleから`sandbox_mode`や`agents.enabled`をchild固有の強制設定として適用できません。そのため上記のread-only、Git mutation禁止、再委譲禁止は**Roleの行動契約**であり、security boundaryとは扱いません。

機械的な誤操作防止はParent session側のsandbox、execpolicy、PreToolUse Hookが担当します。これらをGit内部helperや外部MCPまで隔離するhard security boundaryとは扱いません。Parentはchildへ対象file・scope・禁止事項を明示し、完了判定を保持します。childから追加subagentを起動しないことも`developer_instructions`で要求しますが、`[agents] enabled = false`や`agents.max_depth`で保証できるとは記載しません。`max_depth`はMulti-agent V2では無視されるため追加しません。

今回、childごとのhard permission boundaryを新設するwrapperや別sandboxは追加しません。今回の目的は役割分離と誤操作抑止であり、Parentとchildで別のsecurity principalを構築することではありません。

### supported Hook topology

Codex 0.160.0では複数sourceからHookが読み込まれ、`PermissionRequest` Hookや別の同期`PreToolUse`がproject-local policyと競合し得ます。ここをrepository-local security frameworkで一般解析はしません。

fresh runtime受入では`/hooks`を確認し、少なくとも次を満たす環境だけを今回のguardrail検証対象とします。

- repository-owned `.codex/hooks/pre_tool_use_policy.mjs`が`Bash` `PreToolUse`として有効である
- repository-owned `session_start_context.mjs`が`SessionStart(source=compact)`へ登録されている
- `Bash` commandを書き換える別の同期`PreToolUse`が有効でない
- ユーザー承認を自動承認へ変える有効な`PermissionRequest` Hookがない
- 条件を満たさない場合は、設定を書き換えて回避せず、そのruntimeを今回の検証済み環境としてPASSにしない

この確認はproject Hookが評価したcommandと実行commandを一致させ、execpolicyの`prompt`が実際にユーザー承認へ到達することを確認するためのruntime qualificationです。Git内部のhelperや任意programまで同じ境界で隔離するものではありません。

### PreToolUse safety Hook

`qa-training-store`のHookからshell commandの基本的な分解とWindows transport互換部分を再利用しますが、policyは今回の目的へ縮小します。matcherは`^Bash$`だけにします。

Hookの責務は次に限定します。

1. **protected branchのcontextual block**
   - protected branchは`main` / `master`と、解決できる場合の`origin/HEAD`で決める
   - protected branch上のcommit / merge / rebase / cherry-pick / revert / pull / am / reset等、履歴またはstaged / working-tree stateへ意図的に変更を加えるGit操作をdenyする
   - protected branchへの明示push、branch rename / delete等もdenyする
2. **対象repositoryの固定**
   - state-changing GitをHookでcontext判定する場合だけ、同じshell command内でcanonical repository rootへ移動し、その直後にdirectな`git` / `git.exe`を実行する形式を要求する
   - `git -C`、`--git-dir`、`--work-tree`等で別repository contextを指定する形はsupported formにしない
   - read-only Gitにはcanonical cwd移動を要求しない
3. **明確な破壊操作のblock**
   - force push、hard reset、commit amend、force branch / tag rewrite、`git clean`、`git rm`、`git update-ref`等、通常の自律開発で誤操作リスクが高い形をdenyまたはexecpolicyの承認境界へ送る
   - `rebase -x` / `--exec`とinteractive rebaseは今回の通常workflowで必要性がないためunsupported denyにする
   - command-based deletionは移植元の既知familyを維持するが、任意script内部まで再帰解析しない
4. **opaque nested shellのblock**
   - `bash -c` / `sh -c` / `zsh -c`、PowerShell `-Command` / `-EncodedCommand`、`cmd /c`、`Invoke-Expression`等、Hookから内側commandの意味を安定して判断できないwrapperをBash toolから使う形はdenyし、必要なcommandを直接実行させる
5. **Hook入力異常のblock**
   - Hook本体が起動した後のmalformed inputやrepository context解決失敗はfail-closedにする

#### read-only Gitの定義

read-only Gitは、commandの目的としてrefs、staged contents、working-tree contents、repository config、remote / worktree等を変更しない形式を指します。

代表例:

- `status`
- `diff` / `log` / `show`
- `rev-parse`
- `ls-files`
- `check-ignore`
- branch / tagの一覧・現在branch確認
- `config`のget / list系
- `remote`の一覧 / `get-url`
- `worktree list`
- `stash list` / `stash show`

この分類は**副作用ゼロの保証ではありません**。Git公式仕様上、`git status`はindex stat cacheをrefreshしてindexを書き出すことがあり、`git diff`も`diff.autoRefreshIndex=true`では`update-index --refresh`を実行できます。またGit config / attributesによりfilter、GPG、pager等のchild processが起動し得ます。

そのため、次は今回のrepository-local Hookの保証対象外です。

- Git自身の内部cache / index stat refresh
- trusted repository / user configurationとattributesに基づくfilter / GPG / pager / Hook / credential / transport helper
- Git内部で将来追加される任意のchild process

一方、モデルがCLIから明示的に要求できる既知の副作用は低コストなguardrailとして扱います。少なくとも`git diff` / `log` / `show`の`--output`、明示`--ext-diff` / `--textconv`はread-only扱いしません。`--no-ext-diff --no-textconv`はvalidation commandで使用できますが、「外部program実行を完全排除する証明」には使いません。

`core.fsmonitor`、`core.hooksPath`、default hooks directory、`filter.*`、`gpg.*`等をread-only可否のsecurity invariantとして列挙しません。これらを追い続けるgeneric Git child-process sandboxは今回追加しません。

#### Git state-changing操作

native Git subcommandを「全挙動を証明したallowlist」にしません。Hookが認識する既知read-only form以外のdirect Gitはstate-changing / unknown候補として安全側に扱い、protected branch contextではdenyします。

feature branch上では、通常のadd / commit / restore / switch等を一律禁止しません。remote操作、履歴rewrite、削除・強制操作等の高影響familyはexecpolicyの`prompt`または`forbidden`へ委譲します。

push / fetch / pullについてremote URL、refspec、SSH helper、`insteadOf`、`core.sshCommand`等をrepository Hookが完全にモデル化しません。これらはユーザー承認とtrusted Git configurationの境界とします。protected branchへの明示pushやforce系の明確な誤操作だけをHookでblockします。

#### GitHub CLI

GitHub CLIは「既知read-only subcommandの全optionを安全証明する」方式をやめます。

- `pr view|list|status|checks|diff`、`issue view|list|status`、`repo view|list`、`run view|list|watch`等の通常read操作は通常sandboxへ残す
- remote mutationはexecpolicy `prompt`へ送る
- `gh api` / `gh repo sync`は今回の通常workflowで必要性がなく影響範囲が広いため`forbidden`を維持する
- `gh auth status --show-token`のような明示secret出力はdenyする
- `--web`、browser環境変数、download / output option等を網羅する独自option allowlistは作らない。browser起動やlocal file出力まで「read-only副作用ゼロ」の保証対象にしない

#### shell / environmentの境界

state-changing Gitのcanonical formを成立させるため、同じcommand内でrepository contextを差し替える明示的な`GIT_DIR` / `GIT_WORK_TREE`等やcwd変更の多重化はsupportedにしません。ただしGit / ghが参照し得る環境変数を完全列挙するparserは作りません。

`git` / `gh`のalias、PATH shadowing、system側wrapper等もrepository-local Hookが完全に認証する対象にはしません。fresh runtimeでは通常のCLIが利用できることを確認しますが、system環境全体のcommand identityをsecurity boundaryとして証明しません。

Codex 0.160.0のPreToolUseへtool-level `workdir`とper-call `shell`が渡らない制約は維持します。state-changing Gitのguardrailを受入するruntimeはlocal primary environmentとし、POSIXはBash / Zsh、WindowsはWindows PowerShell / pwshを前提にします。別shellやper-call shell overrideはこのguardrailの検証済み経路に含めません。

### compact後の指示再注入

`session_start_context.mjs`は`SessionStart(source=compact)`時だけroot `AGENTS.md`を`additionalContext`へ返します。`startup` / `resume` / `clear`では重複注入しません。

Codex 0.160.0では`additionalContextLimit`はmodel-visible hook outputのtoken上限で、上限を超えると全文ではなくhead / tail previewと一時file pathへspillされます。`0`はspill無効を意味するため、このrepositoryでは`additionalContextLimit = 0`を固定し、compact後のroot `AGENTS.md`全文をmodel-visibleな`additionalContext`として維持します。独自token counterや`AGENTS.md <= 4096 tokens`制約は追加しません。

Hook本体が正常に起動した状態でroot解決、Hook input、`AGENTS.md`読込、structured output生成に失敗した場合は、明示的な停止結果を返します。ただしlauncher failureやtimeoutまで絶対的に停止できるとは扱いません。compact後の再注入は`AGENTS.md`の正本を補完する回復手段であり、唯一の安全境界にはしません。

contract testでは`session_start_context.mjs`が返す`additionalContext`本文をroot `AGENTS.md`全文と一致させ、`.codex/config.toml`の`additionalContextLimit = 0`も同時に固定します。fresh runtime acceptanceではmodel-visibleな再注入を、`AGENTS.md`の先頭・中間・末尾にある既知の必須契約がcompact後もすべて保持されることで確認し、head / tailだけが残る状態をPASSにしません。

### execpolicy rules

`.codex/rules/`はHookの代替ではなく、Hook failure時にも高影響操作を無承認で通しにくくする承認境界として使います。通常のread-only command用`allow` ruleは追加しません。

`20-risky-prompt.rules`では、少なくとも次をfamily単位で`prompt`にします。

- `git commit`
- `git merge`
- `git rebase`
- `git pull`
- `git push`
- `git fetch`
- `git reset`
- `git am`
- `git cherry-pick`
- `git revert`
- branch / tagの削除・rewriteへ到達し得るfamily
- `git config` / `git remote` / `git worktree` / `git stash`のstate-changing formを含み得るfamily
- GitHub CLIのPR / Issue / repository / workflow / run / release / secret / variable / cache / label等のremote mutation
- download、force move / rename等、local fileへ影響する既知の高影響family

prefix ruleではread-only formとmutation formを完全分離できないfamilyがあります。その場合、read-only formまで承認対象になることを許容し、独自option parserを増やして無承認read-onlyへ戻すことを優先しません。

`30-destructive-forbidden.rules`では、今回の通常workflowでCodexから使う必要性がなく、影響範囲が広い少数のfamilyだけを`forbidden`にします。

- `gh api`
- `gh repo sync`
- `git clean`
- `git rm`
- `git update-ref`
- `rm` / `del` / `erase` / `rd` / `ri` / `Remove-Item` / `rmdir` / `unlink`等のcommand-based deletion

force push、hard reset、commit amend等はoption位置で意味が変わるため、execpolicy prefix ruleだけで完全な永久禁止を表現しません。Hookで既知の危険variantをblockし、family-level `prompt`をfallbackにします。

固定版Codex CLIで、代表commandがrule未一致 / `prompt` / `forbidden`へ期待どおり分類されることをcontract testします。POSIX / Windowsのfresh runtimeでは、設定ファイルのparse結果だけでなく、実際に`prompt`がユーザー承認へ到達し、`forbidden`が実行前拒否になることを安全なprobeで確認します。

Git / GitHub CLIの全subcommand・全option・全configをrepository独自policy engineで再実装しません。未分類の副作用を完全に排除することではなく、通常のCodex開発経路で高影響操作を承認へ送り、明確な破壊操作を防ぐことを目的とします。

### Hook trust

`docs/reference/codex-safety-harness.md`には次を記載します。

- Codex 0.160.0のHook trust hashはnormalizedされたHook設定identityから計算され、参照先`.mjs` / `.ps1`のsource本文はhash対象ではない。`Trusted`表示をHook source未変更の証拠として扱わない
- `.codex/config.toml`等のHook定義を変更した場合はCodex interactive CLIで`/hooks`を再確認する
- Hook sourceを変更した場合は、既存trustが自動失効する前提を置かず、該当contract testとfresh trusted Codexでのruntime受入を再実行する
- Hookの定義元、command、matcher、timeout、trust状態を確認する
- 実行環境とtrust確認時の`CODEX_HOME`を一致させる
- contract test PASS、Hook sourceの変更確認、実Codex上のtrust / runtime確認は別の証拠として扱う
- Hook source digestをcommandへ埋め込む独自revision機構は追加しない。Hookは絶対的なsecurity boundaryではなく、永久禁止操作はexecpolicy `forbidden`でも防御する
- `--dangerously-bypass-hook-trust`を通常運用へ入れない

### ハーネスのログ

`log_event.mjs`は移植せず、ユーザーprompt本文、tool input preview、session transcript等をrepository配下へ独自複製しません。必要な開発証跡はGit diff、Plan、PR、CI、テスト結果で確認します。

## 実装時の注意

初回の一括formatは変更file数が大きくなります。これは今回の目的上許容しますが、format変更と意味変更を混ぜません。

安全Hookは、移植元parserをそのまま増築しません。今回残すprotected branch、canonical cwd、明確な破壊variant、opaque nested shell、malformed inputに必要な処理だけを再利用・整理します。Git config / attributes / helperの新しい副作用経路が見つかっても、それを理由に個別parserを追加して「副作用ゼロ」を追いません。

read-only Gitはrepository stateを意図的に変更しないcommand semanticsであり、Git自身の内部cache更新やtrusted configuration由来のchild processを含まないという意味ではありません。実装・test・documentationでこの境界を同じ表現に揃えます。

state-changing Gitのprotected branch guardrailだけは対象repositoryの取り違えを避ける必要があるため、command内でcanonical project rootを固定してからdirectな`git` / `git.exe`を実行します。これ以外のshell / environment全体をsecurity parserへ広げません。

execpolicyは高影響familyをユーザー承認へ送り、少数の不要な破壊familyだけを永久禁止します。prefix ruleでread-only formとmutation formを分けられないfamilyは、無理にoption parserを増やさずread-only側も承認対象になることを許容します。

Codex 0.160.0ではPreToolUseへtool-level `workdir`とper-call `shell`が渡らないこと、`write_stdin`が2回目のPreToolUseを発火しないこと、Code Mode外側`exec`とnested `tools.exec_command()`の経路が異なることを前提に、実runtime acceptanceを維持します。ここはGit helper完全隔離とは別問題であり、削りません。

移植元のハーネス全体を正しい前提として扱いません。現行Codex仕様で旧aliasや不要な運用になっている箇所は現在仕様へ合わせます。

`AGENTS.md`、Skill、referenceを増やすこと自体を目的にしません。同じ契約を複数文書へコピーせず、rootにはroutingと常時必要な規則、詳細は担当文書へ置きます。

custom agentについては、Codex 0.160.0のrole overrideで実際に強制できる設定と、`developer_instructions`による行動契約を混同しません。

QA Skill本体の`skills/**`と開発Agent用`.agents/skills/**`は別責務です。開発SkillをQA workflowの19 Skillへ追加せず、既存Skill countや評価datasetを変更しません。

lintで実コード修正が必要になった場合は、可能ならformatの機械的差分と分けて確認できる状態にします。特に`F`系の指摘を直す際は、unused importに副作用がないこと、public importとして使われていないことを確認してから削除します。

Markdown / JSON / YAMLのformatは、見た目の統一より既存契約の維持を優先します。全件formatできる場合は全件を対象とし、問題がある箇所だけ最小限の例外にします。
