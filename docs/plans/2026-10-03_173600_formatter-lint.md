# Formatter / Python lint / Codex開発ハーネス導入Plan

このPlanは、`qa-workflow-skills`の開発を安定させるために、formatter / Python lintと、`qa-training-store`で実運用しているCodex開発ハーネスのうち、このリポジトリで現在必要なものを同じ変更で導入する実装計画です。

段階分けはしません。`qa-training-store`の構成を丸ごとコピーするのではなく、現在の`qa-workflow-skills`の構成、Python中心のruntime、既存CI、既存のPlan / review運用、現在のCodex公式仕様に照らして、必要なものだけを移植します。

Formatter / lintはrepository-wideなコード・文書品質を維持し、Codexハーネスは開発Agentの指示、委譲、安全境界、検証を維持します。QA Skill本体のworkflow / runtime / artifact graphとは別責務として扱います。

## 目的

次を同時に満たします。

- PythonをRuffでformat / lintする
- Markdown / JSON / YAML / TOML / JavaScriptをdprintでformatする
- 評価fixture、過去Plan、history、reportを含め、今回Planで定義した対象拡張子のtracked fileを原則すべてformatする
- format後も現在のSkill契約、runtime、deterministic / semantic / trigger評価、CI結果を変えない
- PR以降に追加された対象拡張子の未formatファイルをGitHub Actionsで検出できるよう、format / lintを継続検査する
- root `AGENTS.md`でCodexの作業範囲、安全性、Plan / review / implementationの基本契約をrepository-localにする
- Plan、review、bounded repairの開発workflowを`.agents/skills/`へ移植する
- 調査専用、限定実装、テスト調査、品質ゲート実行をcustom subagentへ役割分離できるようにする
- Bash tool経路では、execpolicy rulesで静的に判定できる高影響 / 禁止操作を分類し、`PreToolUse` Hookで現在branch等の実行時contextが必要な危険操作とopaqueなnested shellをguardrailとして検査する
- low-level Git mutationから既存安全分類を迂回させない。`git config`はget / list系以外、`git remote`は明示read-only以外、`git worktree`は`list`以外をunsupportedとしてHookでdenyし、Hook failure時は各familyのexecpolicy `prompt`をfallbackにする。通常開発workflowで必要性がない`git update-ref`はallowlistへ入れずfamily全体を`forbidden`にする
- Codex 0.160.0の`PreToolUse`はshell-like toolについて`tool_input.command`だけを渡し、`exec_command.shell`を渡さないため、state-changing Gitのshell-dependent safety判定は対応するsession default shell＋per-call shell overrideなしを受入前提にする。repository Hookがshell identityを機械的に強制できるとは扱わない
- Codex 0.160.0では複数の同期`PreToolUse` Hookが同じ元inputを並行評価し、別Hookの`updatedInput`で実行commandが書き換わり得るため、Bash safety contractの受入対象runtimeではrepository-owned safety Hook以外に`Bash`へmatchする有効な同期`PreToolUse` Hookが存在しないことを必須にする
- granular approvalで、通常のfeature branch Git mutation、高影響操作の明示承認、永久禁止操作を分離する
- `.codex/config.toml`の設定値だけで承認境界が有効とみなさず、POSIX / Windowsの各supported fresh trusted Codex 0.160.0 `--no-daemon --strict-config` runtimeでsandbox approvalとproject-local execpolicyの実動作を確認する。managed/shared app-serverはsupported runtimeおよびprobe対象に含めない
- compact後に必要なroot `AGENTS.md`を再注入できるようにする
- WindowsとPOSIXの両方で安全Hookを利用できるようにする
- ハーネス自体のconfig / Hook / Windows launcherをCIで回帰検出する
- `qa-training-store`固有のNodeアプリ、Android、Agentic QA、Run Artifact、textlint、CI待機MCP等は持ち込まない
- QA Skill本体の19 Skill、artifact graph、evaluation contractをCodex開発ハーネスの都合で変更しない

formatやハーネス導入を理由に、QA workflowの責務、評価datasetの意味、runtime契約、validator契約、テストケースの内容を変更しません。

## 採用するツール

### Ruff

PythonのlintとformatにRuffを使用します。

実装時点ではRuff `0.16.8`を固定します。

理由:

- 現在のリポジトリはPython 3.11をCIの正本としている
- Ruff単体でlint、import sorting、Python formatを扱える
- Black + Flake8 + isortを個別導入する必要がない
- `ruff.toml`を利用でき、Python package管理を導入する必要がない

Ruff 0.16系では既定lint ruleが従来より大幅に増えているため、既定ruleへ依存しません。初回導入では現在の目的に必要なruleだけを明示します。

`ruff.toml`の基本方針:

```toml
target-version = "py311"
required-version = "==0.16.8"
extend-exclude = ["*.md"]

[lint]
select = ["E4", "E7", "E9", "F", "I"]

[format]
line-ending = "lf"
```

`required-version`でローカルとCIのRuff version差を実行時にも拒否します。`line-ending = "lf"`でWindows / POSIX間の改行差分を作りません。

共通scriptからRuffを呼ぶときは、repository rootの`ruff.toml`を絶対pathで解決し、すべての`ruff check` / `ruff format`へ`--config <repository-root>/ruff.toml`を明示します。Ruffの「対象fileに最も近いconfigを使う」discoveryへ依存しません。将来、配下に`.ruff.toml` / `ruff.toml` / `[tool.ruff]`を持つ`pyproject.toml`が追加されても、共通script経由ではroot設定だけを適用します。

`*.md`をRuff側で除外するのは、Ruff 0.16系がMarkdown内のPython code blockもformatできるためです。Markdownの所有者はdprintへ一本化し、同一ファイルを2つのformatterが変更する状態を作りません。

初回導入では次を有効にしません。

- `ALL`
- `B`
- `UP`
- `SIM`
- docstring rule
- type checker
- `E501`

formatter / lint導入と直接関係しないリファクタリングや型付けまで変更範囲を広げないためです。追加ruleが必要なら、今回の導入後に実際の必要性を確認して別途追加します。

### dprint

Markdown / JSON / YAML / TOML / JavaScriptのformatにdprintを使用します。

dprint本体は`0.55.2`を固定します。remote Wasm pluginはversionだけでなくchecksumも固定し、実装時に`dprint add --checksum`で生成された設定をcommitします。checksum値を手入力しません。

ローカルとCIで同じdprint本体を使うため、`scripts/format_tracked.py`はdprintを使う処理の開始前に`dprint --version`を1回確認します。stdoutの末尾改行だけを除去した値が`dprint 0.55.2`と完全一致する場合だけ処理へ進み、それ以外はformat / checkを開始せず失敗します。`0.55.2`というversion tokenだけを曖昧に検索する実装にはしません。READMEのversion確認だけに依存しません。

また、すべてのdprint invocationでrepository rootの`dprint.json`を明示し、`--config-discovery=false`を併用します。配下の`dprint.json` / `dprint.jsonc`等を自動発見させず、共通script経由ではroot設定だけを使用します。

採用plugin:

- TypeScript / JavaScript: `0.96.1`
- JSON: `0.25.1`
- Markdown: `0.25.0`
- TOML: `0.8.0`
- Pretty YAML: `0.6.0`

Plan作成時に記載していたMarkdown `0.24.0`は、実装前確認時点のplugin registryで`0.25.0`がcurrentだったため更新します。ほかのpluginも実装開始時にregistryを再確認し、versionを変更する場合はPlanと設定を同時に更新します。

`dprint.json`は少なくとも次を対象にします。

```text

**/*.json
**/*.yml
**/*.yaml
**/*.toml
**/*.js
**/*.cjs
**/*.mjs
```

現在の目的はJavaScriptまでです。TypeScript / TSXは今回新規導入しないため`*.ts` / `*.tsx`を対象へ広げません。今回の実装でTypeScript fileを追加する設計にもせず、移植元の`feature-plan/scripts/validate-plan-output.ts`は移植しません。

原則としてディレクトリ単位の除外は設定しません。

Markdownでは、日本語文書や評価入力の既存改行を必要以上に変えないため、`textWrap = "maintain"`を使用します。改行コードはfile種別ごとではなくglobalにLFへ統一し、incremental cacheへ結果を依存させません。

```json
{
  "newLineKind": "lf",
  "incremental": false,
  "markdown": {
    "textWrap": "maintain",
    "emphasisKind": "asterisks",
    "strongKind": "asterisks",
    "unorderedListKind": "dashes"
  }
}
```

formatter / lintの対象集合はformatter自身のdirectory discoveryではなく、Git tracked fileを正本にします。`.gitignore`、`.git/info/exclude`、global gitignoreの内容で対象が変わらないようにします。

### formatter / lint対象集合

対象列挙とtool呼び出しはPython 3.11標準ライブラリだけの`scripts/format_tracked.py`へ集約します。このscriptはformat ruleを持たず、次だけを担当します。

- repository rootで`git ls-files -z --`を実行してtracked pathを取得する
- Ruff対象を`.py`、dprint対象を`.md` / `.json` / `.yml` / `.yaml` / `.toml` / `.js` / `.cjs` / `.mjs` / `.jsx`へ絞る
- Ruffへtracked Python pathを明示argvとして渡し、repository rootの`ruff.toml`を`--config`で必ず指定する。Ruffは`force-exclude = false`のままにし、明示pathがgitignoreで落ちないことを利用する
- dprintを使う処理では最初に`dprint --version`のstdoutから末尾改行だけを除去し、`dprint 0.55.2`との完全一致を確認する。不一致なら対象fileへ触れる前に失敗する
- dprintへtracked pathをnewline区切りで渡し、repository rootの`dprint.json`を`--config`で指定し、`--config-discovery=false`を付けた`fmt --no-gitignore --stdin-files` / `check --no-gitignore --stdin-files`を使う。`.gitignore`、`.git/info/exclude`、`DPRINT_GLOBAL_GITIGNORE=1`時のglobal gitignoreを対象選定へ反映させず、nested dprint configも利用しない
- dprint対象のtracked pathが0件なら、dprint 0.55.2のempty `--stdin-files`へ依存せず、`file-paths` / `fmt` / `check --stdin-files`を起動しない。対象0件を正常状態として扱い、untracked fileやconfig includesへフォールバックしない
- 同じroot config固定条件で`dprint file-paths --no-gitignore --stdin-files`の解決結果と期待するtracked対象を比較し、`dprint.json`のincludes / excludesやplugin association等で対象が静かに欠落した場合は失敗する
- shell展開や`xargs`へ依存せず、`subprocess.run(..., shell=False)`でtoolを起動する
- newlineを含むtracked pathは`--stdin-files`で安全に表現できないため明示エラーにする。現行repositoryには存在しない

標準入口は次で固定します。

```bash
python scripts/format_tracked.py ruff-check
python scripts/format_tracked.py import-fix
python scripts/format_tracked.py format
python scripts/format_tracked.py check
```

- `ruff-check`: tracked Pythonだけへread-onlyの`ruff check`
- `import-fix`: tracked Pythonだけへ`ruff check --select I --fix`
- `format`: tracked Pythonへ`ruff format`、tracked dprint対象が1件以上なら`dprint fmt --no-gitignore --stdin-files`。0件ならdprintを起動せず正常終了する
- `check`: tracked Pythonへ`ruff check`＋`ruff format --check`、tracked dprint対象が1件以上なら`dprint check --no-gitignore --stdin-files`。0件ならdprintを起動せず正常終了する

CIとREADMEの通常手順はこのscriptを使用し、`ruff check .` / `dprint check`等のdirectory discoveryを正規入口にしません。共通scriptがroot config固定とdprint本体version確認も担当するため、通常手順でformatterを直接起動しません。formatter configの対象patternはplugin associationの契約として維持しますが、対象ファイル集合の正本にはしません。

実装時に意味保持のため個別除外が本当に必要になった場合は、formatter設定だけで静かに除外せず、`scripts/format_tracked.py`の期待対象と理由も同じ変更で更新します。広いdirectory単位の除外は引き続き行いません。

### .gitattributes

Ruff / dprint側でLFを指定するだけでなく、Git checkout時のworking tree改行もformatter対象についてLFへ固定します。既存の`* text=auto`は維持し、次を追加します。

```gitattributes
*.py text eol=lf
*.md text eol=lf
*.json text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
*.toml text eol=lf
*.js text eol=lf
*.cjs text eol=lf
*.mjs text eol=lf
*.jsx text eol=lf
```

既存の`skills/*/scripts/runtime_contract.py text eol=lf`は`*.py text eol=lf`に包含されるため削除し、同じ契約を重複させません。

`.gitattributes`自体はRuff / dprintのformat対象ではなく手動管理します。format完了後に`git ls-files --eol`でformatter対象のindex / working treeがLFであることを確認します。

### `AGENTS.md`

root `AGENTS.md`は常時読み込まれるため、移植元の全文をコピーしません。次の毎回必要な契約だけを保持します。

- ユーザーの明示指示と作業範囲を最優先する
- Plan-only / review-only / investigation-onlyでは実装やGit mutationへ進まない
- 実装・設計前に関連Issue / PR / Plan / code / test / CIを必要な範囲で確認する
- QA Skillの仕様は`README.md`、`EVALS.md`、対象`skills/<name>/SKILL.md`を正本として扱う
- 既存runtime / validator / helperを確認してから新規抽象化を追加する
- default branchへの直接commit / push、force push、branch削除、merge、release等をユーザー指示なしに行わない
- Codex 0.160.0でmulti-agent作業またはapproval pending中にreconnect / recovered queueが発生した場合、recovered approvalを承認して継続せずfresh sessionで作業状態を再確認する。別session由来と疑われるapproval / outputが見えた場合も停止する
- Codex 0.160.0のrepository safety contractを使うfresh runtimeは`--no-daemon`でshared background app-serverを使わない。managed/shared app-serverへ接続したsessionはapprovalのsession isolationを保証できないためsupportedとして扱わない
- file delete / rename / move等の破壊的変更は明示された対象範囲内だけで行う
- formatter / lint / relevant tests / CI contractを完了前に確認する。完了判定に使う独立したvalidationは原則1 command = 1 tool callで実行し、改行区切り・`;`・複数commandを1回のshell実行へまとめたaggregate exit codeだけでPASS判定しない。Parentは各validationの成功結果を個別に確認する
- Codex 0.160.0では選択model / runtimeのeffective tool modeを確認する。Directではdirect `exec_command`、Code Mode / CodeModeOnlyでは`exec`内のnested `tools.exec_command()`についてrepository-owned `Bash` `PreToolUse`とexecpolicyのfresh runtime受入を通し、該当経路がPASSした場合だけstate-changing Gitをsupportedとして扱う。未検証または受入FAILのmodel / runtimeではstate-changing Gitを実行せず停止する
- 人間向けエンジニアリング文書は原則日本語で記述する
- Planは`PLANS.md`、reviewは`CODE_REVIEW.md`、安全Hook詳細は`docs/reference/codex-safety-harness.md`へ委譲する
- subagentは親Agentがscopeと完了判定を保持し、childから追加subagentを起動しない

このPRで検証済みとしてサポートするCodex CLIは`0.160.0`です。Hook payload、execpolicy、custom role override、granular approval、Hook trustの安全契約を0.160.0の実装へ照合しているため、CIとfresh runtime受入では`codex --version`のstdoutから末尾改行だけを除去し、`codex-cli 0.160.0`との完全一致を必須確認します。異なる出力・versionでは受入成功と判定しません。

Codex 0.160.0には外側のCode Mode `exec`自体が`PreToolUse`を発火しないopen issue `openai/codex#23411`があり、0.160.0の`CodeModeExecuteHandler`にも`pre_tool_use_payload`実装はありません。ただし、0.160.0のnested tool dispatchは`ToolCallSource::CodeMode`から通常の`ToolCallRuntime` / `ToolRouter` / `ToolRegistry`へ渡され、`ExecCommandHandler`はnested `tools.exec_command()`に対して`Bash`の`PreToolUsePayload`を生成します。0.160.0のupstream integration testにも、Code Mode内のnested `exec_command`を`PreToolUse`で実行前denyするcaseと`updatedInput`で書き換えるcaseがあります。またCode Mode `exec`のruntime contractはraw JavaScriptにNode / file system / network / consoleを提供せず、外部副作用は有効なnested tool経路へ委譲する設計です。

このため#23411を理由にCode Mode全体を一括でunsupportedにはしません。一方、外側`exec`にrepository-owned Hookを追加したとみなしたり、raw JavaScriptを解析するgeneric policy engineを実装したりもしません。このrepositoryのG1〜G10とexecpolicyはshell / Git境界の契約として、Directではdirect `exec_command`、Code Mode / CodeModeOnlyではnested `tools.exec_command()`に適用します。選択model / runtimeごとにfresh runtime acceptanceで、nested commandがrepository-owned `Bash` `PreToolUse`を実際に通ること、denyが実行前に止まり副作用を残さないこと、execpolicyのrule未一致 / `prompt` / `forbidden`が同じnested経路で成立することを確認します。これらをPASSしたCode Mode / CodeModeOnly runtimeはsupportedに含め、FAILまたは経路を確認できないruntimeはsupportedにしません。外部MCPやこのPlanでpolicy対象にしていないnested tool familyは、従来どおりrepository-local shell policyの保証範囲外です。

Codex 0.160.0には、独立した複数commandを1回の`exec_command`へまとめたとき前段失敗が後段成功のexit code 0で隠れ得るopen issue `openai/codex#50301`があります。このrepositoryではCLI自体をwrapperで修復せず、完了判定に使う独立したvalidationを個別tool callで実行し、Parentがformatter / lint / test / eval / runtime等の成功結果を個別に確認します。`quality_gate_runner`と`repair-loop`も同じ契約を持ち、aggregate shell exit codeだけを完了根拠にしません。

Codex 0.160.0には、multi-agent利用中のpending approval / outputがdisconnect・reconnect後に別sessionへ表示されるcross-session leakageのopen bug `openai/codex#50233`があります。加えて`openai/codex#50355`では、reconnectなしでも同じshared app-serverへ接続した独立CLI session間でsubagent approval dialogが別windowへ表示される再現があります。このrepository-local harnessはupstreamのsession routingを修復できないため、0.160.0についてmanaged/shared app-server上のapproval session isolationを保証しません。

そのためCodex 0.160.0のfresh runtime受入は、**`codex --no-daemon --strict-config`でshared background serverを使わないembedded runtime**を正本にします。managed/shared app-serverへ接続したsessionは、version一致や単一sessionのapproval probeが成功してもsupported runtimeとしてPASSにしません。repository側でdaemonを停止・再起動・更新する処理や、複数session isolationを再現する独自proxy / wrapperは追加しません。

multi-agent作業またはapprovalがpendingの状態でdisconnect / reconnect、recovered queue、別session由来と疑われるapproval / outputが発生した場合も、そのsessionを安全な継続状態とはみなしません。recovered approvalを承認せずfresh `--no-daemon` sessionで対象作業を再確認します。root `AGENTS.md`と`docs/reference/codex-safety-harness.md`へ#50233 / #50355とこの運用制約を記載します。

別versionをサポート対象へ追加する場合は、Hook / execpolicy / role override / granular approval / Hook trust / Code Mode経路に加え、#50233 / #50355相当のapproval / output session isolationが解消または受入可能であることを再確認し、CIの固定version、`docs/reference/codex-safety-harness.md`、contract test、完了条件を同じ変更で更新します。自動version managerは導入しません。

| event | matcher | POSIX handler | Windows handler | timeout | その他 |
| --- | --- | --- | --- | ---: | --- |
| `PreToolUse` | `^Bash$` | Git rootを`git rev-parse --show-toplevel`で解決し、`node <root>/.codex/hooks/pre_tool_use_policy.mjs`を実行する | Git rootを解決して`.codex/hooks/pre_tool_use_policy_windows.ps1`を実行し、stdin / stdout / stderr / exit codeをNode Hookへ透過する | 30秒 | `type = "command"`、`statusMessage = "Checking Bash command safety policy"` |

Codex 0.160.0のWindows command Hook runnerは、cmd-style shellでは`cmd.exe /C`へcommand line全体を外側のdouble quoteで包んで渡します。OpenAI Codex issue #38168で報告されているとおり、`powershell.exe ... -Command "..."`のように`command_windows`自身がembedded double quoteを持つ形式は、この境界で誤解釈され得ます。このため、このrepositoryの`PreToolUse.command_windows` / `SessionStart.command_windows`は次を固定契約にします。

- command lineは`powershell.exe -NoProfile -NonInteractive -EncodedCommand <base64>`形式とし、`command_windows`文字列自身にliteral `"`を含めない
- `<base64>`は実装時に人間が読めるPowerShell payloadをUTF-16LEでencodeして生成し、移植元のopaqueなbase64文字列をコピーしない
- encoded payload内で`git rev-parse --show-toplevel`によりrepository rootを解決し、実Windows pathや空白を含むrepository pathはdecoded PowerShell側で扱う。absolute repository pathを`command_windows`文字列へ埋め込まない
- `PreToolUse`のencoded payloadはroot解決後にrepository-ownedの`.codex/hooks/pre_tool_use_policy_windows.ps1`へstdinを透過し、同launcherはtransport-onlyのまま維持する
- `SessionStart`のencoded payloadは同じroot解決 / fail-closed契約でrepository rootの`session_start_context.mjs`へstdinを渡す
- contract testはbase64をdecodeして期待するPowerShell処理と一致することを検証し、encoded文字列そのものを読めない正本にしない

さらにWindows contract testでは、`command_windows`を直接起動するだけでなく、Codex 0.160.0のcmd-style Hook runnerと同じ`cmd.exe /C "<command_windows>"`境界を通して同じ結果になることを確認します。repository pathに空白を含む一時checkoutでもこの経路を検証します。

`SessionStart`のPOSIX / Windows launcherは、Hook本体を起動できない場合にもcompact後の必須指示欠落を見逃さないよう、移植元のfail-closed launcher semanticsを維持します。新しいWindows launcher fileは追加せず、上記の検証可能な`-EncodedCommand` payloadで実装します。

承認境界は次で固定します。

| 操作 | 期待する扱い |
| --- | --- |
| read-only command、通常のworkspace内source変更 | 原則としてsandboxとParent scopeの範囲で実行し、execpolicyのprompt対象にはしない。ただしvariant-dependent destructive operationやunsupported mutationのfallbackとしてfamily単位`prompt`へ置く`git branch` / `tag` / `stash` / `config` / `remote` / `worktree`等は、read-only形式でも承認対象になる。この例外はprefix制約下で無承認の危険variantを通さないために許容する |

| feature branchの通常`git add` | 同じshell command内でcanonical project rootへ安全に移動した直後のbare `git` / `git.exe` commandならHookで一律denyしない。absolute / relative path付きGit executable、`command git ...`、`env ... git ...`等のwrapper、cwd固定なしのmutation、`git -C`等のcontext overrideはG10でdenyする。sandbox承認が必要な場合はユーザーへ要求する |
| feature branchの通常`git commit` / `git push` | Hookでは許可候補とするが、`--amend` / force・prune・mirror等のvariantをHook failure時も無承認で通さないため、execpolicyは`git commit` / `git push` family単位で`prompt`にする。通常pushのcanonical formは`git push --no-follow-tags <configured-remote> <single-refspec>`とし、configured remoteのeffective push URLが1件で`remote.<name>.mirror`がtrueではない場合だけ許可候補にする |
| feature branchの`git fetch` / `git pull` | `git fetch` / `git pull` family全体をexecpolicy `prompt`にする。Hookではconfigured remote 1件、custom vcs / uploadpackなし、`--no-tags`、effective fetch URLがHTTPS / SSH（scp-like SSHを含む）の通常transport、persistent destinationが`refs/remotes/<remote>/**`だけであることを許可条件にする。remote URL自体または`url.*.insteadOf`展開後のeffective URLが`<transport>::<address>`、unknown protocol、local path / `file://`等のunsupported transportになる場合、`refs/heads/**` / `refs/tags/**` / その他local refへのdestination、`--update-head-ok`、`--force`、`--tags`、direct URL / 複数remote / `--refmap`等はdenyする。`pull`はfeature branch上でもmerge / rebase / squash等へ到達するためcanonical formでも承認対象とする |

`approvals_reviewer = "user"`を明示し、granular approvalを自動reviewへ委譲しません。`mcp_elicitations`、`request_permissions`、`skill_approval`は今回のrepository-local harnessで承認経路を増やす目的がないためfalseにします。将来必要になった場合はその利用経路を確認して別途変更します。

この承認表はBash / shell経路のrepository-local harness契約です。今回の`.codex/config.toml`にはmutation-capable MCP serverを追加しません。ユーザー設定やpluginから利用可能なMCP toolはrepository-local execpolicyの対象ではなく、MCP側の`approval_mode`やユーザー側設定が別の安全境界になります。`mcp_elicitations = false`をMCP tool mutationの承認制御とは扱いません。

custom agentのRole名・選択ガイダンスは親`.codex/config.toml`の`[agents.<name>]`と`description`を正本とします。Codex 0.160.0では、親configの`config_file`から読み込んだrole fileに対してrole名がhintとして渡され、child file側の`name` / `description`は必須ではありません。この宣言方式を維持し、移植元のトップレベル`name` / `description`をchild fileへ重複コピーしません。

子`.codex/agents/*.toml`は`developer_instructions`と、Codex 0.160.0で実際にrole overrideとして適用される設定だけを持たせます。`sandbox_mode`や`[agents] enabled = false`をchild fileへ書いてsecurity boundaryとして扱いません。0.160.0のrole適用処理はこれらをchild overrideへ反映しないためです。

### custom subagent

4 roleに限定します。

- `code_researcher`: code / contract / dependency / test / CIの調査専用。編集しないことを`developer_instructions`で要求する
- `implementation_worker`: 親Agent指定のfile / scopeだけを変更する。不要なrefactor、delete / rename / move、Git mutation、追加subagentを行わないことを`developer_instructions`で要求する
- `test_investigator`: 既存test、evaluation、CI failure、flaky候補、未カバー領域の調査専用。編集しないことを`developer_instructions`で要求する
- `quality_gate_runner`: 親Agent指定のvalidationだけを実行し、formatter write、source変更、dependency install、Git mutationを行わないことを`developer_instructions`で要求する。完了判定対象の独立したvalidationは1 command = 1 tool callで実行し、複数validationを改行区切り・`;`等で1回のshell invocationへまとめない。各結果を個別にParentへ返し、先行failureを後続successで上書きしない

Codex 0.160.0では、custom roleから`sandbox_mode`や`agents.enabled`をchild固有の強制設定として適用できません。そのため上記のread-only、Git mutation禁止、再委譲禁止は**Roleの行動契約**であり、security boundaryとは扱いません。

機械的な安全境界はParent session側のsandbox、execpolicy、PreToolUse Hookが担当します。Parentはchildへ対象file・scope・禁止事項を明示し、完了判定を保持します。childから追加subagentを起動しないことも`developer_instructions`で要求しますが、`[agents] enabled = false`や`agents.max_depth`で保証できるとは記載しません。`max_depth`はMulti-agent V2では無視されるため追加しません。

今回、childごとのhard permission boundaryを新設するwrapperや別sandboxは追加しません。今回の目的は役割分離と誤操作抑止であり、Parentとchildで別のsecurity principalを構築することではありません。

### supported Hook topology

Codex 0.160.0では、user / project / session / plugin / managed等の複数sourceから同じeventへHookが読み込まれ得ます。同期`PreToolUse` handlerは同じ元のtool inputを並行して評価し、blockがなければ複数の`updatedInput`のうち完了順で最後のrewriteが実行inputへ採用されます。rewrite後にrepository safety Hookが再実行される契約はありません。

そのため、このrepositoryのBash safety contractを受入可能とするruntime topologyを次へ限定します。

- `Bash`へmatchする有効な同期`PreToolUse` Hookは、repository-owned `.codex/hooks/pre_tool_use_policy.mjs`だけであること
- user / projectの別定義 / session / plugin / managed Hookに、`Bash`へmatchする有効な同期`PreToolUse` Hookが1つでも存在する場合、そのruntimeをBash safety contractのsupported environmentとしてPASSにしないこと
- user / project / session / plugin / managedを含む全sourceについて、有効な`PermissionRequest` Hookが0件であること。Codex 0.160.0では`PermissionRequest` Hookの`allow`が通常のユーザー承認UIより先に`Approved`へ解決されるため、1件でも存在するruntimeはexecpolicy `prompt` / sandbox approvalのユーザー承認契約を保証できずunsupportedとする
- async Hookは実行commandの`updatedInput`制御へ使わないため、この「単一同期Hook」条件の対象外とする。ただしasync HookをBash safety enforcementの証拠にも数えない
- `/hooks`でrepository Hookの存在だけを確認して終了せず、全source / event / matcher / execution modeを確認し、`Bash`へmatchする同期`PreToolUse`がrepository-owned Hookだけであることと、`PermissionRequest` Hookが0件であることを検証すること
- Hook topologyが変わった場合はfresh runtime受入を再実行すること

別Hookの`updatedInput`を逐次再検査するwrapperや、他Hookの内容を一般解析する仕組みは追加しません。他のBash同期`PreToolUse` Hookとの共存をunsupportedにすることで、repository safety Hookが検査したcommandと実際に実行されるcommandを一致させます。

### PreToolUse safety Hook

`qa-training-store`の`pre_tool_use_policy.mjs`はNode標準ライブラリだけを使用し、Scenario Shop固有依存を持たないためparserの大部分を再利用します。ただし移植元の全policyをそのまま正本にはせず、今回の承認モデルへ合わせて境界を変更します。

Hookのmatcherは`^Bash$`だけに限定します。`apply_patch` / `Edit` / `Write`用のpatch parserや、任意のMCP tool inputを解釈するgeneric parserは今回追加しません。file delete / rename / move等のpatch操作は`AGENTS.md`とParent / `implementation_worker`のscope契約で制御し、今回Hookで機械的に防止できるとは主張しません。

静的に判定できる禁止操作はexecpolicy `forbidden`を使い、Hookは次のように、現在branch、複合shell、repository contextなど実行時contextが必要な判定のguardrailを担当します。

- protected branch上のcommit / merge / rebase / cherry-pick / revert / pull / am / `reset`等のcontextual mutation。`reset`はmodeやpath-formを個別に許可せず、protected branch上ではfamily全体をdenyする
- protected branchまたはprotected local refへのpush / fetch / `update-ref` / branch rename・delete / worktree変更
- state-changing Git commandの直前に、canonical repository rootへの単一・絶対path・検証済みのcwd移動がない場合、またはそれ以外のcwd変更が先行する場合
- state-changing Git commandで`git -C`、`--git-dir`、`--work-tree`、`GIT_DIR`、`GIT_WORK_TREE`等のrepository context overrideを使用する場合
- 複数Git invocationやshell chainで安全なcontext判定ができないmutation
- inline commandを隠せるnested shell wrapper
- Hookが正常に起動した後のmalformed input

protected branchは実装者判断にしません。このrepositoryのcanonical default branchである`main`を必ず含め、移植元互換のfallbackとして`master`も含めます。さらに`refs/remotes/origin/HEAD`が解決できる場合は、そのbranch名もprotected集合へ追加します。今回のrepositoryでは`main`がdefault branchであり、複数remoteのdefault branchを汎用探索する仕組みは追加しません。

Codex 0.160.0では、実際の`exec_command`はtool-level `workdir`から実行cwdを決めますが、Bash `PreToolUse`の`tool_input`には`command`しか渡されません。そのためHook processのcwdやtool-level `workdir`をstate-changing Git operationの実行対象として信頼しません。

同じ制約はshellにもあります。Codex 0.160.0のlocal `exec_command`はruntimeによって`shell` parameterを公開し、session shellとは別のshell binaryをper-callで指定できますが、`PreToolUse` payloadにはその`shell`値が含まれません。したがってNode Hookがcommand文字列だけから実行shellを機械的に証明することはできません。

今回のBash safety contractでstate-changing Gitを受入対象にするruntimeは次へ限定します。

- local primary environmentを使う
- POSIXではsession default shellがBashまたはZshである
- Windowsではsession default shellがWindows PowerShellまたはPowerShell 7+（`pwsh`）である
- state-changing Gitの`exec_command`でper-call `shell` overrideを指定しない
- remote / foreign execution environment、上記以外のdefault shell、またはshell overrideを利用するstate-changing Gitはsupported environmentとして扱わない

`AGENTS.md`でshell override禁止とunsupported shell時の停止を要求し、fresh runtime受入ではdefault shellを安全なprobeで確認します。ただしCodex 0.160.0ではHook自身がper-call `shell` fieldを観測できないため、これはruntime / 行動契約でありhard security boundaryではありません。Hook failureと同様に、shell identityを機械的に保証できるとは記載しません。高影響Git familyは引き続きexecpolicy `prompt` / `forbidden`を第2境界として使います。

state-changing Git commandは、**対応するsession default shell上で、同じshell command内でcanonical repository rootへ安全に移動した直後のbare `git` / `git.exe` + `<subcommand>`**だけを許可候補にします。POSIXでは概念的に`cd -- "<absolute-repository-root>" && git <subcommand> ...`、PowerShellでは`Set-Location -LiteralPath "<absolute-repository-root>" -ErrorAction Stop`の成功後にbare `git`または`git.exe` + `<subcommand> ...`を実行する形です。移動先はHook launcherが解決したこのprojectのcanonical Git rootと同じpathでなければなりません。

Hookは既存のcwd変更検出を全面的に緩めません。state-changing Git commandの直前にあるcwd変更について、次をすべて満たす場合だけ例外として認識します。

- cwd移動が1回だけである
- 移動先が絶対pathである
- canonical project rootと一致する
- 移動失敗時に後続Git commandへ進まない制御構造である
- cwd移動とGit mutationの間に別command、branch変更、Git environment変更がない
- Git invocation自体はbare `git <subcommand>`であり、`git -C`、`--git-dir`、`--work-tree`、`GIT_DIR`、`GIT_WORK_TREE`を使わない

これ以外のcwd変更後mutation、bare Git mutationだけの実行、相対pathへの移動、project root外への移動、複数回のcwd変更、repository context overrideはG10でdenyします。これによりhiddenなtool-level `workdir`が別repository / worktreeを指していても、実際のGit mutationはcommand自身でcanonical project rootへ固定されます。

この形式を採用する理由はexecpolicyとの整合です。Codex 0.160.0はshell compound commandをplain commandへ分解してexecpolicy評価し、`cd <root> && git rebase ...`のGit部分をbare `git rebase ...`として評価できます。一方、`git -C <root> rebase ...`ではprefix rule `["git", "rebase"]`へ一致しません。動的なrepository pathを含むrules生成は追加せず、実際に実行するGit argvとexecpolicyが評価するGit argvを同じbare subcommand契約へ揃えます。

read-only Git commandはcanonical rootへのcwd移動必須契約の対象外です。ただし上記で明示したread-only形式以外はstate-changingとして扱ってfail-closedします。特に`git add`、`git fetch`はstate-changingです。

`git config`は既存のget / list系だけを今回サポートするread-only形式にします。それ以外の値設定・削除・rename等はunsupportedとしてHookでdenyします。`git config remote.origin.pushurl <url>`等からpush先設定を書き換えると、`git remote set-url`を禁止しても別経路からeffective push URLを変更できるためです。Hook failure時にも無承認実行させないため、execpolicyでは`git config` / `git.exe config` family全体を`prompt`にします。

`git remote`は引数なし / `-v` / `--verbose` / `get-url` / `show`だけを今回サポートするread-only形式にします。それ以外の`update` / `prune` / `add` / `remove` / `rename` / `set-url` / `set-head` / `set-branches`等は、state-changingとして個別に許可せずunsupportedとしてHookでdenyします。`remote update`はfetch、`remote prune`はref削除、`remote add -f`はremote追加後のfetch、`remote add --mirror=fetch`はlocal `refs/`へのmirrorへ到達でき、今回のfetch / protected-ref安全判定を別経路から迂回できるためです。

`git worktree`は`list`だけをread-only形式としてサポートし、`add` / `remove` / `move` / `prune` / `repair` / `lock` / `unlock`等のstate-changing形式はunsupportedとしてHookでdenyします。worktree mutationを通常開発workflowで許可する要件がなく、`remove --force`等から別の削除・branch操作経路を増やす必要もないためです。Hook failure時のfallbackとして`git worktree` / `git.exe worktree` family全体をexecpolicy `prompt`にします。

`config` / `remote` / `worktree`の各familyについて汎用parserや個別mutationの再実装は追加しません。family-level `prompt`の制約によりread-only形式も承認対象になりますが、Hook failure時の無承認mutationを防ぐことを優先します。remote / foreign execution environmentでcanonical project rootを同一pathとして証明できないGit mutationも許可しません。

canonical rootへの移動後、current branchはそのcwdで`git branch --show-current`を使って取得します。detached HEAD、Git repository外、またはbranch contextを安全に解決できない状態でmutationが要求された場合はG10としてdenyします。`origin/HEAD`が解決できないことだけでは全操作を止めず、`main` / `master` fallbackを使用します。

G10は「protected branchへのpush」だけではありません。次を同じcontextual protectionとして保持します。

- protected branchへの直接push
- fetch / pullでprotected local refを書き換えるrefspec
- protected branchのrename / delete
- supported state-changing Gitからprotected local refへ到達する操作。`update-ref`はallowlist外＋execpolicy `forbidden`、state-changing `worktree`はunsupported denyとするためG10の個別解析対象にしない
- protected branch上のcommit / merge / rebase / cherry-pick / revert / pull / am / `reset`。`git reset --soft <commit>`、`git reset <commit>`、`git reset --merge <commit>`、`git reset --keep <commit>`を含め、protected branch上では`reset` family全体をdenyする
- repository / runtime Git context overrideを使って行うcontext-sensitive mutation
- canonical project rootへの検証済みcwd移動以外のbranch / cwd / environment変更後に同一shell command内で続けるcontext-sensitive mutation
- mutation対象やGit contextを安全に決定できない場合

nested shellについてはrecursiveなshell parserを新設しません。`bash` / `sh` / `zsh` / `dash` / `ksh`の`-c` / `-lc`、`pwsh` / `powershell`の`-Command` / `-EncodedCommand`、`cmd` / `cmd.exe`の`/c`、`Invoke-Expression`等、tool inputの内側へ別commandを隠せる実行形はPreToolUseでdenyし、必要なcommandをBash toolへ直接出し直させます。これにより既知のnested shell bypassをprefix ruleだけへ依存させません。

ただし、このrepository-local harnessを任意コード実行に対する完全なsecurity sandboxとは扱いません。例えば`python script.py`や外部MCP toolの内部処理まで意味解析して禁止操作を保証するものではありません。OS sandbox、ユーザー承認、外部tool側の権限制御が別の境界です。

Git network operationは、command lineだけでなく実行結果を変えるeffective Git configurationのうち、このPlanのref / repository / transport判定に直接関係する項目もfail-closedで確認します。Git設定全般をsecurity parser化するのではなく、通常push / fetch / pullの安全判定に必要な有限項目だけを対象にします。

pushは既存条件に加えて次を必須にします。

- configured remoteの`remote.<name>.vcs`が未設定であること。任意のcustom `git-remote-<vcs>`へ委譲するremoteはunsupportedとしてdenyする
- configured remoteの`remote.<name>.receivepack`が未設定であること
- command lineに`--receive-pack` / `--exec`がないこと
- effective push URLが、今回サポートする通常のGit URL形式であること。`<transport>::<address>`の明示remote-helper形式や、未知transportへ委譲するURLはdenyする。HTTPS / SSH等の通常transport内部実装まで「remote helper禁止」と誤解しない
- refspec先頭の`+`、`--force-with-lease`をforce pushとしてdenyする。既存の`--force` / `-f`と同じくoption位置に依存させない

fetch / pullは、protected refだけでなく**persistent local destination全体**を安全境界として判定します。`git pull`はfetch後にmerge / rebase / squash等へ到達できるため、feature branch上でもfamily全体をexecpolicy `prompt`へ置きます。`git fetch`もHook failure時にunsafe refspecを無承認で通さないためfamily全体を`prompt`へ置きます。

- 対象remoteをconfigured remoteとして一意に解決する。direct URL、`--all`、`--multiple`、remote group等、複数または非configured remoteへ広がる形式は今回の通常workflowではdenyする
- `remote.<name>.vcs`と`remote.<name>.uploadpack`が未設定であることを要求し、command lineの`--upload-pack`もdenyする
- configured remoteがfetchで実際に使用する先頭のeffective URLを`git remote get-url <remote>`相当で解決し、`url.*.insteadOf`展開後の値をtransport判定へ使う。許可するtransportはHTTPSとSSH（scp-like SSHを含む）だけとし、`<transport>::<address>`の明示remote-helper形式、unknown protocol、local path / `file://`等のunsupported transportはdenyする。push側の通常Git URL判定を共通化して使い、fetch専用のgeneric URL parserは作らない
- `--no-tags`をcanonical formで必須にし、`--tags`、explicit tag refspec、`fetch.pruneTags` / `remote.<name>.pruneTags` / `--prune-tags`等、local tag作成・更新・削除へ広がる形式はdenyする
- command lineにrefspecがない場合はeffective `remote.<name>.fetch`を全件解決し、persistent destinationが`refs/remotes/<remote>/**`だけであることを要求する。通常fetchが内部で使用する`FETCH_HEAD`はpersistent ref destinationとして扱わない
- command lineにfetch対象を明示する場合も、明示destinationは`refs/remotes/<remote>/**`だけを許可し、`refs/heads/**`、`refs/tags/**`、`refs/notes/**`、その他local refへのdestinationはprotected / featureの別なくdenyする。destinationを省略したsource-only refspecもeffective `remote.<name>.fetch`へ解決し、同じremote-tracking namespace条件を満たす場合だけ許可候補にする
- `--refmap`等でmappingを差し替える形式、`--update-head-ok`、`--force`はdenyする。remote-tracking refspecに通常含まれるleading `+`はdestinationが上記namespace内である場合だけ許可する
- 通常の`--prune` / `fetch.prune` / `remote.<name>.prune`は、effective refspecのdestinationが上記remote-tracking namespaceだけに限定できる場合に限り許可候補とする
- `git pull`のintegration mode（merge / rebase / squash等）をHookで再実装しない。protected branch上のpullは既存G10でdenyし、feature branch上のcanonical pullはfamily-level `prompt`で明示承認へ送る

contract testは、移植元matrixを別の手書き一覧へ複製せず、Hookがexportするcurrent matrixと追加のcontext fixtureを使ってdata-drivenに検証します。pushについては移植元の`PUSH_SAFE_OPTIONS`をそのまま採用せず、`--follow-tags`をsafe optionから外し、`--no-follow-tags`をcanonical formで必須にします。Hookはconfigured remoteの判定に既存のremote名取得を使い、effective push URLは`git remote get-url --push --all <remote>`相当で取得して1件であることを確認します。`remote.<name>.mirror`は`git config --bool --get remote.<name>.mirror`相当で確認し、trueならdenyします。明示1 refspecを必須にすることで`push.default` / `remote.<name>.push`等のimplicit refspecへ依存しません。direct URLや`--repo`を許可するための追加parserは作りません。

Hookが正常に起動し、Codex schemaに適合する明示的denyまたはblocking exitを返した場合はtool callを止められます。一方、Hook launcher failure、timeout、unsupported / malformed response等ではHook failureとしてtool callが継続し得ます。このため`PreToolUse` Hookを絶対的なsecurity enforcement boundaryとは扱いません。execpolicyのprefix ruleでcommand family全体を安全に表現できる操作だけを`forbidden`へ置きます。危険性が後続optionや引数位置で決まる操作はHookでdenyし、対応するcommand familyのexecpolicy `prompt`をfallbackにして、Hook failure時も無承認では実行させません。

Windowsの`pre_tool_use_policy_windows.ps1`はstdin / stdout / stderr / Node exit codeをtransportするだけにし、安全policyを複製しません。

### compact後の指示再注入

`session_start_context.mjs`は`SessionStart(source=compact)`時だけroot `AGENTS.md`を`additionalContext`へ返します。`startup` / `resume` / `clear`では重複注入しません。

Hook本体が正常に起動した状態でroot解決、Hook input、`AGENTS.md`読込、structured output生成に失敗した場合は、明示的な停止結果を返します。ただしlauncher failureやtimeoutまで絶対的に停止できるとは扱いません。compact後の再注入は`AGENTS.md`の正本を補完する回復手段であり、唯一の安全境界にはしません。

### execpolicy rules

`.codex/rules/`は静的command policyの正本であり、Hookの代替ではなく相互補完です。

- `20-risky-prompt.rules`: merge、通常rebase、`git am`、`git cherry-pick`、`git revert`、通常tag操作、local branch delete、通常のGitHub CLI remote mutationに加え、variant-dependent destructive operationのfallbackとして`git push` / `fetch` / `pull` / `reset` / `commit` / `restore` / `checkout` / `switch` / `branch` / `tag` / `stash`、unsupportedなstate-changing `git config` / `git remote` / `git worktree`のfallbackとして各family、必要なnetwork / file-operation familyをfamily単位で`prompt`にする
- `30-destructive-forbidden.rules`: command family全体を禁止できる`gh api`、`gh repo sync`、`git clean`、`git rm`、`git update-ref`、`rm` / `del` / `erase` / `Remove-Item` / `rmdir` / `unlink`等だけを`forbidden`にする。後続option位置の意味解析が必要なforce push、hard reset、commit amend等をprefixだけで「永久禁止」とは定義しない

Git / GitHub CLIのexecpolicy ruleはWindowsとPOSIXで同じ判定になるよう、実行ファイルtokenをalternativesとして固定します。Git ruleは`["git", "git.exe"]`、GitHub CLI ruleは`["gh", "gh.exe"]`を先頭tokenの候補にし、`git.exe` / `gh.exe`だけ承認・禁止ruleを迂回できる状態を作りません。

通常のread-only commandやworkspace内の通常作業には明示的な`allow` ruleを置きません。Codex 0.160.0では、commandの全segmentが明示的な`allow` ruleへ一致するとsandbox bypassが有効になり得るためです。read-only commandはexecpolicy ruleへ一致させず、通常のsandbox経路で実行します。意図的にsandbox外実行を許可する要件が将来発生しない限り、`decision = "allow"`は追加しません。

branch deleteを`prompt`と`forbidden`の両方へ重複定義しません。`git push` family自体を`prompt`にし、canonical formの単一remote branch deleteもその承認経路へ含めます。`--prune` / `--mirror`、force push、delete refspec等はHookでdenyします。execpolicyのprefix matchingでは`git push origin main --force`のような任意位置optionを完全に`forbidden`へ分離できないためです。通常rebaseも`prompt`とし、protected branch上の禁止はHookの実行時context判定へ分離します。

PreToolUseで直接扱うnative Git subcommandは、現在のrepository運用と既存Hookが意味を判定できる次の集合へ固定します。`add`、`am`、`branch`、`check-ignore`、`checkout`、`cherry-pick`、`clean`、`commit`、`config`、`diff`、`fetch`、`log`、`ls-files`、`merge`、`pull`、`push`、`rebase`、`remote`、`reset`、`restore`、`revert`、`rev-parse`、`rm`、`show`、`stash`、`status`、`switch`、`tag`、`worktree`だけを許可候補とします。`update-ref`は通常開発workflowで必要性が確認できず、branch rewrite / branch delete / reset相当の低レベルref mutationへ到達できるためallowlistへ入れず、execpolicyでもfamily全体を`forbidden`にします。この集合にない`git <subcommand>`は、Git alias / external subcommandを含めて内容を再帰解釈せずG10でdenyします。必要なnative subcommandが今後増えた場合は、用途とread-only / mutation semanticsを確認してallowlistとcontract testを同じ変更で更新します。

Git subcommandの状態変更判定はallowlistとは別に実装者判断へ残しません。常にread-onlyとして扱うのは`status`、`log`、`diff`、`show`、`rev-parse`、`ls-files`、`check-ignore`です。`branch`は一覧 / `--show-current`、`config`は既存のget / list系、`remote`は引数なし / `-v` / `--verbose` / `get-url` / `show`、`worktree`は`list`、`stash`は`list` / `show`、`tag`は一覧系だけをread-onlyとして認識します。このうち`config` / `remote` / `worktree`はread-only形式以外をsupported state-changingへ回さずunsupportedとしてHookでdenyし、各familyのexecpolicy `prompt`をHook failure時のfallbackにします。したがってprefix ruleの制約上、read-onlyの`git config --get ...`、`git remote -v`、`git worktree list`も承認対象になります。`add`、`fetch`を含む残りのallowlist内subcommandはsupported state-changingとして扱い、read-onlyと明示できない形式はcanonical repository root固定とcontext判定を必須にします。contract testではallowlist内の全subcommandがread-only / supported state-changing / unsupported denyのいずれかへ必ず分類され、未分類がないことを検証します。 さらに、protected branch上でG10がcontextual denyするsupported state-changing Git familyは、Hook failure時のfallbackとしてexecpolicy `prompt`または`forbidden`のどちらかへ必ず分類されることをdata-drivenに検証し、`commit` / `merge` / `rebase` / `pull` / `reset` / `am` / `cherry-pick` / `revert`等の追加時に片側だけ更新される状態を防ぎます。

GitHub CLIも汎用parserを追加せず、bare `gh` / `gh.exe`の`namespace + subcommand`を有限な分類表で扱います。ただし、同じsubcommandでもoptionによりsecret出力やlocal file writeへ変わるものは、subcommand名だけでread-onlyと判定しません。

repository-local harnessがread-onlyとして許可するのは、`--version` / `help` / `status` / `browse`と、`repo view|list|read-dir|gitignore|license`、出力fileを作らない`repo read-file`、`pr view|list|status|checks|diff`、`issue view|list|status`、`run view|list|watch`、`workflow view|list`、`release view|list`、`cache list`、`secret list`、`variable get|list`、`label list`、`search ...`です。

option-sensitiveな例外は次で固定します。

- `gh auth status` / `gh.exe auth status`はfamily単位でexecpolicy `prompt`へ置き、PreToolUseでは`-t` / `--show-token`をdenyする。安全と明示した既知option以外はfail-closedにする
- `gh repo read-file` / `gh.exe repo read-file`はstdoutへ読む形だけをread-onlyとし、`-o` / `--output`、`--clobber`等のlocal file write variantはread-only分類へ入れずPreToolUseでdenyする。未知optionもfail-closedにする
- `gh run download` / `gh.exe run download`と`gh release download` / `gh.exe release download`はlocal file writeを伴うためread-onlyから外し、family単位でexecpolicy `prompt`にする
- 上記のためだけにGitHub CLI全体のgeneric option parserは作らず、現在サポートするoption-sensitive subcommandだけを有限集合で判定する

これ以外のremote mutationを承認可能にする場合はexecpolicy `prompt`へ明示分類します。

今回サポートする`prompt`対象は、`auth status`、`pr create|edit|close|merge|ready|reopen|review`、`issue create|edit|close|delete|reopen`、`repo archive|unarchive|delete|edit|rename`、`repo autolink create|delete`、`repo deploy-key add|delete`、`release create|edit|delete|upload`、`release download`、`workflow enable|disable|run`、`run cancel|delete|rerun`、`run download`、`secret set|delete`、`variable set|delete`、`cache delete`、`label clone|create|edit|delete`とします。

`gh api`は任意の認証済みGitHub REST / GraphQL APIへ到達でき、refのforce update等の禁止操作まで表現できるため、このrepository-local harnessではfamily全体を`forbidden`とします。`gh repo sync`もsafe / `--force` variantをprefix ruleだけで完全分離できず、今回のrepository workflowで必須ではないためfamily全体を`forbidden`とします。HTTP method / endpoint / request bodyや任意位置flagを解析するgeneric GitHub API / CLI security parserは追加しません。

上記read-only / prompt / forbiddenのどれにも入らない`gh` commandは、現在存在するcommandも将来追加されるcommandもこのharnessではunsupportedとしてPreToolUseでdenyします。`gh alias`、`gh extension`、path付き`gh` / `gh.exe`、`command gh ...` / `env ... gh ...`等のwrapperもdenyします。新しい`gh`操作をサポートする場合はread-only / prompt / forbiddenのいずれかへ分類しcontract testを同じ変更で追加します。

Git mutationのexecpolicy ruleはbare `git` / `git.exe` + `<subcommand>` prefixを正本にします。state-changing Gitを実行するときはHook契約に従い、canonical project rootへの検証済みcwd移動とbare `git` / `git.exe` commandを同じshell command内で組み合わせます。`git -C <dynamic-path> ...`を実運用形式にはせず、repository pathごとのrules生成も行いません。これにより、実際に実行するGit subcommandと`prefix_rule([["git", "git.exe"], ...])`が同じargv形になります。

Codex 0.160.0のexecpolicyはordered prefix matchingであり、`match` / `not_match`はload時の検証例です。したがって`git push origin main --force`や`git reset HEAD --hard`のように危険flagが任意位置へ現れるcommandを、特定flagのprefix ruleだけで完全に`forbidden`へ分類できるとは扱いません。family全体を禁止できない場合はHookでvariantをdenyし、execpolicyではfamily単位`prompt`をfallbackとして使います。これによりHook failure時にも無承認実行を防ぎますが、ユーザー承認後まで機械的に禁止する保証とは区別します。

各`prompt` / `forbidden` ruleは、Codex execpolicyの`match` / `not_match`例に加え、sandbox approvalやHook由来の停止と区別できる短いrule固有`justification`を持たせます。`rules-auto-net`は追加しません。

CIでは固定版Codex CLIを使って`codex execpolicy check --rules ...`を実行し、少なくとも代表的な「rule未一致」 / `prompt` / `forbidden`をCodex自身のparser / evaluatorで確認します。variant-dependent familyではoption位置を前後へ変えたfixtureも評価し、Hook denyとfamily-level `prompt` fallbackの両方を確認します。独自execpolicy parserは作りません。

execpolicy prefix ruleだけでnested shellや任意script内部のcommandまで完全に捕捉できるとは扱いません。Bash tool inputに現れるopaqueなnested shell wrapperはPreToolUseでdenyし、外部MCPや任意program内部のmutationはrepository-local execpolicyの保証範囲外と明記します。

### Hook trust

`docs/reference/codex-safety-harness.md`には次を記載します。

- Codex 0.160.0のHook trust hashはnormalizedされたHook設定identityから計算され、参照先`.mjs` / `.ps1`のsource本文はhash対象ではない。`Trusted`表示をHook source未変更の証拠として扱わない
- `.codex/config.toml`等のHook定義を変更した場合はCodex interactive CLIで`/hooks`を再確認する
- Hook sourceを変更した場合は、既存trustが自動失効する前提を置かず、該当contract testとfresh trusted Codexでのruntime受入を再実行する
- Hookの定義元、command、matcher、timeout、trust状態を確認する
- 実行環境とtrust確認時の`CODEX_HOME`を一致させる
- contract test PASS、Hook sourceの変更確認、実Codex上のtrust / runtime確認は別の証拠として扱う
- Hook source digestをcommandへ埋め込む独自revision機構は追加しない。Hookは絶対的なsecurity boundaryではなく、永久禁止操作はexecpolicy `forbidden`でも防御する
- `--dangerously-bypass-hook-trust`を通常運用へ入れない

## 実装時の注意

初回の一括formatは変更file数が大きくなります。これは今回の目的上許容しますが、format変更と意味変更を混ぜません。

安全Hookはsecurity-sensitiveです。parser全体を書き直さず、移植元で検証済みのshell / Git解析を維持しながら、今回確定したapproval / execpolicy境界に必要な箇所だけ調整します。direct / compound commandは既存parserを維持し、nested shellは再帰解析せずopaque wrapper自体をdenyします。Codex 0.160.0ではPreToolUseへtool-level `workdir`とper-call `shell`が渡らないため、state-changing Git commandは対応するsession default shell上でcommand内にcanonical project rootへのfail-closed移動を含め、その直後のbare Git subcommandへ統一します。`git -C`等のrepository context overrideは使わず、Hook process cwdを実行対象repositoryの証拠にもしません。shell identityはHookが機械的に証明できないため、対応default shell＋shell overrideなしをruntime / 行動契約とし、対象外runtimeをfresh acceptanceでPASSにしません。これによりG10のrepository固定とexecpolicyのbare Git prefixを同時に成立させます。protected branch解決とG10は上記契約を正本にします。execpolicy / HookはBash tool経路のguardrailであり、Hook failure、shell override、任意program内部、外部MCPまで絶対防止できるとは扱いません。変更したpolicy caseはcontract testを同時に更新します。

一方、移植元のハーネス全体を正しい前提として扱いません。現行Codex仕様で旧aliasや不要な運用になっている箇所は現在仕様へ合わせます。

`AGENTS.md`、Skill、referenceを増やすこと自体を目的にしません。同じ契約を複数文書へコピーせず、rootにはroutingと常時必要な規則、詳細は担当文書へ置きます。移植元SkillのRun Artifact / Repository mapping等も名前だけ消すのではなく、今回の保持 / 置換 / 削除表に従って意味契約を閉じます。

custom agentについては、Codex 0.160.0のrole overrideで実際に強制できる設定と、`developer_instructions`による行動契約を混同しません。実装者がchild TOMLの`sandbox_mode`や`agents.enabled`をsecurity boundaryと誤認しないようにします。

QA Skill本体の`skills/**`と開発Agent用`.agents/skills/**`は別責務です。開発SkillをQA workflowの19 Skillへ追加せず、既存Skill countや評価datasetを変更しません。

lintで実コード修正が必要になった場合は、可能ならformatの機械的差分と分けて確認できる状態にします。特に`F`系の指摘を直す際は、unused importに副作用がないこと、public importとして使われていないことを確認してから削除します。

Markdown / JSON / YAMLのformatは、見た目の統一より既存契約の維持を優先します。全件formatできる場合は全件を対象とし、問題がある箇所だけ最小限の例外にします。
