# QA遂行効率の比較評価・受入契約

## 目的と責務境界

この文書は、[QA全工程Plan](./2026-11-07_170134_qa-full-process-implementation.md)で予定するSkill構成とworkflowが、**QA品質・追跡性・安全性を維持しながら、重複分析・不要なSkill起動・人手の再確認・無関係scopeの再処理を減らせること**を、実Agentの記録で確認するための実装契約である。

- **Skill構成・workflowの効率評価**：既存`EVALS.md`のワークフロー統合評価および実Agent評価の担当。評価データの取得と比較は実装・評価側で行い、個々のQA活動を担当するSkillへbenchmark責務を移さない。
- **案件のQA活動評価**：新設予定`test-evaluation`がQA活動の工数・品質・改善・再測定を担当する。workflow設計の開発時評価と混同しない。
- **取得元**：既存Agent実行ログ、Skill発火観測、owner成果物、workflow／run状態、GitHub Actions・実runner証拠、利用者が記録した人間の確認・修正時間。元データは読取専用で比較し、評価値で実テスト結果を書き換えない。
- **外側の責務**：Agent起動・常時監視・通知・定期実行はSkill外。モデル・CLI・ハーネスを固定せず、実際に採用した実行環境を各測定記録に残す。

**実装完了**、**QAの品質受入**、**効率化の実証**は別々に判定する。機能と品質が通っただけで時間短縮や効率改善を実証済みと表示しない。

## 比較対象と実行条件

### 必須シナリオ

対象は`ryu-yoshikawa-pro-vision/qa-training-store`の受入開始時に固定したcommit、既存Playwright／Vitest、および必要な独立fixtureとする。実製品の受入結果とfixture結果は別集計とする。

1. **初回QA**：同一の製品source・仕様・QA目標から必要な分析・正式設計・実行準備・結果報告へ至る。
2. **変更なしの再依頼**：同じsource revision・依頼scopeで実行し、検証済み成果物を再利用できる。
3. **局所コード変更**：特定の機能にだけ影響する差分を与え、関係する成果物・テストのみを再確認する。
4. **仕様資料だけの改版**：製品コード不変の条件で仕様Authorityの変更を入力し、該当scopeのみ再分析・再設計する。
5. **中断後の再開**：保存途中・実行中断・別セッション再開を与え、証拠を維持しながら重複操作を防ぐ。

各シナリオで評価する成果物の品質基準・要求範囲・既知の異常例を、**評価対象Agentとは独立した期待結果**として先に保存する。比較の都合で正式なQA対象や必要な安全対策を省かない。

### 比較基準

- 比較元は、同じQA目的を実際に達成できる**既存Skill経路または記録済みの人手手順**とする。比較元のsource revision・作業内容・品質判定・工数の取得根拠を明示する。
- 既存構成では必要なQA活動自体が実行不能な場合、機能追加の受入として評価し、その範囲を「従来比の効率改善」として計算しない。比較可能な共通活動についてのみ負担の増減を比較する。
- 比較元と変更後の実行に、同じsource／入力scope、QA目的、期待品質、対象テスト集合、必要な環境・権限を使用する。テストデータ・外部依存・runner設定の違いがある場合は、影響を記録して比較不能を判定する。
- Agentの実行にばらつきがあるため、同等条件の独立した実行を各シナリオで複数回記録する。実行回数・個別結果・分布を保持し、良い結果だけを選んで比較しない。model／CLIは固定しないが、使用した設定やversionの差は記録する。

## 必須の測定と成果物

### 実行・コスト・人間の作業

- **処理時間**：Agent処理開始・完了、各Skillの開始・終了、必要なrunner待機・再実行、成果物保存・読戻し。壁時計時間と重複した並行処理時間を混同しない。
- **Agent利用量と費用**：Skill呼出回数・再起動回数、利用可能なtoken／request／課金情報を元の計測元・単位・課金条件とともに取得する。取得できない値は推測値で置き換えず`未測定`とする。モデル・料金プランの違う費用を単純合算しない。
- **人間の確認工数**：承認を除いた確認・差戻し・手直し・再調査と、必要な承認／意思決定の時間を分けて記録する。記録されていない人間の介入を0分としない。
- **再処理**：重複したSkill発火、同じsourceの再読込・同一分析の再生成、再試行attempt、不要な再検証、作成・改版した成果物件数をscope／owner／理由で追跡する。
- **成果物再利用**：対象scope内の有効な既存成果物数、再利用できた数、再生成・要再検証・blockedとした数、それぞれのsource revision・判定根拠を保存する。品質未検証の再利用を効率化の分子に入れない。

### 品質・安全性の制約

- **独立基準の達成**：重要な要求・テスト条件の欠落、誤った期待結果、誤PASS、未実行／未確認の完了扱い、Risk・traceability・現在性の不備を評価する。
- **証拠の完全性**：必要な成果物、元run・cleanup・承認・source revision、未解決事項の取得完全性を検証する。
- **安全性**：秘密情報、認証・権限、既存変更の保持、二重副作用・二重Issue登録、競合拒否・中断復旧を検証する。

比較で処理量が減少しても、これらの必須品質・安全基準を満たさない試行を「効率改善」と判定しない。

### 評価の保存情報

各試行の評価記録は、シナリオID、比較元／変更後の区分、対象source・QA目的・品質基準、実行環境、Agent・Skillの版、開始／終了、owner成果物のref／revision、実run refs、計測値と取得元、未測定理由、再試行／中断、独立品質判定と結果を保持する。

既存の`EVALS.md`の評価レイヤー／開発時評価成果物を使用し、通常のQA成果物へ新しい汎用ベンチマーク台帳を追加しない。開発評価に必要な記録形式と実行手順は、実装時に評価基盤へ追加する。

## 比較方法と判定条件

1. **同じ分母**：対象scope、QA目的、対象成果物・テスト集合と必要な完了条件を比較元／変更後で揃える。新しいSkillが追加した有効な検証は、工数が増える場合も品質上の根拠を含めて分離して扱う。
2. **正常系と異常系**：初回、変更なし、変更あり、中断・再開を別々に比較する。変更なしで無意味な再計算が発生しないか、局所変更で無関係scopeの再実行が発生しないかを独立に検証する。
3. **実測に基づく差**：処理時間・Agent利用・人間の工数・再利用と再処理を、記録済みの元データから差分計算する。複数試行では中央値・ばらつき・最も負担の大きい試行を併記し、平均だけで悪化を隠さない。
4. **結果の分類**：品質・安全の必須基準を満たした比較可能な試行だけ効率比較の根拠とする。効率指標が改善した場合にのみ当該指標の改善を主張する。品質向上による必要な追加処理と、不必要な重複処理を区別し、理由のない負担増は該当Skill・handoff・保存・再検証に戻して修正する。
5. **受入の独立判定**：全機能・安全受入が完了しても、比較元欠落・重要指標未測定・条件不一致なら効率化は`未実証`として記録する。品質・安全を維持し、少なくとも対象とする効率指標で実測改善が確認できた場合のみ`効率化を実証`とする。目標に対する費用増加を許容するには、案件の承認済み基準と品質上の効果を記録する。案件固有の費用上限を全案件共通に固定しない。
6. **悪化時の差戻し**：説明できない処理・確認負担の増加や誤発火があれば、元のログと成果物参照から発生ownerを特定し、必要なSkill統合・routing修正・保存／再利用条件・実行計画の改版を行って同条件で再測定する。単に数値を報告しただけで効率化の受入を閉じない。

## 実装対象・検証手順

- `EVALS.md`のワークフロー統合評価・実Agent受入、既存評価データ・記録処理に上記5シナリオの比較元・変更後・独立品質評価・計測契約を追加する。
- Agent本体の起動・課金データの取得は使用環境の実能力に従う。直接取得できない値は元データの範囲と未測定理由を保持し、利用可能な手動記録を明示する。
- [継続workflow受入Plan](./2026-11-07_170134_qa-full-process-implementation_03_workflow-and-acceptance.md)の実Agent／実runner証拠、[詳細Plan04](./2026-11-07_170134_qa-full-process-implementation_04_workflow-runtime-and-regression.md)の再開、[詳細Plan05](./2026-11-07_170134_qa-full-process-implementation_05_testware-execution-and-quality.md)の安全な編集、[詳細Plan06](./2026-11-07_170134_qa-full-process-implementation_06_static-testing-and-improvement.md)のQA Knowledge再利用を測定対象に含める。
- 比較元と変更後のraw記録、観測できない項目、異常系・最悪値・品質差、差戻し後の再測定を、レビューできる成果物として保存する。固定製品commit・独立fixtureの結果を混同しない。

## 完了条件

1. 5シナリオの比較元・変更後・独立した品質基準・実測記録が取得され、各ケースの比較可否と理由が判定できる。
2. Agent処理時間、Skill起動・再起動、人間の確認・修正、再分析・再実行、再利用成果物、品質・追跡性・安全性について、取得元と測定単位を保持する。測定不能は0件・0円・0分としない。
3. 機能受入／品質受入／効率化実証を独立して判定する。品質低下による時間短縮、fixture成功のみ、比較不能を効率化成功として扱わない。
4. 処理負担が悪化した場合は該当owner・再実行／引継ぎの原因を追跡し、是正と同条件の再測定を行う。改善が実測できない範囲を完了と報告しない。
