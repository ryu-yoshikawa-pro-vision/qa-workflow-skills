## 詳細

### Q-01（ブロッカー・保留）統合時の許容上限超過

- 根拠: BR-CART-002「SKU単位で数量を合算します。許容上限を超える数量分、非公開商品、会員ランク不足の商品、無効なSKU、在庫0の商品は統合対象から除外し、その理由を明示します。」
- 矛盾ではないが解釈が2通りある:
  - (a) 超過分の数量だけ除外し、上限までは統合する（部分統合）
  - (b) 上限を超えるSKUは統合全体から除外する
- 「許容上限」の定義もない（BR-CART-001の上限と同一とみなすのは自然だが、仕様上の明示はない）。
- 扱い: 保留。部分統合の期待結果（TCN-CART-009 CI06 の超過条件、TCN-CART-008 CI05 の合算結果の上限）は確定しない。他の除外条件（非公開、会員ランク不足、無効SKU、在庫0）の期待結果は影響を受けないため、先へ進める。
- 承認者: 製品仕様の決定者。

### Q-02（ブロッカー・保留）カートバージョン

- 根拠: AC-CART-002「統合結果、除外理由、**カートバージョン**、およびゲストカートの状態が仕様どおり一致すること。」
- cart.md の BR・機能一覧・UI規約にはカートバージョンの定義がない。checkout-and-payment（BR-CHECKOUT-002）はカートバージョンの不一致で注文を止める規則を持つため、バージョンの増加条件が不明だと両機能の期待結果が決まらない。
- 扱い: 保留。バージョン値を期待結果として書かない。統合の他の結果（明細、除外理由、ゲストカート状態）は先へ進める。

### Q-03（要確認・保留）価格変更の承認

- 根拠: BR-CART-003「価格変更が発生している場合は、会員の承認が得られるまでチェックアウト手続きへ進めません。」
- 未規定: 承認の操作主体（ゲストは「会員」ではないため承認できない、とみなすか）、承認の画面と操作、承認後に確定する価格（承認時点の価格か）、価格が再度変わった場合、価格が元に戻った場合。
- 扱い: 「承認がなければ進めない」は仕様どおりに確定できるため検証可能。承認後の挙動と、ゲストの扱いは保留。

### Q-04（要確認・保留）数量の不正入力

- 根拠: BR-CART-001 は「上限超過は拒否」「0で削除」のみを定める。
- 未規定: 負数、小数、非数値、空入力の扱い。
- 扱い: 保留。「不正入力を拒否して数量を維持する」と書くことは、仕様に明示がないため期待結果として確定しない（推測補完になる）。

### Q-05（要確認・保留）在庫減少後の数量

- 根拠: BR-CART-001「数量の自動補正を行わずに操作全体を拒否」（操作時の規則）。BR-CART-003「在庫数を再検証」（表示・開始時の規則）。
- 未規定: 再検証で「既存の数量 > 現在の在庫数」となった明細は、自動補正するのか、問題明細として扱うのか。操作時の補正禁止を再検証へ拡張してよいかが不明。
- 扱い: 保留。TCN-CART-017 CI02 の期待結果を確定しない。

### Q-06（仮定中）統合規則の正本

- authentication.md は「ゲストカート統合について定義します」と記載するが、規則の本体（BR）は cart.md の BR-CART-002 にある。
- 仮定: cart.md を統合規則の正本とする（cart.md 冒頭「ログイン時のゲストカート統合仕様を定義します」の記載に従う）。authentication 側は統合の起動（ログイン境界）の仕様として参照のみ。
- 承認待ち。承認されない場合は両文書の記述を比較し直す。

### Q-07（要確認・保留）空の統合

- 未規定: ゲストカートが空（明細0件）の状態でログインした場合、統合元は abandoned になるか。会員カートが無い場合の扱い。
- 扱い: 保留。ただし空の統合で「明細が増えない」は仕様から導けないため、この条件でも期待結果は書かない。

### Q-08（要確認・保留）問題の解消操作

- 根拠: AC-CART-003「ユーザーによる承認または明細の修正が行われない限りチェックアウトへ進めない」。
- 未規定: 問題種別と解消操作の対応（どの問題が「修正」で解消できて、どれが「削除」のみか）。
- 扱い: 保留。「明細を削除すると問題が解消される」は一般的には導けるが、仕様上の明示は「修正」のみのため、削除での解消の期待結果も保留にする（削除は明細の除去であり、保守的に検証対象とするが、解消の期待結果は承認後に確定する）。

### Q-09（要確認・保留）除外理由の複数表示

- 根拠: BR-CART-002「その理由を明示します」。
- 未規定: 複数理由が同時に該当するときの表示。
- 扱い: 保留。単一理由の場合の表示は、理由と原因が一致することを期待結果とする（確定）。

### Q-10（要確認・保留）合計金額の計算

- 根拠: cart.md UI規約「カート明細には…合計金額…を表示」。
- 未規定: 計算式（現在価格×数量の総和か、会員割引・セール・配送料の扱い）。
- 扱い: 合計が「表示される」ことは確定する。計算結果の数値は保留。

### Q-11（仮定中）二重実行防止

- 根拠: cart.md「更新処理の実行中は同一カートに対する変更操作の二重実行を防止する」。
- 未規定: 防止の方法（拒否、直列化、ボタン無効化）。
- 仮定: 期待結果は「同一の操作が二重に反映されない」だけとする。方法は問わない。
- 承認待ち。

### Q-12（提案）チェックアウト開始時の定義

- 「チェックアウト開始時」（BR-CART-003）と、checkout-and-payment の「注文作成直前」（BR-CHECKOUT-002）の境界が一致するかを明確にすると、再検証の境界を一意にできる。
- 扱い: 提案のみ。TCN-CART-016 では「チェックアウトへ進む直前」として扱う（仮定ではなく、既存表現の範囲内）。

## 仕様間の整合性確認

- roles-and-permissions.md（カート: ゲスト〇、顧客〇、オペレーター×、管理者×）と cart.md（ゲストまたは会員のみ）は一致する。
- state-and-scenarios.md（Cart: active → consumed / abandoned、終端からの変更禁止）と cart.md BR-CART-002（統合元の abandoned）は一致する。
- cart.md の BR-CART-003（承認までチェックアウト不可）と state-and-scenarios.md の再検証境界は一致する。
- 矛盾は検出していない。解釈の分岐は Q-01・Q-02・Q-05 にある。
