# 05 テスト観点・条件（test-condition-design）— カート

対象 / 実行範囲: テスト条件・カバレッジ基準・カバレッジ項目（`テスト設計`）
入力: `04_test-requirements.md`（TR-CART-001〜011）、`01_spec-authority.md`、`02_question-analysis.md`、`03_test-analysis.md`
注: 手順・具体的テストデータ・期待結果の文言は `test-case-design` で確定する。ここでは「何を、どの条件で、どの根拠で確認するか」と、判断に必要な具体境界値までを示す。

記法:

- CI = カバレッジ項目。`TCN-CART-0xx-CIyy`。
- 優先度は関連TRの最高優先度を継承（すべて「高」「中」のいずれか）。
- 「保留」は承認または回答まで期待結果を作らない項目。

## TCN-CART-001 数量上限の境界（TR-CART-001 / 高）

- 技法: 境界値分析（3-value）、Domain Testing（2変数: 在庫数・購入上限数）
- 根拠: SPEC-CART-001、AC-CART-001
- カバレッジ基準: 上限を決める条件（在庫数・購入上限数・99）ごとに、上限-1・上限・上限+1 を通す。2変数の境界（在庫数 = 購入上限数、在庫数 < 購入上限数、在庫数 > 購入上限数）の各 ON/OFF 点を通す。
- 期待結果の根拠（観測すること）: 上限以内は受理。上限超過は操作全体を拒否し、数量を補正せず、変更前の数量を維持する。

| CI   | 条件                                                       | 境界の値（例）                                      | 基準                                         |
| ---- | ---------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| CI01 | 上限 = 在庫数（在庫数 < 購入上限数 < 99）                  | 合算数量 = 在庫数-1 / 在庫数 / 在庫数+1             | 3-value BVA                                  |
| CI02 | 上限 = 購入上限数（購入上限数 < 在庫数 < 99）              | 合算数量 = 購入上限数-1 / 購入上限数 / 購入上限数+1 | 3-value BVA                                  |
| CI03 | 上限 = 99（在庫数 > 99、購入上限数 = 99）                  | 合算数量 = 98 / 99 / 100                            | 3-value BVA                                  |
| CI04 | 在庫数 = 購入上限数 < 99（同値の境界）                     | 合算数量 = 上限-1 / 上限 / 上限+1                   | Domain（ON/OFF）。二重に減算しないことの確認 |
| CI05 | 在庫数 > 購入上限数 かつ 購入上限数 < 99（購入上限が最小） | 購入上限数 側の ON/OFF 点                           | Domain（S > P の側）                         |
| CI06 | 在庫数 < 購入上限数 かつ 在庫数 < 99（在庫が最小）         | 在庫数 側の ON/OFF 点                               | Domain（S < P の側）                         |
| CI07 | 在庫数 = 0（上限 0）                                       | 追加数量 1                                          | 同値（上限0のクラス）                        |

- 注: CI01〜CI03 の具体値は、各上限を決める条件が成立する整数の組で確定する（`test-case-design`）。
- 注（2026-11-13 変更差分）: 製品の契約定数 `INPUT_LIMITS.maxCartQuantity` が100になった（実効判定は99のまま）。CI03 の「合算数量100は拒否・数量維持」は SPEC-CART-001 の正本どおりで期待結果は不変。実機で100が受理された場合は欠陥候補として扱う。値の正否は Q-CART-011 / P-CART-15 で保留（`07_change-impact.md`）。
- 注: 2変数の ON/OFF 点は整数ステップ1で表現でき、丸めは不要。

## TCN-CART-004 明細のCRUDとロール（TR-CART-009、TR-CART-003 / 中）

- 技法: CRUD（完全性マトリクス）、状態を変える一連操作
- 根拠: SPEC-CART-008、SPEC-CART-001/002
- カバレッジ基準: 明細エンティティ × 操作（Create＝追加、Read＝表示、Update＝数量変更、Delete＝削除・0） × 利用者（ゲスト、customer、operator、admin）の全セル。

| 操作 \ 利用者      | ゲスト                | customer | operator             | admin                |
| ------------------ | --------------------- | -------- | -------------------- | -------------------- |
| Create（追加）     | 許可（SPEC-CART-008） | 許可     | 不可（`/cart` 拒否） | 不可（`/cart` 拒否） |
| Read（表示）       | 許可                  | 許可     | 不可                 | 不可                 |
| Update（数量変更） | 許可                  | 許可     | 不可                 | 不可                 |
| Delete（削除・0）  | 許可                  | 許可     | 不可                 | 不可                 |

- 不可の根拠: SUP-4 `screen_list.md` L75、SUP-9 `roles_and_permissions.md` L37（カート追加）。正本 `roles-and-permissions.md` のカート列は未確認（INF-CART-009）。
- 一連シーケンス（状態を変える C/U/D のみ）:
  - CI-S1: 追加 → 数量変更 → 0で削除（全明細が無くなる → 空状態）
  - CI-S2: 追加（別SKU） → 削除 → 残りの明細が保持される
- 注: R（表示）は完全性マトリクスで担保し、シーケンスには含めない。
- 保留: Create の「0」指定（Q-CART-002、TCN-CART-003 CI06 と同じ）。

## TCN-CART-005 ゲストカート統合の判定（TR-CART-004 / 高）

- 技法: デシジョンテーブル
- 根拠: SPEC-CART-003、AC-CART-002。上限は INF-CART-001（承認待ち、Q-CART-004）。
- 条件（入力）:
  - C1: SKUが有効
  - C2: 商品が公開
  - C3: 会員ランクを満たす
  - C4: 在庫数 > 0
  - C5: 会員カートの同一SKU数量に上限余地がある（合算が上限以内）
- 動作（期待される判定）:
  - A1: 全量統合
  - A2: 上限余地まで統合し、超過分を除外（超過件数を表示）
  - A3: 明細を除外（理由を表示）

| ルール | C1       | C2 | C3 | C4 | C5                                  | 判定                        | 根拠 / 扱い                                          |
| ------ | -------- | -- | -- | -- | ----------------------------------- | --------------------------- | ---------------------------------------------------- |
| R1     | Y        | Y  | Y  | Y  | Y                                   | A1 全量統合                 | SPEC-CART-003                                        |
| R2     | Y        | Y  | Y  | Y  | N（余地あり・一部のみ）             | A2 余地まで統合、超過分除外 | SPEC-CART-003。上限は INF-CART-001（P-CART-01）      |
| R3     | Y        | Y  | Y  | Y  | N（余地ゼロ：会員カートが既に上限） | A2 統合0、全量が超過除外    | 同上（境界）                                         |
| R4     | N        | Y  | Y  | Y  | -                                   | A3 除外（無効SKU）          | SPEC-CART-003                                        |
| R5     | Y        | N  | Y  | Y  | -                                   | A3 除外（非公開）           | SPEC-CART-003                                        |
| R6     | Y        | Y  | N  | Y  | -                                   | A3 除外（会員ランク不足）   | SPEC-CART-003                                        |
| R7     | Y        | Y  | Y  | N  | -                                   | A3 除外（在庫0）            | SPEC-CART-003                                        |
| R8     | 複数が N | -  | -  | -  | -                                   | A3 除外（全理由）           | 除外判定は確定。**理由の表示順は保留**（Q-CART-006） |

- カバレッジ基準: 各ルールを1つ以上の代表で通す。R8 は単独の除外理由ごとのルール（R4〜R7）に加え、2つ以上の除外理由が重なる代表を1つ通す（順序の確認は保留）。
- 統合サマリー（追加件数・上限超過件数・除外件数）の表示: SUP-6 L157（補助）。CI として作るが期待結果の文言は `test-case-design` で確定する。

## TCN-CART-007 再検証の問題種別と表示時・チェックアウト開始時（TR-CART-006 / 高）

- 技法: 組合せ（2-wise）、デシジョンテーブル（チェックアウトのブロック）
- 根拠: SPEC-CART-005、SPEC-CART-007、SPEC-CART-011
- 問題種別（P）: P0 問題なし、P1 公開停止、P2 購入権限不足（会員ランク）、P3 価格変更、P4 在庫不足（在庫0を含む）、P5 無効SKU
- 因子: 明細1の問題種別（6値）、明細2の問題種別（6値）、再検証の契機（表示時／チェックアウト開始時）

### CI（2-wise）

- 2つの明細の問題種別の全ペア（6×6＝36ペア）、契機との全ペア（2×6、2×6）を通す。
- 成立不能の組合せはない（同一明細に複数の問題が同時に成立する場合を除く。その場合は別途、同一明細の複合を CI-M で扱う）。
- CI-M（同一明細の複数問題）: P3 と P4 が同一明細で同時に成立する場合の表示と、チェックアウトのブロック。
  - 表示の各問題の提示は仕様上必要（SPEC-CART-011）。**問題の表示順は保留**（Q-CART-006）。

### デシジョンテーブル（チェックアウトのブロック）

| ルール | 問題あり                    | 価格変更 | 承認            | 修正                  | 判定                                         | 根拠                                                               |
| ------ | --------------------------- | -------- | --------------- | --------------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| R1     | N                           | -        | -               | -                     | チェックアウトへ進める                       | AC-CART-003                                                        |
| R2     | Y（価格変更のみ）           | Y        | Y（会員の承認） | -                     | 進める                                       | SPEC-CART-006                                                      |
| R3     | Y（価格変更のみ）           | Y        | N               | -                     | 進めない                                     | SPEC-CART-006                                                      |
| R4     | Y（P1/P2/P4/P5 のいずれか） | -        | -               | N                     | 進めない                                     | SPEC-CART-007                                                      |
| R5     | Y（P1/P2/P4/P5 のいずれか） | -        | -               | Y（明細の修正・削除） | 進める（修正後に再検証）                     | SPEC-CART-007                                                      |
| R6     | Y（P3 と P1 等の複合）      | Y        | Y               | N                     | 進めない（承認だけでは他の問題は解消しない） | SPEC-CART-007。AC-CART-003 の「承認または修正」の解釈（P-CART-05） |

- 注: R6 の解釈（承認だけで複合のブロックが解けるか）は AC-CART-003 の文言からは「承認または修正が行われない限り」と読めるが、個別の問題ごとの解消か全体かは未規定。承認の単位（P-CART-05）に依存するため、R6 は承認待ちとする。

### 価格変更の方向

- 同値クラス: 価格上昇 / 価格下降 / 変更なし。`変更なし` は再検証で問題なし（R1）。
- 上昇・下降のどちらも SPEC-CART-006 の「価格変更が発生している場合」に該当する（同じ規則で扱う）。
