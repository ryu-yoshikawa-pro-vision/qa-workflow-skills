# テスト分析: カート

## テスト分析範囲

- 対象機能 / 変更: カート（追加・数量変更・削除、上限判定、表示時・開始時の再検証、ログイン時のゲストカート統合）。新規・変更の区別は、本リポジトリ上の変更差分を入力にしていないため「仕様対象の全体」として扱う
- 案件固有のテスト目的 / 重点: 上限判定（自動補正禁止）、ゲストカート統合、再検証による購入ゲート
- テストレベル: システムテスト（既定）。対象: Web（デスクトップ）と Android（ネイティブ、製品スコープ上の保証範囲）
- 観測方法: 画面表示（数量・上限・問題点・合計・通知）、チェックアウト開始の可否。状態の準備はシナリオ制御（`cart-with-invalid-items` 等）を前提にできる（`state-and-scenarios.md`）
- 環境制約: 決済・注文作成はチェックアウト側。本件の期待結果には使わない
- 対象外: 注文データ生成、決済、チェックアウト画面の詳細、管理画面からの在庫・価格変更の操作
- ブロッカー: 局所のみ（Q-001 カートバージョン規則、Q-002 画面上の版競合）。`02-question-analysis.md` 参照
- 対象 / 実行範囲: テスト分析

## 選択したテスト技法

| テスト技法                        | 適用領域                                                                                                          | 選択理由                                                                               | 関連プロダクトリスク / 現在有効な仕様根拠              | `test-condition-design`への着眼点                                                                 |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 境界値分析（BVA）                 | 上限 L（在庫・購入上限・99の最小値）と合算後の数量、0と1                                                          | 数量の上限は単一の数値境界であり、BVAが直接適用できる                                  | RISK-001, RISK-002 / SPEC-001, SPEC-002                | 上限ちょうど（accept）、上限+1（reject、補正なし）、0（削除）。L の値は具体化しない               |
| 同値分割                          | L の決定元（在庫、購入上限、99）、商品状態（公開/非公開）、会員ランク、在庫（0 / 正）                             | 有効・無効の区分が明確で、代表値で区分を覆える                                         | RISK-001, RISK-003, RISK-004 / SPEC-001, SPEC-004      | 「どの上限が最小か」の3区分を別々に覆う。ランクは同等以上/不足の境界                              |
| デシジョンテーブル                | (1) 統合結果（既存明細の有無・上限・ゲスト数量）、(2) 再検証の結果（問題種別×検出境界×解決方法）、(3) 利用者×操作 | 複数条件の組合せで結果が決まり、ルールが明確に列挙できる                               | RISK-003, RISK-004, RISK-006 / SPEC-003〜007, SPEC-008 | 統合は4ルール程度（既存なし、既存+ゲスト≤上限、超過、既存が上限）。再検証は価格変更の承認ゲート等 |
| 状態遷移                          | カートの active → abandoned / consumed、チェックアウト開始の進行可否                                              | 終端状態からの変更不可、承認前の進行不可が状態の問題として表現できる                   | RISK-009, RISK-004 / SPEC-012, SPEC-006                | 有効遷移（統合で abandoned）と無効遷移（終端からの変更）                                          |
| 分類木 + 制約付き組合せ（2-wise） | 再検証の要素（問題種別、検出境界、解決方法）                                                                      | 3要素で組合せが多く、承認は価格のみ可能という制約がある                                | RISK-004 / SPEC-005〜007, UNK-003（Q-003）             | 承認は価格変更のみ（制約）。承認手段の仕様が未確定のため、承認の組合せはブロック中                |
| エラー推測                        | 二重実行、古いバージョンでの操作                                                                                  | 二重実行防止（SPEC-011）が仕様にあり、版競合は未定義のため経験的に確認すべき対象になる | RISK-005 / SPEC-011, UNK-002（Q-002）                  | 連続操作。版競合の期待結果は Q-002 回答まで保留                                                   |

採用しない技法（理由）:

- ランダムテスト・メタモルフィックテスト: 明示的な入出力関係や分布要件がない
- 構文ベーステスト: 入力文法の定義がない（数量は整数の範囲として扱う）
- スキーマ / UI パターン: 画面状態は SPEC-010 の3状態で既に定義されている
