# テスト分析: カート（SCREEN-STOREFRONT-CART）

## テスト分析範囲

- 案件固有のテスト目的 / 重点: ゲスト・会員のカートで、数量の上限判定（自動補正なし）、ログイン時統合、表示時・チェックアウト開始時の再検証と、問題がある明細のチェックアウトへの持ち越し防止を確認する。
- テストレベル: システムテスト（既定）。UI操作と画面確認はweb-desktop・androidで行う。統合・上限判定の内部結果（明細の数量、Cart状態）はAPI・データ状態の観測で補う（非E2E / 結合の層を併用する余地あり。層の割当は`test-architecture-design`の判断）。
- 環境制約: 観測に必要なもの — (a) 2つのブラウザ状態（ゲストとログイン済み会員）、(b) 在庫・購入上限・公開状態・会員ランクを操作できるテストデータ（シナリオ `cart-with-invalid-items` 等）、(c) Cart状態（active / abandoned）を読める手段（API / DB）。未確認。
- 対象外: 注文データへの変換、注文確認・注文作成時の再検証（チェックアウト側）、ゲスト購入（Phase 2）、`consumed`状態、ネイティブ実装の詳細、実装コード。
- ブロッカー: `02-question-analysis.md` の Q-001, Q-002, Q-005, Q-006, Q-009。局所ブロックのみで、他の条件は継続可能。
- 対象 / 実行範囲: テスト分析（spec-analysis の SPEC-001〜019 を根拠）

## 所見（分析の結論）

- 仕様根拠が明確なSPEC（上限・統合の主要規則・再検証・権限・画面状態）を中心に、数量上限、統合、再検証の3領域を高優先度とする。
- 未確定のUNKNOWN（価格変更、版、合計、モバイルWeb、統合失敗など）に依存する条件は、条件として保持しつつ期待結果を保留にする。これは`02`の分類と一致する。
- test-analysis で新たに見つかった2件（空カートの統合、ランク不足商品の追加）は`02`へ追加した（Q-012, Q-013）。
- 実行のための環境要件（テストデータ・Cart状態観測）は`environment_requirements`の作業として別途整理する。
