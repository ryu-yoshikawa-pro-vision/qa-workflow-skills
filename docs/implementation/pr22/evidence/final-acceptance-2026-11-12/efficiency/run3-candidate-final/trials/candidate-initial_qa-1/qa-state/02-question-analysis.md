- 対象 / 実行範囲: カート機能。入力は`01-spec-analysis.md`の`UNK-CART-001〜010`、`INF-CART-001〜003`、および仕様内の矛盾
- 作成日: 2026-11-13

## 1. 分類の方針

下流（テスト要求・テスト条件）の成立に必要かで分類した。

- `ブロッカー`: 回答がないと、影響するテスト要求の期待結果を仕様根拠から決められない
- `要確認`: 回答で設計は変わるが、現在の情報だけでも嘘をつかずに作業を続けられる
- `仮定可能`: 明示した暫定仮定で分析・ドラフトを続けられる。仮定は`SPEC`ではなく、PASS/FAILの根拠にする前に承認が要る
- `提案・任意`: 期待挙動を確定しない改善案

ブロッカーは影響するテスト要求に限定し、無関係なカート範囲は継続する。

## 4. 回答の正規化方針

回答を受けたら、期待挙動の根拠を次のどれかに正規化してから再開する。回答をそのまま期待結果に使わない。

- 情報源（`features/cart.md`）を更新 → `SPEC`として`spec-analysis`で再分析
- ステークホルダーが正式に確定 → `DECISION`として記録（決定事項の正本の既存IDを確認し、重複採番しない）
- 暫定の前提としてのみ合意 → `ASM-`として仮定の正本へ記録し、承認を得る（有効な`SPEC`を上書きしない）

回答の意味がどれか判断できない場合は、`DECISION`・`ASM`へ勝手に昇格させず再確認する。
