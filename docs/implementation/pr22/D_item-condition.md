## `no_change`再送で未解決状態が消える問題

### 原因と修正

- item／conditionの両`materialize()`は、前回artifactと今回候補のprojectionが一致すると、診断を計算する前に`status: no_change`、`valid: true`、`issues: []`を返していた。B分析がincomplete、source boundaryがpartial、候補currentnessがstale／unknown、conditionがunconfirmed／blockedでも、呼出元が最新結果だけを見ると未解決事項が見えなくなる。`test_no_change_replay_preserves_unresolved_analysis_state`で修正前の`issues=[]`を再現した。
- 早期returnを除き、毎回source・currentness・gap・状態診断と指標を計算してから`no_change`を返す。`status`は従来どおり候補内容の変更有無を示し、追加の`analysis_status`が`complete`／`incomplete`を表す。`valid`は構造検証のみを表す。
- itemは`issues`、stale／unknown／recheck item IDs、未表現feature IDs、候補識別率と測定不能理由を返す。conditionは`issues`、stale／unknown／unconfirmed／blocked／recheck condition IDsを返す。`crosscheck()`を同じ未完了artifactで再実行した結果も等価で、gap／incomplete状態を保持する。
- `candidate`は前回の検証済みpayloadをそのまま返し、stable ID・fingerprint・append-only historyを変更しない。履歴の連続イベント後の同一再送、旧v1のread-only読取、既存の誤artifact拒否テストも維持した。provider revision fixture（`provider-r1`／`provider-r2`）とcandidate fingerprintは別の値として扱う。
- `no_change`のwrite preconditionは`performed: false`／`provider_selected: false`のみで、provider write／CAS／readbackを要求しない。永続化成功や承認済みを意味しない。
- 両Skillの`SKILL.md`、`references/data-contract.md`、出力templateに意味を追記し、出力fixtureを更新した。`candidate_support.py`の共通処理変更は不要だったため両isolated packageの同一性を維持した。

### 回帰検証

追加したD runtime回帰は、B分析incomplete、partial source boundary、unknown area、未取得source、未表現feature、stale／unknown currentness、unconfirmed／blocked condition、無効previous artifact、completeな同一入力の複数再送を扱う。正常系ではstable ID・fingerprint・history・返却順序が変わらず、write要求が発生しないことを確認する。履歴同一性、source競合、旧v1互換性は従来の回帰テストでも再確認する。

## 廃止item・unknown feature状態の扱い

### 原因と修正

- **廃止itemのsource影響**：condition側`crosscheck()`は廃止itemをstale／unknownから除外していたが、item側`materialize()`／`impact()`は廃止itemも評価していた。廃止後に証拠sourceが改版されると、`stale_item_ids`／`recheck_item_ids`と`source_stale`、`status: incomplete`が恒久的に残り、廃止itemへ`source_changed` historyも追記された。廃止itemは再検証不要なので、`materialize()`は診断・recheck・`source_changed`追記から除外し、`impact()`は`impacted_item_ids`／`source_unknown_item_ids`／`unaffected_item_ids`に入れず`retired_item_ids`で別返却する。保存される`currentness`はvalidatorが証拠から再導出を要求するため従来どおり算出し、既存artifactと過去の`source_changed`eventの検証は変わらない。
- **unknown feature指標**：item側の確認済みactive母集団は`retired`以外の全feature（B status `unknown`を含む）で、unknownのfeatureが分母に入った測定済み率や`candidate_ready_unpersisted`／`analysis_status: complete`になり得た。condition側`crosscheck()`は既にunknown featureを非測定・未完了としていた。item側も`unknown_feature_ids`を返し、非blockingの`unknown_feature_status` issue、`analysis_status: incomplete`、指標status `not_measurable_unknown_feature_status`（rate／denominatorはnull）にする。unknown featureは未表現ならgapにも残る。
- `candidate_support.py`は変更せず、両isolated packageのbyte-identical同一性を維持した。`no_change`でも同じ診断を計算し、再送でunknown feature状態が消えない。

### 回帰検証

`test_retired_item_source_change_needs_no_revalidation`は、廃止item証拠のsource改版後の`impact`、`materialize`（stale／unknown／recheck空、`source_changed`非追加、`complete`、retired行のvalidate成功）と、同じ改版が生きたitemでは従来どおりstale・`source_changed`・`incomplete`になる対照を確認する。`test_unknown_feature_status_is_not_a_confirmed_active_denominator`は、unknown feature時の非測定・incomplete、`no_change`再送後の維持、全feature確認済みの対照で`measured`・rate 1.0を確認する。両テストは修正前コードで失敗し、修正後にPASSすることを確認した。

## readback hash契約と識別指標の分子

### 指摘1：readbackのhash契約

- **原因**：`validate_readback()`はproviderの`content_hash`を候補の`content_fingerprint`と比較していた。`content_fingerprint`は`content_fingerprint`欄自身を除くcanonical JSONのSHA-256だが、Aの既存保存（`artifact_graph.py`の`commit_qa_workflow_baseline_local`／`read_qa_workflow_artifact_revision_local`）が使う`artifact_sha256`は**保存した全バイト列**のSHA-256で、artifact revisionは`sha256:`＋その値のprovider所有値。そのため、候補artifact全体をそのまま保存した正常なreadbackが`readback_hash_mismatch`で拒否された。修正前コードで、保存バイト列の正しいhashを渡して`valid: false`になることを再現した。
- **修正**：両Skillの`validate_readback()`は、`content_hash`を**保存コンテンツhash**（候補artifact全体のcanonical UTF-8 JSONのSHA-256。両packageのbyte-identicalな`candidate_support.py`の`storage_content_sha256`）と比較する。`materialize()`の`write_precondition`へ`storage_content_sha256`と`storage_content_encoding: canonical-json-utf8`を追加し、Aのadapterが保存すべきバイト列と期待hashを知れるようにした。結果は`candidate_fingerprint`と`storage_content_sha256`を別fieldで返す。`content_fingerprint`は`validate_artifact`が従来どおり再計算して改変を検出する。
- **revision**：provider revisionはprovider所有で候補fingerprintから導かない。任意の`expected_revision`を渡した場合だけ`readback.revision`との一致を検査し、不一致は`readback_revision_mismatch`。未指定では従来どおりopaqueとして扱う。認証・承認・CAS・実読戻しは証明せず、`provider_authenticity`／`provider_cas`は`not_established_by_this_validator`のまま。
- **A（共有実装）への引継ぎ**：Aの既存コードは変更していない。D operationをA側へ登録するときは、adapterがD候補を`canonical-json-utf8`バイト列で保存するか、別の直列化を使う場合はadapter側で上記hashへ対応付ける必要がある。保存後は`artifact_sha256`相当を`readback.content_hash`、CAS結果のrevisionを`expected_revision`として`validate_readback`へ渡す。実provider・認可済みapproval・native CAS・独立readbackはA owner／PR #22で未接続（blocked）。

### 指摘2：識別指標の分子

- **原因**：item側`materialize()`のnumeratorは`retired`以外の全feature（B status `unknown`を含む）との共通部分で、非測定でもunknown featureが分子に入った。condition側`crosscheck()`も同様で、rate／denominatorだけをnullにしていた。さらに両側が別々の集計コードと状態名（`not_measurable_incomplete_population`／`not_measurable_incomplete_or_unknown_population`）を持っていた。
- **修正**：確認済みactive featureを「`retired`でも`unknown`でもないfeature」と定義し、両packageのbyte-identicalな`identification_coverage()`へ集計を一本化した。item／conditionの両方が同じ関数を使い同一のmetricを返す。`measured`の場合だけ`numerator`・`denominator`・`rate`を設定し、`not_measurable_*`（`zero_denominator`→`incomplete_population`→`unknown_feature_status`→`stale_or_unknown_items`の順）ではすべてnullにする。unknown featureは分子・分母のどちらにも入らず、未確認母集団を測定済みや100%として扱わない。condition側の状態名は`not_measurable_incomplete_population`へ統一した。未表現featureの一覧（`unrepresented_*`）とcrosscheckの完了gateは従来どおり。
- **影響範囲**：候補識別の指標だけを変更する。Authority、正式TCN／CI、Disposition、期待結果、正式カバレッジ、実行結果は生成・更新せず、E所有の指標はnullのまま。`no_change`再送でも同じ診断・指標を再計算する。

### 回帰検証

- readback：`_stored_readback`が実ファイルへ保存して読み戻したバイト列のhashとprovider形式のrevisionを作る。正常系、`content_fingerprint`を`content_hash`として渡した旧来の混同、保存後の改変（読戻しhash不一致と候補fingerprint不一致の両方）、`expected_revision`不一致、revision未指定時のopaque扱い、owner／scope不一致、不正hash、未知の要求fieldを両Skillで確認する。
- 指標：feature構成をmeasured／retired混在／unknown混在／全unknown／partial母集団／空母集団に変え、itemの`item_candidate_coverage`とconditionの`candidate_identification_coverage`が同一になること、非測定でnumeratorがnullになることを確認する。unknown時の`no_change`再送は既存の回帰テストで維持を確認する。

## 互換性・移行・rollback

- test-item-candidates-v1／test-condition-candidates-v1の旧payloadは、feature_inventory_contextがないlegacy formをread-onlyで検証可能。crosscheckではsource populationを完全と推定せずincompleteにする。次の成功materializeで現在のB contextを追加するが、stable ID、id_history、既存history eventは書換えない。
- 新規event IDはbody／sequence／previous event IDに結び付く。新readerはlegacy body-fingerprint eventとchain eventの双方を検証する。旧writerは新規chain eventを理解しない可能性があるため、provider書込みを有効化する前にD reader/writerの対応versionをA／PR #22で統一する。Dは旧artifactへ一括migrationや再採番を行わない。
- Dにproviderは選択されず、実保存・approval・CASは未接続。repository内に実保存artifactがあるとは確認していない。外部保存artifactの有無・backup・rollback実証は未検証。PR #22で保存先を選ぶ前に旧historyをread-only validateし、forward-compatible readerを配備してから最初のwriteを行う。
- rollback時はD artifactを旧writerで更新しない。復旧は新readerを使うcode forward-fixを優先し、旧writerへ戻す必要があれば保存artifactをread-only保全してowner承認の移行計画を立てる。実providerがないため現時点でデータrollbackは発生していない。
